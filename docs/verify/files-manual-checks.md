# 手で確かめるもの（admin/files）— 実機・ブラウザ・実クライアント ID が要る分

> 2026-08-15 storage が作成。**実装は済んでいるが、私の側では測れなかったもの**をまとめる。
> **宛先は特定の担当ではない。** 実機やブラウザを持てる人なら誰でも使える形にしてある。

## 0. 使い方（先に読む）

各項目は次の形で書いてある。

- **何を触るか** … 実際の操作
- **合格の形** … 🚨 **「動く」ではなく、観測できる形**で書いてある。目で見て判定できる
- **なぜ機械で測れないか** … 🚨 **次の人が「代用できないか」を考え直さずに済むように**

### 🚨 測れなかったときの書き方（これが一番大事）

**測れなかったものを「異常なし」にしない。** 次のどれかで書く。

```
✅ 合格   … 合格の形を実際に見た
❌ 不合格 … 合格の形にならなかった（何が起きたかを書く）
🚨 測れず … 端末が無い／画面が出ない／途中で落ちた等。**合格でも不合格でもない**
```

**「測れず」は失敗ではない。** 隠されるより、**測っていないと分かる方がはるかに良い**。
2026-08-15 に全員が踏んだのは、**「取りに行けなかった」を「無かった」と書いてしまう**形だった。

## 1. 掴んで放す操作（PC・ブラウザが要る）

### 1-1. 一覧にファイルを放り込むとアップロードされる

**何を触るか**
1. `http://localhost:3102/admin/files` を開く
2. デスクトップから画像ファイルを **1 つ、一覧の上へドラッグして放す**

**合格の形**
- ドラッグ中に **一覧全体に破線の枠**が出て「ここに放すとアップロードします」が見える
- 放すと **右下（SP は上部）にトースト**が出て「1 件アップロードしました」
- **一覧にそのファイルが増える**

**🚨 対照（これも見る）**
- **フォルダを開いた状態**で放すと、**そのフォルダの中**に入る（ルートに落ちない）

**なぜ機械で測れないか**
アップロードの経路（`POST /api/files`）は測ってある（フォルダ指定あり・なしの両方）。
🚨 **測れないのは「掴んで放す」というブラウザの操作そのもの**で、`DataTransfer` を伴う
ドラッグは HTTP では再現できない。CDP でも合成イベントの再現性が低い。

### 1-2. ファイルをフォルダへ運ぶと移動する

**何を触るか**
1. 同じ画面で、**ファイルのタイルを掴んで、フォルダのタイルの上で放す**

**合格の形**
- フォルダの上に来たとき **そのフォルダだけに破線の枠**が出る
- 放すとトーストに「1 件を移動しました」
- **一覧からそのファイルが消える**（移動先のフォルダを開くと居る）

**🚨 対照（これを見ないと意味が薄い）**
- **外からファイルを放り込んだとき**（1-1）と**混ざらない**こと。
  フォルダの上に放したのに**アップロードが始まったら不合格**

**なぜ機械で測れないか**

🚨 **ここに書いてあった「掴む操作は測れない」は誤りでした（2026-08-16 に訂正）。**
**測れます。** `--eval`（または `headless-browser.mjs` の `page.eval`）で
**`DataTransfer` を作って `drop` を投げられます**。**実際に通しました:**
```
検査用のフォルダとファイルを作る
  → dt.setData("application/x-ohmycms-file-ids", JSON.stringify([fileId]))
  → 放す先のタイルへ dragenter / dragover / drop を投げる
     🚨 タイルは **href に id が入っているもの**で特定する（見た目で選ばない）
  → **DB の folder が、放した先の id に変わった**（🟢 期待と一致）
  → 後始末: ファイルを元へ戻し、検査用フォルダを消す
```
🚨 **「合成イベントの再現性が低い」と書いていましたが、試していませんでした。**
**試したら通りました。**

**いま本当に測れないのはここだけです:**
- **枠が出るか**（`dragover` 中の見た目）… 出す/出さないの状態は測れますが、
  **人が見て分かるか**は目が要ります
- **本物のマウスで掴めるか** … 合成イベントは `draggable` 属性を無視して投げられるので、
  🚨 **`draggable` が壊れていても、この方法では通ってしまいます**（1-3 が別に要る理由）

### 1-3. 画像だけが単独でドラッグされていないか

**何を触るか**
画像のタイルを掴んで動かす。

**合格の形**
- **タイルごと**動いている（サムネイル画像だけが千切れて動いていない）
- フォルダへ放すと **1-2 と同じように移動する**

**なぜ機械で測れないか**
`draggable={false}` が付いていることはコードで分かるが、🚨 **実際に何が運ばれるかは
ブラウザが決める**。付け忘れると「画像だけが動いて、移動先で何も起きない」になる。

### 1-4. 選んだ画像を並べて、大きく見られる（原典 L95）

**何を触るか**
1. `http://localhost:3102/admin/files/new` を開く
2. **画像を複数まとめて選ぶ**（ドロップでも、箱を押してから選んでもよい）
3. 並んだサムネイルの **1枚を押す**

**合格の形**
- 選んだ枚数だけ **サムネイルが横に並ぶ**
- サムネイルに **カーソルを乗せると虫めがね（`cursor-zoom-in`）**になる
- 押すと **大きく開く**。左右で **選んだ他の画像へ移れる**
- 🚨 **拡大できる**（＋ボタン、SP はピンチ）。**ここが効かないことがある** →
  下の「なぜ機械で測れないか」を読む
- 閉じると **元の並びに戻り、削除の × もそのまま使える**

**🚨 対照（これも見る）**
- **画像でないもの（PDF 等）を混ぜて選ぶ** → **PDF のサムネは押せない**
  （押せて真っ白が開いたら不合格）
- 選び直したあとも **前に選んだ画像が混ざらない**

**なぜ機械で測れないか**

🚨 **ここに書いてあった「ブラウザでしか測れない」は誤りでした（2026-08-15 に訂正）。**
監査スクリプトには **`--file <パス>`** があり、**隠れた `<input type=file>` に実ファイルを
載せられます**。私はそれに気づかず「測れず」と書き、**その間ずっと見えていなかった違反が
1 件ありました**（ボタンが SP で 40px。44px 未満）。
```
node scripts/audit-surface-depth.mjs --base http://localhost:3102 --session <token> \
  --paths /admin/files/new --file /tmp/<画像>.png --measure 'button.cursor-zoom-in'
→ sp 44x44 / pc 40x40（直したあと）
```
🚨 **「測れず」と書くときは、道具の使い方を一度全部読んでから書くこと。**
**測れないと書いた瞬間に、誰も測らなくなります。**

**いま本当に測れないのはここから先です:**
- **ライトボックスが開くか / 拡大できるか**
  🚨 監査は **`--click` を `--file` より先に実行します**（実測: click 1370 行 / file 1435 行）。
  つまり **「ファイルを選んだ後に現れるものを押す」ができません**（`押した要素: NOT_FOUND`）。
  **選んでから出るものは、この道具では押せない**——ボタンの寸法までは測れますが、その先は人が要ります。
- **拡大が効くか**は特に目で見てください。実寸を渡さないと**黙って効きません**。
  ここはアップロード前なので DB に寸法が無く、**画像が読み込めた瞬間にブラウザから測って**います。

🚨 **ここで一度間違えました。**
HTML に「を大きく見る」という文字が在ったので ✅ にしかけましたが、
**それは辞書がクライアントへ積まれているだけ**で、描かれた `aria-label` ではありませんでした。
見分け方（対照）: **選んだ後にしか出ない別の文字（「外す」）も同じように在る**。
つまり **文字が在ること＝描かれたこと、ではない**。
`aria-label="…"` の形で正規表現に掛けたら **無い** と出ます。

🚨 **読み込みが速すぎる／遅すぎる場合に寸法を取り逃す余地**があり、
その取り逃しは**画面でしか見えません**。

### 1-5. 右クリックのメニューが、押した場所に出る（PC・ブラウザ）

**何を触るか**
`/admin/files` でファイル（またはフォルダ）のタイルを**右クリック**する。

**合格の形**
- メニューが **そのタイルのところ**に出る
- 🚨 **画面の左上に出ない**（2026-08-15 に実際にそうなっていた）
- 画面の**右端・下端**のタイルで右クリックしても、**メニューが画面外へはみ出さない**

**🚨 測るときは「押した座標」と「出た座標」を並べて出す**
「ずれている」ではなく、数字で:
```
押した (563,234) / タイル [386,33,354,402] / メニュー [386,439,176,30]
  → x がタイルと一致し、タイル下端の直下に出ている
はみ出し 右 -194 / 下 0
```
🚨 **メニューの箱の実座標で測る。**「押せる場所」と「見える場所」は別。

**🚨 起点が壊れていないかを、開かずに見る方法**
```
document.querySelectorAll('[data-slot=dropdown-menu-trigger]') の
  display と getBoundingClientRect() を**全部**出す
  → **display:contents / 矩形 0×0 が 1 つでもあれば、そのメニューは左上に出る**
🟢 対照(+) 実座標を持つトリガーが同じ画面に在ること（＝測り方が効いている）
```
**2026-08-15 の実測: 直す前 25 個中 23 個が 0×0 → 直した後 0 個。**

**なぜ機械で測れるのに見つからなかったか**
🚨 **一度もブラウザで右クリックしていなかった。**
`4ca9f6d` で入れたときの受入に、**位置の確認が入っていなかった**。
**「使うたびに壊れているのに、誰も画面で押していなかった」形。**

## 3. Google ドライブの実接続（実クライアント ID が要る）

### 3-1. 繋いで、一覧して、取り込む

**前提**
🚨 **実在する client_id が要る**。堀池さんに依頼中（2026-08-15 時点）。
**秘密鍵は要らない**（PKCE だけで組んである）。
🚨 **ただし redirect_uri が本番の HTTPS ドメインで通るかは未確認**。
ローカル（`http://localhost:3102/api/drive/callback`）での検証が先。

**何を触るか**
1. `/admin/settings/storage` で **クライアント ID** を入れて保存
2. `/admin/files/new` を開く → 「Google ドライブに繋ぐ」を押す
3. Google の同意画面で許可する
4. 戻ってきたら「一覧を取得」→ ファイルを 1 つ「取り込む」

**合格の形**
- 2 で **Google の同意画面が出る**（`accounts.google.com`）
- 3 の後 **`/admin/files?notice=drive_connected` に戻る**
- 「**<メールアドレス> で繋いでいます**」が出る
- 一覧に **ドライブのファイル名が並ぶ**
- 取り込むと **CMS のファイル一覧に増える**
- そのファイルの詳細に **「もとのファイルをみる」**があり、押すと**ドライブの画面へ飛ぶ**
- そのファイルに **「外部から取り込み」ラベルが付いている**

**🚨 測れなかったときの目印**
```
設定を入れていない        → パネルごと出ない（正常。不合格ではない）
設定はあるが繋いでいない  → 「繋ぐ」だけ出る（正常）
繋いだのに一覧が空        → 🚨 これは要報告（ドライブ側が空か、権限が足りない）
```

**なぜ機械で測れないか**
Google の同意画面は**人が押す前提**の画面で、自動化は規約上も技術上も想定されていない。
🚨 私が測れたのは「**同意画面へ送るところまで**」と「**設定が無い/繋いでいない状態の応答**」。

## 3.5 ラベルを消せない人に、正しい理由が出る（PC・ブラウザ）

**何を触るか**
1. **ラベルを触る権限が無い利用者**で `/admin/labels` を開く
2. ふつうのラベルの「削除」を押す

**合格の形**
- 「**権限がありません**」が出る

**🚨 対照（これを見ないと意味がない）**
- **権限がある人**で、**システム**と印の付いたラベルを見る → **削除ボタンがそもそも無い**
- 権限がある人がふつうのラベルを消す → **消える**

**なぜ機械で測れないか**
🚨 **サーバの応答は測ってあります**（2026-08-15 実測・7 経路）:
```
システムラベルを消す    403 LABEL_IS_SYSTEM
権限の無い人が消す      403 PERMISSION_DENIED   ← **同じ 403 だが原因が違う**
存在しない id を直す    404 LABEL_NOT_FOUND
重複した名前で作る      409 LABEL_EXISTS
101 文字の名前で作る    400 INVALID_FIELD
セッション無し          401 INVALID_SESSION
🟢 対照(+) 正常に作れる  201（エラー無し）
```
🚨 **測れていないのは「その `code` を受けて、画面にどの文字が出るか」**です。
分岐は `code` で書いてあり（状態コードで分けると **403 の2つの原因**でどちらかが嘘になる）、
**部品の `case` を抜き出して API 側と突き合わせる**ところまではやりました。
**トーストに出る実際の文字は、押してみないと見えません。**

## 4. 🚨 原典との1行照合（他の担当にも効く）

2026-08-15、**実装した項目を数えても取りこぼしは出ない**ことが分かった。

原典 L77「ラベルは検索でも引っかかる」

### 🚨 照合の落とし穴（2026-08-15 に実際に踏んだもの）

1. **cwd を間違えると「無い」と出る。**
   `.temp/…` を `apps/studio` から探して「No such file」→ **危うく「知らない」と答えるところだった**
   （実体はリポジトリ直下）。**パスが出てこないときは、まず自分がどこに居るかを見る**
2. **HTML に文字が在ること ≠ 画面に描かれたこと。**
   辞書はクライアントへ丸ごと積まれるので、**まだ描いていない文言も HTML に居る**。
   見分け方: **同じ条件でしか出ない別の文言（対照）も在るかを見る**。両方在れば、それは辞書
3. 🚨 **`grep -c` を使わない。** 2 つの罠がある。
   - **「行数」であって「個数」ではない**（1行に3個あっても 1 と出る）
   - **0 件のとき exit 1 を返す**（0 を印字したうえで）。だから
     ```
     ❌ grep -c "語" file || echo 0       … 0 が二重に出て、以降の数値比較が壊れる
     ❌ grep -c "語" file || echo "無い"   … **実在するファイルを「無い」と報告する**
     ✅ grep -n "語" file > /tmp/out.txt 2>&1; echo "exit=$?"; wc -l < /tmp/out.txt
     ```
   **2026-08-15 に 3 人が別々に踏んだ。私は朝に報告した本人で、その日の夕方に別の形で踏んだ。**
   **規律では止まらなかったので、形で塞ぐ**（規律8「ファイルへ落としてから `$?` を見る」と同じ）
4. 🚨 **対照は「在るものが在ると出る」側でなければ意味がない。**
   ```
   ❌ 対照(-)  存在しない名前 → 0 件      ← **本命も 0 なので、区別できていない**
   🟢 対照(+)  実在する名前  → **1 以上**  ← これだけが、探し方の正しさを保証する
   ```
   **パス間違い・クォート漏れ・cwd 違いは、どれも 0 を返します。**
   `(-)` はそれらを1つも検出できません。**`(+)` の無い「0 件」は書かない。**
   （2026-08-15 に私自身が 2 回やりました。結論は両方とも変わりませんでしたが、
   **結論が同じでも、根拠が無かったなら言う**）
