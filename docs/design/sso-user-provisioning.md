## 0. 読み取ったこと（**私の読み。違っていたら止めてください**）

| 堀池さんの言葉 | 私の読み |
|---|---|
| 「メアドリストがあればいい」 | **招待メールもパスワード発行も要らない**。入口は IdP 一本 |
| 「そこに無い人は**権限がありません**」 | **入れないのではなく、入れるが何もできない**。文言が「権限がありません」なので**認可で落ちる** |

🚨 **「権限がありません」は認証の失敗の文言ではありません。** ここが設計の分かれ目（§1）。

## 1. 🚨 どの層で落とすか（**司令塔の問い①への答え**）

**認証は通す。セッションは作る。認可で落とす。**

    IdP で本人確認 → 利用者の行を作る／更新する → セッションを作る
    → 🚨 **ポリシーを一切割り当てない**
    → 画面も API も **403 ADMIN_ACCESS_REQUIRED / PERMISSION_DENIED** で落ちる

**理由**:
1. **堀池さんの文言がそう言っている**。「権限がありません」は**入れた人に出す言葉**。
   入れないなら「ログインできません」になるはず
2. **`AGENTS.md` §3.5 と整合する**——**サーバ側で拒否**する形になる。
   いまの `lib/permissions/resolve.ts:247` の `requireAdminAccess` が**既に 403 を投げる**ので、
   **新しい仕組みを作らずに済む**（一覧に無い人は「権限を持たない普通の人」になるだけ）
3. **運用が回る**。一覧に入れ忘れた人が来たとき、**その人が誰か記録に残る**。
   セッションを作らないと「誰かが弾かれた」しか分からず、**管理者は誰を追加すべきか分からない**

🚨 **反対の案（セッションを作らない）を採らない理由**:
「入口で弾く」と、**IdP で認証は成功しているのに製品側に痕跡が残りません**。
**招待の代わりが「一覧に足す」である以上、足す相手が分からないと運用が詰みます**。

🚨 **ただし例外が1つ**: 一覧に無い人の行を**作る**なら、**その行が管理者の頭数に混ざらない**ことを
`sso-only-switchover.md` §3.3 の判定で保証すること（**ポリシーを持たないので自動的に混ざらない**が、
**実測で確かめる**）。

## 2. 一覧の置き場所（**司令塔の問い②への答え**）

**DB に置く。`ohmycms_saml` の設定と同じ場所**（＝SSO の設定の一部）。

  ・**環境変数にしない**。🚨 **管理者が画面から足せないと、運用のたびに再デプロイ**になる。
    「メアドリストがあればいい」は**運用で足すもの**として言われている
  ・**独立した表にする**（`ohmycms_saml_allowed_emails` のような）。
    🚨 **設定の1列に改行区切りで詰め込まない**——**1件ずつ足す・消す・誰が足したかを記録する**のに要る
  ・**照合は小文字で正規化して完全一致**。🚨 **前方一致やドメイン一致にしない**
    （「`@example.com` なら全員」は**別の機能**。欲しければ改めて決める）

### 2.1 「全員権限付与」

**【2026-08-15 実装済み `107e6b2`。初版から2点直した】**

    ohmycms_saml_config に 2 列: grant_all_enabled（真偽・既定 false） / grant_all_policy（付けるポリシー）

🚨 **初版の `grant_all_role` は誤り。実装上の単位は「ポリシー」。**
実測: `directus_roles` は **0 行**、`directus_access` の 209 行は**すべて `role=NULL・policy=<uuid>`**。
**role という列名にすると、0 行のテーブルを指す列になる。**
（同じ取り違えを `6469082`「Admin は『Administrator ポリシー』だった」で一度やっている）

  ・ON … 🚨 **一覧を見ない**。来た人全員に `grant_all_policy` を付ける
  ・OFF … 🚨 **何もしない**（初版の「その人ごとに決めた role」は**作っていない**。
    一覧は**入場の可否だけ**を持つ——§5-2 の推奨どおり）
  ・🚨 **切に戻しても、既に付いた権限は剥がさない**（設問 252 の回答＝A・2026-08-15）。
    「これから来る人に自動で付けない」の意味。**要らない人は個別に外す**
  ・🚨 **ON にした瞬間、IdP で認証できる全員が入れる**。**IdP のテナントの広さ＝権限の広さ**になる。
    **切替の画面に、その一文を出す**（`every-element-must-earn-its-place` に反しない。**警告は機能**）
  ・🚨 **この表は単一行（`CHECK (id=1)`）で :3101 / :3102 / :3103 が同じ行を見る。**
    **1つの環境で ON にすると全環境で ON になる。** 受入・検証でこの2列を書き換えないこと
    （8/14 に `sp_entity_id` で同じ形の事故: 受入が入れた値で :3102 のログインが全部落ちた）

### 実測（実物の Keycloak・2026-08-15）

    入にして往復        その人の access **1 → 2**（ポリシーが付いた）
    もう一度往復        **2 のまま**   ← **毎回のログインで行が増えない**（先に select してから insert）
    切にして往復        **2 のまま**   ← **252=A の実測**（既に付いた権限が残る）
    設定を戻す          値が一致し、**往復も通り、付与も起きない**

## 3. 🚨 検証をどう成立させるか（**司令塔の指摘。ここが一番弱い**）

**本番に IdP が無いので、「一覧に無い人が拒否されるか」を本番では確かめられません。**
**これは「異常が無い」ではなく「試せていない」です。**

**成立させる道は3つ。私の推奨は ①**:

    ① **使い捨ての IdP をコンテナで立てる**（Keycloak。sdk が :3107 で提案済み）
       → **本物の SAML 応答**で通せる。🚨 **外部の公開 IdP に依存しない**
         （FAIL が製品の問題か外の問題か切り分けられなくなる）
    ② `upsertSamlUser` を**直接呼ぶ検証**（`lib/auth/saml/verify.ts:191`）
       → **認可の判定は測れる**が、**IdP から来る値の形は測れない**
    ③ 本番で堀池さんに実際に試してもらう
       → 🚨 **一覧に無い人＝堀池さん以外が要る**。**用意できない**

🚨 **①が立つまで、この機能を「できた」と言わないこと。**
**「一覧に無い人は 403」は、否定側を測って初めて言えます**（**肯定側だけ緑でも意味がない**——
一覧に在る人が入れることは、拒否が効いている証明になりません）。

### 3.1 ①は立った。実測の結果（2026-08-15・HEAD `ca15a5f`）

**Keycloak が `:3108` で動き（saml が構築）、実物の SAML 往復で3通りとも記録できた。**

    一覧が空            → reason="not_listed"  email=saml-tester@example.com
    一覧へ足す          → reason="allowed"     email=saml-tester@example.com   ← 🟢 肯定側の対照
    属性の対応づけを外す → reason="no_email"    email=null

🚨 **肯定側（2行目）が無いと、1・3行目は「いつも false を返す実装」と区別できない。**

**まだ測れていないもの**: **email 属性を送ってこない IdP そのもの**。
3行目は**属性の対応づけを外して `identity.email === null` の分岐を再現した**ものであって、
**`mapProfileToIdentity` より手前（IdP が何を送るか）は測っていない。**

### 3.2 🚨 設計に無かった壊れ方: **届いているのに取れない**

**実測（2026-08-15）**: Keycloak は
`http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress` でメールを送ってくる。
`ATTRIBUTE_DEFAULTS.email`（`lib/auth/saml/config.ts:31`）が見るのは**次の4つだけ**:

    emailaddress の claim URI / urn:oid:0.9.2342.19200300.100.1.3 / email / mail

🚨 **この4つ以外の名前で送る IdP を繋ぐと、メールは届いているのに `identity.email` は null になり、
全員が「メールが取れない人」として記録される。** 管理者は一覧を疑うが、**原因は属性の対応づけ**。

    ❌ 画面に「メールアドレスが**届いていません**」→ 管理者は IdP が送っているかを疑う
    ✅ 画面に「メールアドレスが**取れていません**。属性の対応づけを確認してください」

**NameID で代用できない**。実測した NameID は
`G-f23cb26d-…`（Format=`persistent`）＝**不透明な永続 ID で、メールではない**。
**管理者が一覧に足せる値ではない**ので、**メールが取れない人は許可しようがない**
（`verify.ts` は NameID を `external_identifier` に持つので、**IdP 側で引けば誰かは特定できる**）。
