## 0. 🚨 読み違えやすいので、先に

**「メールをやめる」ではありません。**

    ❌ メールを無くす           … **OTP も招待も消える**方向。原文と違う
    ✅ **既定では要らない**       … 環境変数のパスワードで初回に入る
    ✅ **設定すれば使える**       … SMTP を設定すると OTP が選べる
    ✅ **OTP と SSO は共存**      … 外部ライターは OTP、社内は SSO、など

**つまり `email` は「識別子」から「連絡先（あれば使えるログイン手段）」へ降格する。**

    directus_users.external_identifier **nullable** ・ 一意

## 2. 🚨 いちばん大事な発見: **同じ穴が 3 つ空く**

**メールを識別子から外すと、「メールで指していたもの」が全部行き場を失う:**

    ① **内部専用の固定ユーザー**を指す手段
       🚨 **初版は「2 箇所」と書いたが、数え足りなかった**（`service.ts` しか見ていなかった）。
       **役割で割ると 5 箇所**（実測 2026-08-16。onboard の指摘で生産側と受入が見つかった）:

         **生産** `lib/settings/service.ts:615`  insert で `email: LOCAL_ADMIN_EMAIL` を作る
                                                 （🚨 **`external_identifier` は null のまま**
                                                   ＝ local の 2 人に印が無い理由）
         **参照** `lib/settings/service.ts:455 / :601`  その行を引く
         **表示** `lib/admin/user-label.ts:15`   画面に出さないための番人
         **受入** `acceptance/checks/v1-e-first-run.mjs:317`
                                                 🚨 **この email で delete している**
                                                 ＝ NULL にすると **0 件を消して緑のまま**になる

       🚨 **「引いている場所」だけ数えると、生産側と受入が漏れる。**
       **消す作業では、作る側と、それに乗っている検査も同じ数のうち。**
    ② 🚨 **「最初に作った人」**を指す手段
       251-B（最初の人の Administrator は外せない）に要る。
       **いまも無い**（`directus_users` に作成時刻の列が 0 件・実測済み）
    ③ **SSO でメールが来ない人**を指す手段
       いま `<uuid>@saml.invalid` を作って埋めている

**🚨 3 つとも「行に印を付ける」で解ける。** **別々に作ると、また偽の値が増える。**

## 3. 案

### 案A（推奨）: **`id`（uuid）を唯一の識別子にし、`email` を nullable にする**

    email      NOT NULL → **nullable**、一意は**部分一意**（NULL 同士はぶつからない）
    識別子     **`id`（uuid）**。既に主キーで、全員が持っている
    ログイン   メールがある人 … パスワード / OTP（**いまと同じ**）
               メールが無い人 … SSO / リカバリーコード / 初回の環境変数
    偽メール   🚨 **生成をやめる**（`<uuid>@saml.invalid` の行は不要になる）

  ・**引き換え**: 🚨 **画面の「その人が誰か」がメールで表せなくなる**
    → **表示名（`first_name` / `last_name`）** と **アバターの絵文字**で出す（**既にある**）
    → 🚨 **表示名も無い人**は、**何も出ない**。**そこをどうするかは決めが要る**
  ・**引き換え**: **メールで引いている 21 箇所**（実測）のうち、
    **メールが無い人にも効く必要があるもの**を見分ける作業が要る
  ・**利点**: **偽の値を作る仕組みが丸ごと消える**（§2 の③が解決）

### 案B: **`provider` + `external_identifier` の組を識別子にする**

  ・**引き換え**: 🚨 **local の 2 人に `external_identifier` が無い**（実測）。
    **埋めるには値を生成することになり、`@saml.invalid` と同じ「偽の値」を別の列で作る**
  ・**利点**: SSO の人だけを見れば、いまでも一意に引ける

### 案C: **`username` 列を新設する**

  ・**引き換え**: 🚨 **原文に無い**。堀池さんの流れは「環境変数 → SMTP で OTP → SSO」で、
    **利用者が名前を決める場面が出てこない**。**画面を1つ増やす提案になる**
  ・**利点**: メールが無くても人が読める識別子になる

## 4. 🚨 §2 への手当て（**どの案でも要る**）

**`directus_users` に、行の性質を示す印を足す。**

    内部専用か  … ① を解く（`email = LOCAL_ADMIN_EMAIL` をやめられる）
    最初の人か  … ② を解く（251-B が実装できるようになる）

🚨 **②は「これから作る環境でしか正しく付けられない」**（既に動いている環境では、
誰が最初かを後から決められない——実測済み）。**だから記録は早いほど正しい。**
**メールを外す作業と同じ migration で入れるのが安い。**

## 5. 既存データの移行

    `local-admin@localhost`（1 件）  … 🚨 **印を付けてから** email を NULL にする
                                       （印より先に消すと、その行を指す手段が無くなる）
    `<uuid>@saml.invalid`（0 件）    … いまは 0。**生成する経路を止めるだけ**
    `@example.com`（244 件）         … **検証用の実データ。触らない**
    本物の利用者                     … **そのまま**（メールは連絡先として残る）

🚨 **順序が要点**（onboard の指摘で 1 段増えた）:

    ① **印を付ける**（列を足す）
    ② **参照を印に切り替える**（`service.ts:455 / :601` ／ `user-label.ts:15` ／ 受入）
    ③ 🚨 **生産側を止める**（`service.ts:615` が偽メールを作るのをやめる）
    ④ **既存の行の email を NULL にする**

🚨 **③を飛ばすと、④のあとで「次に初期設定した人が、また偽メールを作る」。**
**onboard の受入（V1-E）は毎回まっさらな DB で初期設定を通すので、すぐ再現する。**
🚨 **逆順（④が先）だと、切り替える前にその行を指せなくなる。**

**受入の直しは onboard が持つ**（印の列が決まってから。**決まる前に直すと、
別の鍵に乗り換えるだけになる**——本人の判断）。

## 5.5 🚨 これは 282 では解けない（saml の指摘・**先に閉じる必要がある**）

**どの案を採っても、「同じ人を、次のログインで同じ行に結ぶ」は別問題として残る。**

    【測った・saml】`lib/auth/saml/client.ts:96`  identifierFormat: **null**
      理由（コメント）「メールに固定すると IdP にメールを要求してしまう。
                       Entra ID の永続 ID など、メールでない識別子を返す IdP で入れなくなる」
    【測った・saml】`metadata.ts` が受け入れると広告している形式 … **4 つ**
      unspecified / persistent / 🚨 **transient** / emailAddress

🚨 **`transient` は「毎回変わる」形式。** IdP がそれを選ぶと:

    NameID が毎回違う → `external_identifier` が毎回違う
    → 🚨 **ログインのたびに新しい利用者の行ができる**

    案B … 識別子そのものが不安定になる（**成立しない**）
    案A … `id` は安定だが、**再ログインで既存の行に結ぶ**のは
           いまも `external_identifier` で引いている（`verify.ts:197`）→ **同じく結べない**

🚨 **＝ これは識別子の設計ではなく、SAML の受け入れ形式の問題。** **分けて扱う。**
**282 より先に「transient を受け入れるか」を閉じないと、どちらの案も足元が動く。**
（対処は「広告から外す」「Assertion の Format を検査して拒否」の 2 つだが、
**どちらも `knowledge/decisions/auth-methods.md` の「メールに固定しない」に近い場所**なので、
**saml の一存では動かせない**——本人の判断）

### 🚨 「SSO なら本物のメールが来る」には根拠が無い（saml の自己訂正）

    【測った】provider='saml' の利用者は **1 人だけ**
    その 1 人のメールは `saml-tester@example.com` ＝ 🚨 **saml が Keycloak に設定した値**
    ＝ **標本 1 件、しかも自作**

**したがって「SSO 利用者にはメールがある」を前提にできない。**
🚨 **これは案A を後押しする**（メールが無い人が普通に居る前提で作る）。
