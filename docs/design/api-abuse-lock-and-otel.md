# API 濫用ロック ＆ OpenTelemetry 連携（運用ハードニング）

> 由来: 2026-08-14 堀池指示。原文:
> 「デフォルトで同じ API キー・トークンで大量のアクセスや操作があったらエラーにして一時的に
> ロックする機能も装備。OTel との連携もしやすくする。」
>
> これは **docs（設計素材）**。決定に落ちたら `knowledge/decisions/` へ要点を移す。

## 1. API キー/トークンの濫用ロック（レート制限＋一時ロック）

**既定で、同一の API キー/トークンからの過剰なアクセス・操作を検出して 429 で弾き、一時的にロックする。**
（設定でしきい値を変えられるが、**無効化を既定にしない**＝安全側の既定）。

### 設計の要点

- **数える単位**は「キー/トークン」（＋補助で IP）。ユーザーセッションとは別に、
  **機械アクセス（API キー・PAT・SSO トークン）を主対象**にする。
- **2 段構え**:
  1. **レート超過** → その時だけ `429 Too Many Requests` + `Retry-After`（短時間の絞り）。
  2. **継続的な濫用**（短時間に閾値を何度も超える／認証失敗の連発） → **一時ロック**
     （そのキーを一定時間 403/423 で締め出す。ロック中はエラーで明示）。
- **カウンタの置き場**: リクエスト単位で動く Next.js の route handler では持てない
  （`AGENTS.md §3.6` の「lib は素の値」原則と、`single-nextjs-app-then-hono` の背景）。
  → **DB か Redis 等の共有ストア**に置く（プロセスを跨いで一貫する）。まずは DB(Postgres) の
  カウンタ行 or 単純な token-bucket テーブルで始め、負荷が上がれば Redis へ。
- **認可の最終判断はサーバ/DB**（`AGENTS.md §3.5`）。レート制限も**middleware/proxy だけに置かない**
  （matcher 漏れ・API 直叩きで素通りする）。**API ハンドラ側 or DB 層**で強制する。
- **観測可能に**: ロック発火・解除・429 発生を**メトリクス/ログに出す**（§2 の OTel に載せる）。
  「なぜ弾かれたか」を管理画面から見られるようにする（キー別の直近レート・ロック状態）。
- **誤爆対策**: 正規の大量バッチもあるので、**キー単位でしきい値を上書き**できる
  （信頼済みキーは緩め、公開系は厳しめ）。ロックは**自動解除（TTL）**を既定にし、手動解除も可能に。

### 受入基準（実装時）

- [ ] 同一キーで閾値超のリクエストを送ると `429` + `Retry-After` が返る（実測）
- [ ] 連続超過で一時ロック（`403/423`）に遷移し、TTL 後に自動解除される（実測）
- [ ] 別キー/別 IP は巻き込まれない（分離の実測）
- [ ] middleware を通さず API を直叩きしても効く（サーバ/DB 側で効いている）
- [ ] 発火/解除がメトリクスとログに出る

## 2. OpenTelemetry(OTel) 連携をしやすくする

**OTel でアプリを計装し、OTLP で「任意の OTel 互換バックエンド」に送れるようにする。**
バックエンドを**コード変更なし・環境変数だけ**で差し替えられる状態を既定にする。

### OTel とは（堀池の理解の整理）

- 堀池の理解「OpenAPI みたいにプロトコル」——**方向は合っているが、対象と範囲が違う**。
  - **OpenAPI** = REST API の**形（契約）を記述する標準の言語**（何が呼べるか）。
  - **OpenTelemetry(OTel)** = **観測データ（テレメトリ）を出す・運ぶ標準**。中身は
    **API + SDK + ワイヤプロトコル(OTLP) + 意味規約(semantic conventions)** の束。
- **「どんなものでも対応できる？」**——**バックエンドについては YES。**
  OTel で 1 回計装すれば、**Grafana(Tempo/Loki/Mimir) / Jaeger / Prometheus / Datadog /
  Honeycomb / New Relic / Grafana Cloud** など**OTel 互換の送り先ならどれにでも**、
  エクスポータ設定（＝環境変数）を変えるだけで送れる（アプリのコードは変えない）。
  - ただし**扱えるデータは「テレメトリ 3 種」に限られる**（万能の汎用データパイプではない）:
    - **Traces（トレース）**: 1 リクエストが通った処理の連なり（どこで遅い/落ちたか）
    - **Metrics（メトリクス）**: 数値の時系列（QPS・エラー率・レイテンシ・§1 のロック発火数 等）
    - **Logs（ログ）**: 構造化ログ（トレースと相関づく）
- **OTLP** = OTel の転送プロトコル（gRPC か HTTP）。**Collector** という中継（受けて加工して振り分ける）
  を挟むのが定番。アプリ → (OTLP) → Collector → 各バックエンド。

> 一言でいうと: **「計装は 1 回、送り先は自由」** を実現する“観測の共通規格”。
> OpenAPI が「API の書き方の共通語」なら、OTel は「監視データの出し方の共通語」。

### 設計の要点

- **標準の OTel 環境変数をそのまま読む**: `OTEL_EXPORTER_OTLP_ENDPOINT` /
  `OTEL_EXPORTER_OTLP_HEADERS`（認証）/ `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES`。
  → **送り先の差し替えが env だけ**で済む（＝「連携しやすい」の実体）。未設定なら**何も送らない**
  （既定オフ・S3 の 4 変数と同じ思想）。
- **`lib/` にフレームワーク依存を持ち込まない**（`AGENTS.md §3.6`）。計装の初期化は
  アプリ境界（instrumentation フック）に置き、ドメインロジックは素のまま。
- **秘密を載せない**: OTLP ヘッダのトークンは env/保管庫から。**スパン属性に PII や
  トークンを入れない**（`auth-session-jwt-cookie.md` と同じ規律）。
- **§1 と接続**: レート制限/ロックの発火をメトリクス（例 `ohmycms.ratelimit.blocked`）と
  ログで出す。運用時に「濫用が起きているか」を OTel バックエンドで見られる。

### スコープ / 段階

- **V1 では未装備**（デプロイ優先）。両機能は **V1 後の運用ハードニング**。
- 順序案: ①濫用ロック（DB カウンタの最小版）→ ②OTel（メトリクス/ログ先行、トレースは後）。
- OhMyCMS は Hono へ API 分離する構想（`single-nextjs-app-then-hono`）があるので、
  **レート制限とテレメトリは「分離後もそのまま持っていける」**よう `lib/` 境界を守って作る。
