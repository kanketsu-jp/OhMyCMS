## 0. この機能の本質は「締め出し」

「それ以降は SSO ログインのみ」は、**間違えると誰も入れなくなる**状態を作るということ。
機能としてではなく、**壊れ方から設計する**。

**壊れ方（司令塔の列挙に、実測で1つ足した）**

| # | 壊れ方 | 起きたらどうなるか |
|---|---|---|
| A | SSO の設定を間違えたまま切り替えた | 誰も入れない |
| B | Admin に指定した人が SSO で入れない（アカウントが無い／メールが違う） | 誰も入れない |
| C | IdP が落ちた・証明書が期限切れ | 誰も入れない（**時間差で来る**） |
| D | 最後の管理者から admin を外した | 設定を戻せる人が居なくなる |
| **E** | **切り替えた瞬間、既存のセッションだけが生きている** | **そのタブを閉じた時点で誰も入れない**（🚨 下記） |

🚨 **E は「切り替え直後は普通に使えてしまう」ので、いちばん気づきにくい。**
既にログイン済みのセッション（`directus_sessions`）は切り替えの影響を受けない。
**画面は動き続け、翌朝に誰も入れなくなる。**

## 2. 🚨「割り当て解除できない」の読み

**私の読み: 「最後の管理者は外せない」（＝後者）。** 根拠:

1. **前者（初回ユーザーが永久に Admin）だと、その人が辞めたとき詰む。**
   `directus_users` に削除の経路が無い以上、**行は残り続ける**。
   「永久に Admin な、もう居ない人」が1人固定される。
2. 堀池さんの文は **SSO の切り替えとセットで語られている**
   （「SSO を設定する時、その Admin として**誰を付与するか**を選ぶ」）。
   **付与先を選び直せる**という前提が同じ文の中にある。
   → 初回ユーザーが不変なら「誰を付与するか選ぶ」に意味が無い。
3. 守りたいのは**特定の個人**ではなく「**設定を戻せる人が必ず1人は居る**」という状態。

🚨 **ただし断定はしない。** 「初回ユーザーは特別扱い」という読みも文面から可能で、
**どちらかで作ると後から変えるのは高い**（片方は migration と運用手順に波及する）。
→ **堀池さんに確認する価値がある。** 司令塔へ判断ボード行きを依頼する。

**確認したい問い（そのまま使えます）**:
> 「最後の管理者を外せない」でよいですか。それとも「**初回に作った人だけは、他に管理者が居ても外せない**」ですか。
> 前者だと、初回の人が辞めても他の管理者へ引き継げます。後者だと、その人の行が永久に残ります。

## 3. 提案

### 3.1 切り替えの条件は「設定した」ではなく「**入れた**」

🚨 **`saml.enabled = true` を保存しただけでは切り替えない。**
**指名した Admin が、実際に SSO で1回ログインできたこと**を条件にする。

    状態は3つ:
      password_only        … いま（既定）
      sso_ready            … SSO の設定は入った。**まだパスワードも使える**
      sso_only             … パスワードを閉じた

    sso_ready → sso_only の遷移は、**画面の操作では起こさない**。
    「指名された Admin が SSO で入った」ことを**サーバが観測した時だけ**進む。

  ・観測の記録先は **`ohmycms_saml` に1列**（例 `verified_admin_user` / `verified_at`）。
    🚨 **`saml.enabled` と混ぜない**（`config.ts:92` が既に
    「**enabled と『実際に動かせる状態』は別**」と書いている。**その区別をもう1段深くするだけ**）
  ・これは**壊れ方 A と B を同時に塞ぐ**。設定間違いも、Admin が入れないことも、
    **切り替える前に必ず現れる**

#### 🚨 指名できる Admin は「実在のメールを持つ人」だけ（2026-08-15 追記）

> 🚨 **【同日夜・この節の前提が揺れています】堀池さん（原文）: 「メールアドレスは必要ない。」**
>
> **この節は「実在のメールを持っているか」で指名できる人を絞っています。**
> **メールが識別子でなくなるなら、絞る基準そのものが変わります。**
>
>     ✅ 生きている … **谷そのもの**（切り替えを実行する人と、切り替え後に入る人が別人になる）。
>                      これは**識別子が何であっても起きます**
>     🚨 保留       … **「実在のメールを持つ人」という指名の条件**
>
> **メール無しの場合、指名の鍵は `external_identifier`（IdP の NameID）になります。**
> 🚨 **その値は管理者が事前に知り得ない**ので、**「先に指名する」ができません**——
> **一度 SSO で入ってもらってから指名する**順序になります。
> **これは §3.1 の「切り替える前に、指名した人が実際に SSO で入れることを見る」と、実は噛み合います。**
> **（先に入ってもらう必要がある、という点で同じ）。未決なので、ここでは決めません。**

**初版はここを書いていなかった。** 実測して分かったこと:

    Administrator を持つ人の provider（共有の開発 DB・2026-08-15）
      local  **admin@ohmycms.local**
      local  **local-admin@localhost**
      saml   saml-tester@example.com（検証用）
             🚨 **2026-08-15 に外した。** 検証用アカウントが管理者だと、
             **「一覧に無い人は 403」を測ったときに偽の緑が出る**（saml が発見）。
             利用者は残してある（受入の往復が IdP 側の `saml-tester` と結びつくため）。
             **外したあと、SAML の往復が通ることと、代替の管理者口で入れることを動作で確認済み。**

### 🚨 外したことで、初めて測れたもの（2026-08-15・実物の Keycloak）

**`sso-user-provisioning.md` §4 の受入 #1 は「本番では測れない」と書いていたが、
Studio 側だけで測れた**（IdP は要ったが、本番は要らなかった）:

    一覧 0 件・この人は not_listed の状態で、実物の IdP のセッションを使って:
      GET /api/auth/me        → **200**   ← セッションはできる
      GET /api/policies       → **403**   ADMIN_ACCESS_REQUIRED
      GET /api/settings/saml  → **403**
    🟢 対照(+) 同じ `/api/settings/saml` を**管理者のセッション**で → **200**
      （＝「全部 403」ではない。**拒否が効いている**ことの証明）

    さらに: **一覧に載せてから**同じことをしても → `/api/policies` は **403 のまま**
      （`saml_allowed=true` は記録されている）
      ＝ 🚨 **一覧は「入場の可否」だけで、権限を与えない。** §5-2 の推奨どおりに分離できている

🚨 **この測定は、saml-tester が管理者のままなら永久にできなかった**（全部 200 になる）。
**「測れない」と書いたものの一部は、測る条件を作れば測れる。**

🚨 **`localhost` も `ohmycms.local` も実在しないドメイン**で、**IdP がその値を返すことはあり得ない**。
つまり **いまの管理者2人は、そもそも SSO で入れない**（`sso-user-provisioning.md` の許可リストにも足せない）。

**したがって**:
  ・**切り替えを実行する人**（いまパスワードで入っている管理者）と
    **切り替え後に入る人**（実在のメールを持ち、IdP に居る人）は、**別人になる**
  ・**指名の相手は「実在のメールを持つ管理者」でなければならない。**
    🚨 **`local-admin@localhost` を指名できてはいけない**（**永久に「入れた」が観測されず、
    切り替えが完了しないまま止まる**）
  ・→ **指名の画面・API は、`@localhost` や実在しないドメインの利用者を候補から外すこと。**
    **外す理由を画面に出す**（黙って消すと「なぜ選べないのか」が分からない）

**これは「切り替えの谷」（一覧が空の状態で SSO のみにすると誰も入れない）を渡す唯一の橋でもある**:
    1. **まだパスワードで入れる状態のまま**、管理者が**実在のメール**を許可リストへ足す
    2. **一度 SSO で入ってみる**（この時点ではパスワードも生きている＝**失敗しても戻れる**）
    3. **入れたことをサーバが観測して初めて**、`sso_only` へ進める
🚨 **順序を強制するので、「鍵をかけたが鍵を渡す手段が無い」状態が構造的に起きない。**
  ・🚨 **今日ずっとやってきた「宣言ではなく実測」を、製品の安全装置として使う形**
    （司令塔の叩き台どおり。私からの変更なし）

### 3.2 非常口は**残す**。ただし既定は閉じる

**残す**。理由は**壊れ方 C（IdP が落ちる・証明書切れ）が自分たちの操作と無関係に起きる**から。
SSO だけにすると、**製品の可用性が他社の稼働に完全に従属する**。

    OHMYCMS_ALLOW_PASSWORD_LOGIN=true   … 既定 **false**（未設定なら閉じている）

  ・🚨 **DB ではなく環境変数**にする。DB に置くと、**入れない状態では変えられない**
    （入れないから開けたいのに、開けるには入る必要がある、という循環）。
    環境変数なら**サーバに触れる人**が開けられる
  ・🚨 **開いたことが分かる形にする**: 起動時に警告を出す
    （`app/api/auth/dev-login/route.ts:10-17` が**既に同じ形**をしている。**それに倣う**）
  ・🚨 **既定値を `pass132` のような公開値にしない**
    （`.temp/2026-08-13/auth-state.md` §3.3 の実事故。**リポジトリに書かれた値は公開値**）

### 3.3 最後の管理者を外せなくする（🚨 3経路すべて）

**判定**: 「この操作のあと、`admin_access` を持つポリシーに割り当てられた
**active な利用者**が 1 人以上残るか」。残らないなら **409 で拒否**。

#### 🚨 何を「管理者」と数えるか（**`Administrator` だけでは数えない**）

**`admin_access = true` の全ポリシーで数える。** 名前で絞らない。理由:

  ・**守りたいのは「設定を戻せる人が居ること」**であって、特定のポリシー名ではない。
    `admin_access` を持つ人は**実際に設定を戻せる**ので、名前が何であれ数に入るべき
  ・🚨 **名前で絞ると、両側に嘘が出る**（実測に基づく）:
    - `Administrator` **だけ**で数えると、`dev-admin` しか持たない人しか居ない環境で
      **「0 人」と判定され、権限を触る操作が全部 409 になる**（＝何もできなくなる）
    - 逆に `dev-admin` を管理者として数えない設計にすると、**その 197 人は自由に外せる**のに
      **admin_access は持ったまま**——「守っているつもりで守れていない」状態になる
  ・**ポリシーは増える。** 名前の一覧を持つと、新しい管理者ポリシーが増えるたびに更新漏れが出る。
    **`admin_access` という性質で数えれば、増えても自動で入る**

  🚨 **`dev-admin` の存在自体は別の問題**（§5-5）。**数え方の決定はそれと切り離す**——
  「開発用の抜け道が混ざっているから名前で除外する」は、**上の2つ目の嘘を作る**。

  ・🚨 **`local-admin@localhost` も数に入れる**（§3.4）。
    🚨 **これは 2026-08-15 に訂正した。初版では「数に入れない」と書いていた。**
    間違いだった理由: **パスワードだけで入っている環境では、あの行が唯一の管理者**。
    数に入れないと**残り 0 人と判定され、3経路すべてが常に 409 になる**（＝権限を一切いじれない）。
    同じ誤読で**本番の不具合を1つ出している**（アイコンを変えられなかった。`40d9eb3`）。
    誤りの正体は「**画面に出さない = その利用者は実在しない**」と読み替えたこと。
    **画面に出さないのはメールアドレスの話**で、**その人は実際に操作している**。
  ・🚨 **判定と更新の隙間を消す**。`SELECT ... FOR UPDATE` で対象行を掴んでから数える
    （`lib/auth/otp.ts` の `verifyLoginCode` で使った形。
    **`SKIP LOCKED` にしない**——あれは10並列で全部すり抜けて上限が効かなかった実測がある）
  ・**3経路（①割り当て削除 / ②ポリシーの admin_access を落とす / ③ポリシー削除）で同じ関数を通す**

### 3.4 `local-admin@localhost` の扱い

**残す。ただし「セッションの持ち主」以上の意味を持たせない。**

  ・理由: `directus_sessions.user` が **NOT NULL** で、
    パスワードだけで入る経路（`/api/auth/setup`）には**人のアカウントが無い**
  ・🚨 **メールアドレスを画面に出さない**（`lib/admin/user-label.ts` が既に弾いている。**この保護を外さない**）
  ・🚨 **ただし「実在しない」わけではない。** ここを取り違えると壊れる:
    - **管理者の頭数には数える**（§3.3）。あの行が唯一の管理者である環境がある
    - **本人の設定（アイコン・名前）は変えられてよい**。実際に操作しているのはこの人
    - 出さないのは**メールという文字列だけ**。それ以外の権利を奪う根拠にしない
  ・**実在の人へ引き継がない**——引き継ぐと「メールを出してはいけない行」が人のアカウントと混ざる

### 3.5 🚨 壊れ方 E（既存セッション）への備え

**`sso_only` へ移った時点で、パスワード経由で作られたセッションを切る。**

  ・そうしないと「**切り替えた直後は普通に使えて、翌朝に誰も入れない**」という
    **いちばん気づきにくい壊れ方**が残る
  ・切り替えを**その場で検証可能にする**効果もある（切った直後に SSO で入り直せるかを見る）
  ・実装の目印: `directus_sessions` に「どの経路で作られたか」が要る。
    ~~🚨 **いま無い**（実測: `lib/auth/sessions.ts` の `issueSession` は経路を持たない）~~
    → **2026-08-15 `9660ba0` で入れた**（`auth_method`。nullable・既存 836 行は null のまま）。
    **記録だけ先に始めてある。切る処理はまだ書いていない**（この節の承認待ち）

#### 🚨 切る処理を書く人へ: `directus_sessions` だけを見ると、取りこぼす経路がある

**実測で分かった境界**（onboard が隔離環境で通して指摘・2026-08-15）:

    /api/auth/setup は **2 つの分岐**を持つ
      オンボーディング完了後 → issueSession(...,"setup")  → **directus_sessions に行ができる**（切れる）
      未完了時               → issueSetupSession()        → 🚨 **この表に行を作らない**（別 Cookie）

🚨 **したがって `auth_method` で数えた「setup が通った」は、片側だけ**。
**`directus_sessions` を全部切っても、未完了時の一時セッションは残る。**

**いまは実害が無い**（未完了の分岐は `onboarding_completed_at` が入った時点で通らなくなるので、
稼働中のインスタンスに一時セッションは存在しない）。
**ただし切る処理を「この表を空にする」で書くと、その前提に暗黙に乗ることになる。**
**乗るなら、乗っていると書くこと。**

## 5. 決めてほしいこと（実装前に）

### 5-1. 🚨 堀池さんへの設問（**書き直した**。前の版は対象が噛み合っていなかった）

前の設問は「Admin＝ロールかフラグ」を前提にしていた。**Admin は `Administrator` ポリシー**と
分かったので、**同じ言葉で聞き直す**:

> **管理画面の設定 → ポリシーに「Administrator」があります。**
> 「初回のユーザーは Admin として存在する。そのユーザーは**割り当て解除できない**」の
> **割り当て**とは、**その人に Administrator を付けている行**のことだと理解しました。
>
> 決めていただきたいのは **どちらを塞ぐか**です。
>
> **(A) 最後の1人だけ外せない** … 管理者が2人以上なら誰でも外せる。1人になったら、その人は外せない。
>   **初回の人でも、他に管理者を作れば外せます。**
>   → 初回の人が辞めても引き継げます。**辞めた人の行を消せます。**
>
> **(B) 初回の人だけは永久に外せない** … 他に管理者が何人居ても、初回の人からは外せない。
>   → **その人が辞めても、行は残り続けます**（いま**利用者を消す経路は無い**ので、消せません）。
>
> 私（auth）の見立ては **(A)** です。理由は §2 の3点。**ただし決めるのは堀池さんです。**
