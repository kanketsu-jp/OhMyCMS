## 1. 決めたこと（要約）

**証書を 2 層に分ける。**

    ① ライセンス証書（License）… 人が貼り付ける。長寿命。plan / 端末数の上限 / ライセンスID を持つ
    ② 端末許可証（Device Grant）… 端末ごとに発行。短寿命（既定 30 日）。日々の検証はこちらだけを見る

---

## 2. なぜ 2 層か（1 層では 3 つの要求が同時に成り立たない）

司令塔から来た要求は 3 つで、**互いに引っ張り合う**。

| 要求 | 必要なもの |
|---|---|
| 端末数の上限を守る | **全端末を一望する瞬間**が要る（1 台ずつ見ても総数は分からない） |
| 失効を効かせる | **止まったことを知る瞬間**が要る |
| オフラインで検証できる | 上の 2 つを、**起動のたびには要求できない** |

上 2 つはオンラインを要求し、3 つ目はそれを禁じる。同時に満たす唯一の形は
**「オンラインで受け取り、オフラインで使う」**——受け取る瞬間が①、使う瞬間が②。

    ┌ オンライン（アクティベーション。1 端末につき 30 日に 1 回）
    │   ライセンス証書 + 端末ID を出す → 署名/期限/失効を見る → 台帳で端末数を数える
    │   → 端末許可証（30 日）を署名して返す
    └ オフライン（毎回の起動）
        端末許可証の 署名 + exp + 端末ID の一致 だけ見る。ネットワーク不要

🚨 **この設計は「オフラインで動ける上限」と「失効が効き始めるまでの最大の遅れ」を同じ数にする。**
どちらも端末許可証の寿命（30 日）。**片方だけを短くすることはできない**——これはトレードオフであって、
実装の都合ではない。

## 3. 鍵と署名

### 実測（jose 6.2.8 / apps/studio）

    EdDSA    OK  token_len=235  公開鍵JWK= 79 文字  OKP Ed25519
    Ed25519  OK  token_len=238  公開鍵JWK= 79 文字  OKP Ed25519
    ES256    OK  token_len=235  公開鍵JWK=126 文字  EC  P-256

### 採るもの: **EdDSA（Ed25519）**

1. 🚨 **決定的署名**。ECDSA は署名ごとの乱数を **1 回でも使い回すと秘密鍵そのものが復元できる**
   （PS3・Bitcoin ウォレットで実際に起きた形）。発行鍵は**このプロダクトに 1 本しかなく**、
   漏れたら過去に売った全ライセンスが偽造される。**失敗の代償が非対称**なので、
   失敗しようのない方を採る。
2. 公開鍵が短い（79 文字）。**配布物に定数として埋める**ので効く。
3. Node 24 / Swift CryptoKit（`Curve25519.Signing`）/ Safari 17+ の WebCrypto すべてにある。

`alg` ヘッダは **`EdDSA`**（RFC 8037 の登録名）。jose は新しい別名 `Ed25519` も受けるが、
**古い検証器は知らない**ので登録名を使う。

## 4. ライセンス証書の形

    OMC1.<JWS Compact>          実測 235 + 5 = 約 240 文字

🚨 **接頭辞 `OMC1` は必須。** アルゴリズムや構造を変える日に、**既存キーと区別する唯一の手段**。
後から付けることはできない（付けた瞬間に旧キーが全部 malformed になる）。

| クレーム | 中身 | 🚨 なぜ最初から入れるか |
|---|---|---|
| `iss` | `"ohmycms"` 固定 | 他所で作られた JWT を持ち込ませない |
| `sub` | ライセンス ID | **失効の単位** |
| `jti` | このキーの発行 ID | **再発行しても、旧キーだけを止められる** |
| `iat` | 発行時刻 | |
| `exp` | このキーの寿命 | §4-1 |
| `plan` | `cloud` / `native` / `perpetual` | 3 つの売り方 |
| `dev` | 端末数の上限（整数） | **後から足すと、既存キーに無い＝どう読むかで実装が割れる** |
| `ent` | 機能の集合（文字列の配列） | 将来プランが増えても**キーの形を変えずに**表せる逃げ道 |

### 4-1. 🚨 買い切りにも `exp` を入れる

「買い切り＝永久に有効なキー」にすると、**漏れたキーを止める手段が失効リストだけ**になる。
そして失効リストは**届かない端末には効かない**（§6）。

→ `exp` を長め（5 年）に置き、期限が来たら再発行する。
**買い切りの権利は DB の台帳が持ち、キーはその引換券でしかない。**
利用者から見て「買い切り」であることは変わらない（再発行は無償・自動）。

## 5. 端末許可証と、端末数の上限

    OMC1D.<JWS Compact>
    sub = ライセンスID / dvc = 端末ID / plan・ent は証書から写す / exp = 30 日後

日々の検証は **署名 + `exp` + `dvc` の一致**だけ。DB もネットワークも見ない。

### 🚨 上限の競合

**「数えてから入れる」では守れない。** 上限 3 のときに 3 台目と 4 台目が同時に来ると、
どちらも「いま 2 台」を読んで両方通る。

→ `(license_id, device_id)` に一意制約を置き、**トランザクション内で該当ライセンス行を
`SELECT ... FOR UPDATE` してから数える**。SAML の `consumeAssertion` が
主キー衝突で決着させたのと同じ考え方（**判定と書き込みの間に隙間を作らない**）。

## 6. 失効

失効の単位は 3 つ。**どれも要る。**

    ライセンスごと (sub)   … 返金・契約終了
    キーごと      (jti)   … 再発行したので旧キーを止める
    端末ごと      (dvc)   … 端末を紛失した

### 方式: **短命の端末許可証 ＋ 署名付き失効リスト**（両方）

| 片方だけだと | 何が起きるか |
|---|---|
| 端末許可証だけ | **最大 30 日、止められない** |
| 失効リストだけ | **リストが届かない端末には何も効かない**。しかもオフラインなので**届いたかどうかも分からない** |

失効リスト自体も JWS（`OMC1R.…`）で署名し、`issuedAt` と `nextUpdate` を持たせる。

### 🚨 失効リストが取れなかったことを「失効していない証拠」にしない

`nextUpdate` を過ぎたリストは、**「失効していない」ではなく「判定できない」**として返す
（`LICENSE_REVOCATION_STALE`）。**通すか止めるかは呼び出し側が決める。**

これは `verify-the-verifier.md`「代理を測らない」と
「**0 件は単独では情報を持たない**（異常が無い 0 と、見ていない 0 は同じ見た目）」の、そのままの形。
**リストに載っていない**と**リストを見ていない**を、同じ戻り値にしてはいけない。

## 7. 鍵の置き場

| | 置き場 | 理由 |
|---|---|---|
| **発行鍵（秘密）** | 環境変数 `OHMYCMS_LICENSE_SIGNING_KEY`（PKCS#8 PEM） | 下記 |
| **検証鍵（公開）** | **コードに定数**。`OHMYCMS_LICENSE_PUBLIC_KEY` で上書き可（自前ビルド・試験用） | 配布物に載ってよい唯一のもの |

🚨 **2026-08-14 に「env 最小化・秘密も GUI(DB) へ」へ方針が反転している**
（`secrets-storage-by-recoverability.md` の追記）。**この鍵はその対象外**にする。

- 反転の根拠は「**オンボード後に利用者が設定する項目**を GUI にする」こと。
  発行鍵は**利用者が設定するものではない**（利用者は検証しかしない。発行するのは売る側）。
- DB に入れると **`pg_dump` に写る**。ダンプ 1 つで**過去に売った全ライセンスを偽造できる**。
  同じ決定が挙げていた「バックアップに写る」という漏洩経路が、ここでは**最大の被害**に直結する。

**発行は CLI（`scripts/license-issue.ts`）だけ。API からは発行しない。**

### 🚨 正直に書いておくこと

**OhMyCMS は OSS なので、検証を外したビルドは誰でも作れる。** これは DRM ではない。
**払う気のある人が正しく払えるための仕組み**であり、強度をそこに求めない。
（強度を求める設計にすると、必ずオフライン要求と衝突して壊れる。）

## 8. エラーコード — 🚨 別々の理由で落ちることを、外から見えるようにする

| コード | いつ |
|---|---|
| `LICENSE_MALFORMED` | 接頭辞が違う / JWS として読めない |
| `LICENSE_BAD_SIGNATURE` | 署名が合わない |
| `LICENSE_EXPIRED` | `exp` を過ぎた |
| `LICENSE_REVOKED` | 失効リストに載っている |
| `LICENSE_DEVICE_LIMIT` | 端末数の上限 |
| `LICENSE_DEVICE_MISMATCH` | 端末許可証の端末 ID が違う |
| `LICENSE_REVOCATION_STALE` | 失効リストが古く、判定できない |

`lib/` は**コードだけ**返す。**文言は API / UI 層で辞書**（新しい名前空間 `license`）へ。
ja / en の両方に足す（`AGENTS.md §3.8`）。

## 10. 受入 — 否定側を先に決める

    🟢 対照 0  正しいキーが通る                     ← これが無いと以下は何も証明しない
    🔴 ①      署名を 1 文字変える  → LICENSE_BAD_SIGNATURE
    🔴 ②      期限切れ            → LICENSE_EXPIRED
    🔴 ③      失効済み            → LICENSE_REVOKED
    🔴 ④      上限 +1 台目        → LICENSE_DEVICE_LIMIT
    🔴 ⑤      別端末の許可証      → LICENSE_DEVICE_MISMATCH
    🔴 ⑥      古い失効リスト      → LICENSE_REVOCATION_STALE
    🟢 対照 1  上限**ちょうど**の台数は通る          ← 全部 DEVICE_LIMIT で落とす実装でも ④ は緑になる
    🟢 対照 2  失効リストに載っていないキーは通る    ← 全部 REVOKED で落とす実装でも ③ は緑になる

🚨 **「落ちたこと」でなく「何が落としたか」を assert する。**
SAML のリプレイ検査は「2 回目が 401」で緑になったが、**実際に効いていたのは別の検査**だった
（`acceptance/saml/PITFALLS.md §4-1`）。ここでも同じ罠がある——
署名・期限・失効・端末数は**すべて「弾く」で終わる**ので、**コードまで見ないと区別できない**。

🚨 **計器の生存確認を 1 回だけ測る。** 検証関数を「常に通す」に差し替えると
**①〜⑥ がすべて赤くなる**こと。赤くならない項目があれば、その検査は何も見ていない。
