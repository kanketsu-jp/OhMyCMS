> ログイン画面には『リカバリーコードでログイン』がある。**」
> 関連: `sso-only-switchover.md`（締め出しの設計） / `sso-user-provisioning.md`（誰を入れるか） /
> `knowledge/decisions/secrets-storage-by-recoverability.md`（秘密の置き場所） /

## 0. 何を解いているか

251 で **B（最初に作った人の Administrator は外せない）** を選んだ。
司令塔が B の欠点として挙げたのは「**その人が退職しても外せない**」。

🚨 **堀池さんの答えは、その欠点を消すのではなく、守る不変条件を差し替えている。**

    ❌ 守る不変条件が「最初の人が永久に管理者である」  … 退職すると破綻する
    ✅ 守る不変条件は「**必ず誰かが入れる**」        … 誰が管理者かは可変でよい

**リカバリーコードは「SSO の例外」ではない。「SSO のみ」を安全に入にするための前提である。**
これが無いと `sso_only` は**戻れない一方通行の扉**になる（`sso-only-switchover.md` §3.5）。

## 1. 生成（司令塔の問い①）

### 🚨 まず「key-gen」の読みを確定させる（**割れます**）

このリポジトリで `key-gen` に当たるものは **`scripts/license-keygen.ts`（EdDSA の鍵ペア生成）**
だけ（実測: `grep -rn "key-gen"` で他に無し）。だが**それではない**と読む。

    読み(a) ✅ **「人が決めるのではなく機械が生成する」の意味**（鍵生成器一般）
    読み(b) ❌ ライセンスの EdDSA 署名機構を流用する

**(b) を採らない理由は2つ**:

1. 🚨 **署名トークンは失効できない**。ステートレスに検証できるということは、
   **DB を触っても無効にできない**ということ。**漏れたら永久の裏口**になる。
2. 🚨 **人が非常時に手で打つ**。EdDSA の署名付きトークンは数百文字で、
   **紙や 1Password から、締め出された状態で打つ**ことができない。

**堀池さんの意図と違っていたら、ここで止めてください。** 以降は (a) を前提に書く。

🚨 **2026-08-15 決定（司令塔から「あなたが決めてください」と委ねられた）: (a) を採る。**
**理由**: **失効できることが要るから**。リカバリーコードは**漏れたら管理者権限がそのまま渡る**もので、
**取り消せない鍵を1本作ることは、この設計が守ろうとしている「必ず誰かが入れる」より重い危険**を作る。
署名トークンは検証にサーバの状態を要さない＝**DB を触っても無効にできない**。
**違っていれば堀池さんが直せるよう、この行に理由を残す。**

### 形

    生成元  crypto の乱数（`lib/auth/sessions.ts` の `randomToken` と同じ系統）
    長さ    **25 文字**（5 文字 × 5 群をハイフンで区切る）例: `K7M2Q-9XR4T-...`
    文字集合 🚨 **紛らわしい字を外す**（`0/O` `1/I/l` `8/B`）。**打ち間違いで入れないのが最悪**

**なぜ「人が読める形」にこだわるか**: これを使う人は**画面から締め出されている**。
コピー＆ペーストできない状況（別端末・紙・スマホの 1Password）を前提にする。

## 2. 保管（司令塔の問い②・**ここが最重要**）

### 決め: **一方向ハッシュで DB に持つ。平文も可逆暗号も使わない。**

### 🚨 どのハッシュかは「家の流儀」ではなく **エントロピー** で決める

この家には**2つの前例があり、使い分けに理由がある**（saml の指摘で確認・実測）:

    lib/auth/crypto.ts    randomToken → **sha256Hex** … セッション/エージェントのトークン
                                                        ＝ **機械が作る高エントロピーの値**
    lib/auth/password.ts  **scrypt**                 … 利用者のパスワード / OTP の6桁
                                                        ＝ **低エントロピーで総当たりされる値**

**リカバリーコードは機械生成の 25 文字（約 116 ビット）＝ 高エントロピー側。**
→ **`sha256Hex` が正しい**（セッションと同じ形）。

🚨 **ただし「家がそうしているから」で選ばない。** 選ぶ根拠は**総当たりが現実的か**。
**もし後で「打ちやすいように 8 文字へ短くしよう」となったら、その瞬間に scrypt 側へ移す**
（`ohmycms_login_codes` が 6 桁に scrypt を使っているのと同じ理由）。
**長さを変える人は、ハッシュも見直すこと。**

このリポジトリは既に**判断軸を一般化して持っている**
（`secrets-storage-by-recoverability.md` の 2026-08-15 追記）:

> **秘密を DB へ移してよいかは「誰が設定するか」と「漏れたとき被害がどこまで及ぶか」で決める。**
> 設定するのが利用者本人で、被害がそのインスタンスに閉じるなら DB（GUI）でよい。

リカバリーコードは **①設定するのは利用者本人（そのインスタンスの管理者）**、
**②漏れても被害はそのインスタンスに閉じる** → **DB でよい**。

さらに **照合するだけで平文が要らない**ので、**AES の secret-box（可逆）を使ってはいけない**:

    ❌ 可逆暗号  … DB を読めた人が**コードそのものを取り出して入れる**
    ✅ 一方向ハッシュ … DB を読めても**入れない**（`hashPassword` が既にある）

🚨 **代償を正直に書く: ハッシュにすると「表示は生成した1回だけ」になる。**
**なくしたら復元できない。** これは欠陥ではなく、可逆にしないことの必然。
**緩和は「管理者でログイン中なら、いつでも作り直せる」こと**（§4）。

## 3. ログイン画面（司令塔の問い③）

### 決め: **常に出す。条件で出し分けない。**

🚨 **いまの OTP は条件付きで出ている**（`app/login/page.tsx:48` — `otpEnabled` が真のときだけ）。
**リカバリーコードで同じことをしてはいけない。**

> **非常口は、壊れている当のものに依存して出し分けてはならない。**

「SSO が失敗したときだけ出す」形にすると、**SSO の失敗を検知する側が壊れた瞬間に扉が消える**。
**いちばん要るときに無い**——`sso-only-switchover.md` が扱っている壊れ方と同じ構造。

### 置き方

    ・**主ボタンにしない**（毎日使うものではない。目立たせると常用され、使い切りの意味が薄れる）
    ・**常設の控えめなリンク**「リカバリーコードでログイン」
    ・🚨 **文言はできること以上を約束しない**。これは「管理者が戻る道」であって、
      一般の利用者のログイン手段ではない

## 4. 使ったあと（司令塔の問い④）

    ① **使い切り**（consume）。🚨 再利用可にすると、漏れたときに**恒久的な裏口**になる
    ② **使った直後に、新しいコードを1回だけ表示する**
       🚨 使い切りだけだと「1回使ったら次の非常口が無い」状態で放置される
    ③ **使ったことを記録する**（`directus_sessions.auth_method = "recovery"`。
       🚨 **今日足した列がそのまま使える**。誰が・いつ・どこから入ったかが残る）
    ④ **管理者でログイン中なら、いつでも作り直せる**（§2 の「なくしたら復元できない」の緩和）

### 🚨 総当たり対策

**これは最後の扉なので、失敗回数の制限が要る。**
セットアップパスワードは `10 回 / 15 分`（`lib/auth/setup.ts:7-8`）だが、
🚨 **あれはモジュール変数（プロセス内）なので、プロセスが複数あると弱くなる。**
**リカバリーコードの制限は DB に持つ**（OTP の `ohmycms_login_codes.attempts` と同じ形）。

## 5. `sso_only` との関係（司令塔の問い⑤）

### 判定: **残す。そして「SSO のみ」と呼ばない。**

司令塔の見立てに同意する。理由を1段強く書くと:

> **リカバリーコードは SSO の抜け道ではない。SSO のみへ切り替えることを可能にしている当のものである。**

    残さない → IdP が落ちた日に**誰も入れない**。`sso_only` は**戻れない扉**になる
    残す     → 「SSO のみ」は**厳密には嘘**になる。**だから正直な名前を付ける**

**呼び方**: 「**SSO のみ（緊急の入口を1つ残す）**」。画面にもそう書く。
🚨 **「SSO のみ」とだけ書くと、監査する人が「抜け道は無い」と読む。**

### 🚨 設定の**名前**も変える（saml の指摘）

**`sso_only` という識別子が、実装より強いことを言っている。**
これは「エラー文言が実際より強いことを言っていないか」の**設定名版**。
**画面の文言だけ正直にしても、コードと API に `sso_only` が残れば、次に読む人は名前を信じる。**

    ❌ sso_only        … 「他の経路は無い」と読める
    ✅ sso_preferred / require_sso など、**緊急口が1つあることが名前から否定されない形**

**この改名は `sso-only-switchover.md` 側にも波及する**（設計名・設定キー・画面）。
**実装前に決めること**——**入ってから直すと、移行の migration が1本増える。**

### 🚨 無効化できないようにする

**設定で切れるようにしてはいけない。** 「SSO のみなのだから緊急口も閉じるのが筋だ」と考えた人が
善意で切り、**この設計が防ごうとしている締め出しがそのまま起きる**。
（`sso-only-switchover.md` の「切り替えた直後は普通に使えて、翌朝に誰も入れない」と同じ形）

## 6. 谷との関係（司令塔の問い⑥）

**「切り替えを実行する管理者と、切り替え後に入る管理者は別人になる」問題への橋になるか。**

### 判定: **橋になる。ただし前提の検査を置き換えない。**

### 🚨 その前に: **「入れる」と「設定を戻せる」は別**（saml の指摘）

**入れただけでは `sso_only` を戻せない。** 設定変更は
`requireAdmin(actor, "settings:write")` を通る（`app/api/settings/saml/route.ts`）。

**実測した判定の中身**（`lib/permissions/resolve.ts:247`）:

    人間の actor は  actorHasAdminAccess(actor) だけを見る
                    ＝ **`admin_access` が真のポリシーを1つでも持っているか**
    能力（capability）の粒度が効くのは **エージェントだけ**（248 行目）
    🟢 対照(+) 実データのポリシーは `Administrator`(admin_access=true) と `dev-admin`(同) の2つ

→ **`admin_access` を持つ人として入れば、`settings:write` も通る。** ここは分岐しない。

🚨 **したがって橋の成立条件は1つに絞れる:
「リカバリーコードで入った人が、`admin_access` を持つポリシーを保持していること」。**

**そしてそれを保証するのが 251-B（最初の人の Administrator は外せない）である。**
🚨 **251-B はまだ決定であって実装ではない。** つまり**今日の時点では、
リカバリーコードだけ作っても橋にならない**——**251-B の実装とセットで初めて成立する。**

### 🚨 251-B は、いまのデータでは実装できない（2026-08-15 実測）

**「最初に作った人」を特定する手段が無い。**

    directus_users の列（実測・全部）:
      id, first_name, last_name, email, password, status, role, token,
      last_access, provider, external_identifier, auth_data,
      failed_login_attempts, locked_until, avatar_emoji
    🚨 **作成時刻の列が 0 件**（`created_at` / `date_created` のいずれも無い）
    🟢 対照(+) 同じ数え方で `email` / `status` → 2 件（＝この数え方は列を見つけられる）
    `id` は `randomUUID()` なので**順序を持たない**。`last_access` は最終ログインで、作成ではない

**したがって**:

  ・🚨 **既に動いている環境では、誰が最初かを後から決めることはできない。**
    **コードで推測させてはいけない**（間違えると、**守るべきでない人を守り、守るべき人を守らない**）
    → **人が指名する**しかない（**堀池さんか、そのインスタンスの持ち主**）
  ・**これから作る環境では、記録できる。** 🚨 **記録は早いほど正しい。**
    **今日 `auth_method` でやったのと同じ形**——**判断（何を切るか）より先に、記録を始める。**

🚨 **この部分は ②③（表示回数・事前確認）の回答を待たない。**
**どちらの答えが来ても書き直しにならない**（記録するかどうかは、使い方と独立している）。
**司令塔の「②③のどちらが来ても書き直しにならない部分があるなら先に出せ」への答えが、これ。**

**なる理由**: 251-B により**最初の人は必ず Administrator を持つ**。
リカバリーコードはその人として入るので、**入れば管理権限まで戻る**。締め出しは解ける。

**置き換えない理由**: 🚨 **一度も使われていない非常口は、未検証である。**

    「戻れるはずだ」で切り替える → 戻る道が実は壊れていた、を**いちばん困るときに知る**

**だから前提を1つ足す**（受入に落とす）:

> 🚨 **`sso_only` を入にする前に、リカバリーコードが「生成済み」かつ「実際に1回使えた」こと。**
> **生成しただけでは足りない。使えることを見る。**

これは今日の測り方そのもの——**「配線してある」と「実際に通った」は別**。
そして**確認は無料**でできる: `auth_method='recovery'` の行が1本でもあれば、使えた証拠になる。

### 7.5.1 環境変数の役割 —— **認証ではなく「扉を存在させる許可」**

🚨 **正直に書く。環境変数は、この CLI に対する認証にはならない。**
**コンテナに入れる人は、環境変数も DB も両方読める。** だから「環境変数を知っている人だけ」は成り立たない。

**では何のために要るのか**:

    未設定 → **CLI は動かない**（＝ **緊急口がそもそも存在しない**）
    設定済 → CLI が動く（＝ **持ち主が「この扉を置く」と決めた**）

**＝ 認証ではなく、持ち主の意思表示。** **既定では扉が無い**、が要点。

🚨 **既定値で動かしてはいけない理由は、実事故がある**（`compose.prod.yml:8-11` の記録・実測で確認）:

    OHMYCMS_SETUP_PASSWORD の既定 `pass132` は
      README / compose.yml / AGENTS.md / .env.example / lib/auth/setup.ts:5 に**平文で書いてある公開値**
    そのイメージを公開 URL へ焼き込んだ結果 → **外から `pass132` だけで管理者になれた**

**同じ形を作らない。** **未設定なら動かない。既定値を持たせない。**

### 7.5.2 🚨 CLI は DB を直接触る —— **既存の決定の例外になる**

`knowledge/decisions/cli-mcp-over-rest.md`:
> **CLI と MCP は REST API 経由（DB 直接アクセス禁止）**
> 理由: **権限の強制点を API 層 1 箇所に保つ**

**このリカバリー CLI は、その例外にする。** 理由は決定の**趣旨そのもの**から出る:

    REST 経由にする  → **認可を通らない口を、ネットワークに生やす**ことになる
                       🚨 **いちばん外へ出したくないものを、いちばん外へ出す**
    DB 直接にする    → **コンテナに入れる人しか触れない**。ネットワークからは到達しない

🚨 **この CLI は「権限の層が全員を締め出したとき」に動くもので、
定義からしてその層の外側にある。** REST に載せると、層の内側に穴を開けることになる。

**したがって**: 実装するときは **`cli-mcp-over-rest.md` に例外として追記する**
（このリポジトリが `secrets-storage-by-recoverability.md` でライセンス鍵を例外にしたのと同じ形）。
**黙って逸脱しない。**

### 7.5.3 CLI の形

    置き場所  apps/studio/scripts/（`bun run` で叩く。既存の scripts と同じ）
    要求      🚨 **環境変数が設定されていること**。未設定なら**何もせず非 0 で終わる**
    するもの  新しいコードを生成 → **ハッシュだけ DB へ**（既存のものは失効させる）
    出力      **新しいコードを1回だけ標準出力へ**。🚨 **「二度と表示されない」と明記する**
    🚨 しない **既存のコードを表示しない**（ハッシュしか無いので、そもそもできない）

### 7.5.4 🚨 記録 —— **司令塔の読みを1点訂正します**

> **再発行したことが記録に残る（`auth_method='recovery'` の列が既に在ります）**

🚨 **`auth_method` は「セッションがどの経路で作られたか」の列です。**
**再発行はセッションを作らないので、この列には出ません。**

    **使った**とき   → セッションができる → `auth_method='recovery'` に出る（**既にある**）
    **再発行した**とき → セッションは**できない** → 🚨 **別の記録が要る**

**リカバリーコードの行に「いつ・何回目か」を持たせる**（発行時刻・失効時刻）。
**実装のときに列を決める。** **「既にある」で済ませない。**

  ・**複数のリカバリーコードを一括発行**（GitHub 等の「10 個まとめて」）——
    **管理者は1人（251-B）**なので、まず1本で足りる。要るなら後から足せる
  ・**コードでの API アクセス**（画面のログインだけ。**機械の入口にしない**）
  ・**リカバリーコードでの権限昇格**（既に持っている権限で入るだけ。新しく付けない）
