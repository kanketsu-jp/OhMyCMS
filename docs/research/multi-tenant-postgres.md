## 0. いま確定していること（動かせない前提）

1. **`no-organization-table.md`（active・2026-08-04 堀池）**: 「組織」を第一級エンティティにしない。
   企業は普通のコレクション `companies` の行。分離は **Policy + 行レベルフィルタ**（`$CURRENT_USER.<企業参照>`）。Directus に倣う。
   → 🚨 **本調査はこの決定を覆さない。** テナント = `companies` の行 + 参照カラムであって、新テーブルではない。
2. **open question（同ファイルの「影響」節）**: 認可の**強制点**を app 層／DB 層(RLS)のどちらに置くか未決。
   **「MCP を外部エージェントへ開放する段階で再検討する」**と明記されている。→ 本調査はこれに答える。
3. **`tenant_name` は表示専用**（`ohmycms_settings`・組織名の表示）。テナント機能の器ではない
   （migration コメント: 「機能を設計する前に器を決めない」）。
4. 🚨 **束縛条件＝ランタイム DDL。** 利用者が GUI でコレクションを作ると実行時に `CREATE TABLE` が走る。
   実測: `apps/studio/lib/schema/service.ts` の作成経路に **tenant カラムを注入するフックは無い**
   （`grep -c tenant` = 0）。**どの戦略もこの「実行時に生えるテーブル」を扱えないと成立しない。**

## 1. 選択肢 × ランタイム DDL

| | 強制点 | ランタイム DDL との相性 | 破れ方（security 観点） |
|---|---|---|---|
| **A. 共有DB + app層 行フィルタ**（現状・Directus流） | アプリのクエリビルダ | ◎ 列を1本足すだけ。`resolve.ts` を通せば効く | 🔴 **WHERE を1箇所書き忘れると全テナントへ漏れる**（既出の「2箇所に書くと片方が腐る」形）。🚨 **クエリビルダを通らない経路（生 SQL・MCP・将来の外部エージェント）は素通り** |
| **B. 共有DB + RLS**（tenant_id 列 + テーブル毎の RLS ポリシー） | Postgres | △ **CREATE TABLE の度に** tenant_id 列 + `ENABLE/FORCE ROW LEVEL SECURITY` + ポリシーを**自動付与する必要**。単一チョークポイントが要る | 🟢 app が WHERE を忘れても DB が止める。生 SQL/MCP も**同じ接続 GUC に縛られる**。🚨 ただし**接続プール再利用で GUC がリークする**足元（§2） |
| **C. スキーマ per テナント** | search_path + 権限 | 🔴 **新コレクション = 全テナントスキーマへ CREATE TABLE**。migration が N 倍。`migrations-are-shared` 決定と衝突。多テナントでスケールしない | 🟢 分離は最強・per-tenant バックアップ可。ただし運用コストが破壊的 |
| **D. パーティション（tenant_id で）** | — | △ コレクション毎に partitioned table を実行時に作るのは複雑 | ⚪ **これは分離の境界ではない**（性能・保守の道具）。単体では security を satisfy しない。RLS か app 層と併用が前提 |

## 2. 🚨 RLS を採るなら必ず潰す穴（接続プールの GUC リーク）

RLS は「現在のテナント」を **`SET LOCAL app.tenant_id = ...`**（トランザクション内 GUC）でポリシーに渡すのが定石。
本アプリは knex + pg プール（`pool: { min:0, max:10 }`・`lib/db/knex.ts`）で**接続を使い回す**。

- 🔴 **`SET`（`LOCAL` でない）だと接続に residue が残り、次のリクエスト（別テナント）がそれを引き継ぐ。**
- 正: **リクエスト/トランザクション毎に `SET LOCAL`**、かつ**トランザクションで包む**（`LOCAL` は tx スコープ）。
- 🚨 **`BYPASSRLS` を持つロール（多くは所有者 `postgres`）で接続すると RLS は丸ごと無効。** ランタイム DDL は
  所有者権限を要する（`ALTER TABLE`）ので、**DDL 用接続とデータ用接続をロールで分ける**設計が要る
  （dokploy-ops §6 の「アプリに所有者を渡さない」と同じ判断軸）。

## 3. security としての推奨

**open question のトリガー条件そのものが答えを決める。** 決定は「**MCP を外部エージェントへ開放する段階**で再検討」と書いた。
🚨 **SQL に到達できる外部エージェント（MCP）が DB を触れる瞬間、app 層のみの強制（A）は不十分**——
エージェントはアプリのクエリビルダを通らないので、行フィルタを**構造的にすり抜ける**。

→ **推奨: B を「床」に、A を「その上」に。多層防御。**
- **DB(RLS)を最終防衛線**にする（app が漏らしても DB が止める）。`companies` 参照カラムの値を per-request GUC でポリシーへ。
- **app 層フィルタ（現状 A）は残す**（UX・性能・分かりやすいエラー）。ただし**それを唯一の壁にしない**。
- **C（スキーマ per テナント）は却下**：ランタイム DDL × 共有 migration と両立しない。
- **D（パーティション）は性能アドオンとしてのみ**。分離の根拠にしない。

これは既存の他決定と整合する: `secrets-storage-by-recoverability` の「漏れたとき被害がどこまで及ぶか」で置き場所を決める発想の、認可版。

## 4. 🚨 決める前に実測すること（verify-the-verifier）

推測で B を選ばない。次を**実測**してから決定を起こす:

1. **チョークポイントの実在**: `lib/schema/service.ts` の CREATE TABLE 経路が**1箇所**か。
   1箇所なら、そこに「tenant_id 列 + FORCE RLS + ポリシー」を自動付与できる。分散していたら B のコストが跳ねる。
   （測り方: 作成経路の関数を数え、runtime `CREATE TABLE` を出す箇所を列挙。「0/1/多」を明示）
2. **プール GUC リークの再現**: probe テーブルを実行時に作り、`SET LOCAL` 版と `SET` 版で
   「テナントA で設定 → 同一プール接続の次リクエストがテナントB」を叩き、**A の行が B に見えないこと**を対照付きで確認。
   🔴 見えたら実装が誤り。🟢 見えなければ床が効いている。
3. **BYPASSRLS の確認**: アプリのデータ用接続ロールが `rolbypassrls=false`・非所有者であること（`pg_roles` 実測）。
   DDL 用接続と分かれているか。
4. **app 層すり抜けの棚卸し**: `resolve.ts` を通らずに items を読む経路が無いか（検索・エクスポート・リレーション辿り・MCP）。
   ——これは私が v1 の攻撃演習で「リレーション経由」「横断検索」として既に一部潰した観点の延長。
5. **「0 件」の区別**: RLS テストで 0 行が返ったとき「正しく遮断した 0」か「そもそもデータが無い/クエリが空振りした 0」かを、
   admin 対照（admin では行が見える）とセットで判定する。
