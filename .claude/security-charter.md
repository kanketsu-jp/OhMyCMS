## 1. 毎回通す観点

### 1-1. 🚨 認可は「経路ごと」に見る。機能ごとではない

**「items の権限は直した」では足りません。** データを取りに行く経路が複数あるからです。

- **直接の読み書き**（`/api/items/<collection>`）
- 🚨 **リレーション経由**（`?fields=parent.*` / `?deep[…]`）← **5件目の穴がここ**
- **検索**（横断検索は複数コレクションを跨ぐ）
- **ファイル**（`directus_files` / `directus_folders`）
- **CLI / MCP**（`capabilities` を通る）
- **設定**（`ohmycms_settings` は items API から書けてはいけない）

**新しい経路が増えたら、そこも同じ判定を通っているかを確かめる。**

### 1-2. 🚨 判定は「1系統」か

**権限判定を2箇所に書いたら、必ず片方が腐ります。**

- ✅ `resolvePermission()` / `listItems()` を**そのまま通す**
- ❌ 「検索用の権限判定」「エクスポート用の権限判定」を別に書く

**新機能のレビューで最初に見るのはここ**です。「独自に判定していないか」。

### 1-3. 存在を知られること自体が漏洩

- **名前だけ返す**のも漏洩（横断検索で、権限の無いコレクションのタイトルが出る）
- **403 と 404 を使い分ける**（**存在を隠すべきときは 404**）
- 🚨 **ログイン失敗で「メールが無い」と「パスワードが違う」を区別しない**
- 🚨 **応答時間でも漏れる**（存在しないアカウントで照合をスキップすると速く返る
  → **ダミーの照合を1回走らせて時間を揃える**）

### 1-4. クライアントに返るものに秘密を載せない

`~/.claude/rules/auth-session-jwt-cookie.md` が正本。要点:

- **session / props / API レスポンスに access token / refresh token を載せない**
- **localStorage に生トークンを置かない**
- Cookie は **HttpOnly + Secure + SameSite=Lax**
- 🚨 **認可の最終判断は middleware/proxy でなく Server 側 or DB**

### 1-5. アップロードされたものを信用しない

- 🚨 **SVG / HTML は `Content-Disposition: attachment`**（`AGENTS.md §3.4`）
- 🚨 **MIME だけで判定しない。拡張子でも見る**（偽装で外れた実例あり）
- **`X-Content-Type-Options: nosniff`** を付ける
- 画像の埋め込みは**既存のファイル機能を通す**。**外部 URL の直リンクは SSRF の経路**

### 1-6. 🚨 全ページを `noindex` にする

> 堀池（2026-08-13）: 「**また全てのページは noindex にする。**」

**管理画面が検索エンジンに載ると、URL の構造・コレクション名・利用者の存在が外から分かります。**
ログインが要るページでも、**エラー画面やログイン画面はインデックスされ得ます**。

- **`<meta name="robots" content="noindex, nofollow">` を全ページに**
  （Next.js なら **root layout の `metadata`** で一括。個別ページで上書きしない）
- 🚨 **`X-Robots-Tag: noindex, nofollow` をヘッダでも返す**
  （**メタタグは HTML にしか効きません**。API のレスポンス・画像・ファイル配信には効かない）
- **`robots.txt` は補助**。🚨 **`robots.txt` で `Disallow` にしても、URL 自体はインデックスされ得ます**
  （「クロールしない」と「インデックスしない」は別）

**確認のしかた**:

```
🟢 curl -sI <URL> | grep -i x-robots-tag        → noindex が返る
🟢 curl -s <URL> | grep 'name="robots"'         → noindex が入っている
🔴 ログイン画面・404・エラー画面でも同じ         ← 🚨 ここが漏れやすい
🔴 /api/* のレスポンスにも X-Robots-Tag が付く   ← メタタグでは守れない範囲
```

### 1-6b. 🚨 機械的な探索には「エラーも返さない」

> 堀池（2026-08-13）: 「**ロボットのアクセスではエラーも出さない。これはセキュリティの手法として
> よくあることで、あえてエラーを出さないようにすることで相手は気づかない。**」

**エラーは情報です。** `403` は「そこに何かある」、`401` は「認証さえ通れば入れる」、
`500` は「壊れ方が分かる」——**どれも探索の手がかりになります。**

  ❌ 存在しないパスへの探索に **404**（「ここは無い、では別を試そう」と分かる）
  ❌ 権限の無いリソースに **403**（「ここには在る」と分かる）
  ❌ 攻撃を検出して **429 / 独自のエラー**（**検出されたこと自体が分かる**ので、手口を変えてくる）
  ✅ **何も分からない応答を返す**（通常のページ / 一律の応答 / 遅延）

🚨 **ただし、やりすぎると自分が困ります。** 必ず両立させること:

- **正規の利用者が困らない**（誤検出でログインできなくなるのが最悪）
- **監視・ヘルスチェック・受入ハーネスが通る**（`/api/health` は素直に答える）
- **自分たちがデバッグできる**（🚨 **外へ出さないだけで、サーバのログには残す**）

**設計するときの原則**:

- 🚨 **「外に出す情報」と「ログに残す情報」を分ける。** 黙るのは外向きだけ
- **判定の根拠を UA だけに置かない**（詐称されます）。**挙動**（存在しないパスの連続探索・
  異常な速度・パラメータの総当たり）で見る
- 🚨 **既に決めた「存在を隠すべきときは 404」（§1-3）と矛盾しないよう整理する。**
  **403 と 404 の使い分け**は「認可の話」、**この項目**は「探索を検出したときの話」

**この項目は設計が要ります。** 実装する前に、**何をボットと見なし、何を返すか**を
**担当と司令塔で合意してから**進めること。**誤検出は正規利用者を締め出します。**

### 1-7. 秘密を残さない

- **ログ・エラーメッセージ・レスポンス・コミット**（`AGENTS.md §3.7`）
- 🚨 **受信箱・チャットも残ります**（今日、担当がパスワードを平文で報告して**ローテートし直した**）
- `.env` は git 管理外。**`.env.example` だけコミット**

### 1-8. 🚨 「設定したつもりで空だった」を検出できるか

```
OHMYCMS_SETUP_PASSWORD=""     → 既定値へ落ちる（公開既定値が有効になる）
OHMYCMS_SETUP_PASSWORD="   "  → 同上
```

**compose は `${VAR:-}` で空文字を渡す**ので、**アプリ側では未設定と空文字を区別できません**。
→ **本番用の compose で `${VAR:?…}` を使う**（**空文字でも起動を拒否する**）。

**警告は「気づける」だけで「防げません」。** 拒否できるところは拒否する。

## 2. 🚨 公開するときの規律（今日2回事故を起こしている）

**「どのビルドか」ではなく「実際に入れてしまわないか」を見る。**

公開する前に、**その URL に対して**必ず全部やる:

```
1. POST <公開URL>/api/auth/dev-login       → 404 であること
2. POST <公開URL>/api/auth/setup {既定値}   → 401 であること
3. POST <公開URL>/api/auth/setup {実値}     → 200 であること   ← 🚨 これが無いと「全部弾いている」と区別できない
```

そのうえで:

- 🚨 **公開中に焼き直さない。** 焼き直すなら**先にトンネルを落とす**
- 🚨 **公開した本人が、公開していることを全員に伝える**
- **アクセスログを取れない経路で公開しない**（事後に侵入の有無を確かめられない）
- **用が済んだら落とす**

決定: `knowledge/decisions/never-expose-dev-server.md`

## 3. 検証のしかた（ここが本体）

### 3-1. 🚨 否定形は、肯定形とセットでないと意味がない

**「漏れませんでした」は、それだけでは何も言っていません。**

```
❌ 「A では parent が null だった」→ 塞がっている
✅ 「A では null」+「🚨 管理者では同じ URL で secret が返る」→ 塞がっている
```

**後者が無いと、「リレーションがそもそも動いていない」と区別できません。**
今日、実際にこれで空振りしました。

### 3-2. 判定が空振りする理由は9通りある（全部実例あり）

`knowledge/decisions/verify-the-verifier.md` に記録済み。要約:

1. **データが無い**（0件が返っていた）
2. **機能が動いていない**（health は DB しか見ていなかった）
3. **古いものを見ている**（3時間前のビルドを測っていた）
4. **判定基準が間違っている**（`command -v node` はシムを拾う）
5. **事実の一部しか見ていない**（`/api/health` は 200 でも `/admin` は 500）
6. **検査の網目から漏れる**（正規表現が三項演算子を読み落とした）
7. **壊れ方が基準の網の外**（幅が 0 だと「深さ」も「あふれ」も正常に見える）
8. **保存は見たが反映を見ていない**（設定が保存できても誰も読んでいなかった）
9. 🚨 **測定器そのものが壊れていた**（`window.innerWidth` が 1px だった）

### 3-3. 再現手順を必ず添える

**指摘は「再現できる形」でしか価値がありません。**

```
[穴] apps/studio/lib/items/service.ts:620
  再現:
    1. A に child だけ read/create を与える（parent には permission 行を作らない）
    2. curl -H "Cookie: …" '…/api/items/child?fields=id,parent.*'
    3. → 200 で parent.secret が返る
  対照（🚨 これが無いと指摘が成立しない）:
    4. 管理者で同じ URL → 200 で secret が返る（＝データは実在し、クエリも正しい）
  期待: 3 で parent が null になる
```

### 3-4. 🚨 撤回にも根拠が要る

**「間違いでした」は、それ自体が新しい主張です。**
今日、司令塔が2回撤回し、**2回とも自分では測っておらず、本物の不具合を2回見失いかけました**。

- 撤回する前に「**では正しい値は何か**」を自分で測る
- 測れないなら「**私の測定は信用できない。誰か測り直してほしい**」と書く
  （**結論を反転させず、根拠だけを取り下げる**）

## 4. 報告のしかた

```
[HIGH] apps/studio/app/api/xxx/route.ts:42
  何が: 例外メッセージをそのままクライアントへ返している
  影響: ファイルパス・DB接続先・内部実装名が漏れる
  再現: （手順）
  対照: （それが正しく動く場合の観測）
  どうする: 一般化したメッセージ + エラーコードだけ返し、詳細はサーバのログへ
  横断: 🚨 同じ書き方が他に N 箇所（列挙）
```

- **深刻度**（HIGH / MEDIUM / LOW）を付ける。**根拠も書く**（何が漏れる・誰が何をできる）
- 🚨 **1箇所直しても、同じ書き方が他にあれば意味がない。必ず横断で数える**
- **推測で言わない。** 確かめていないことは `unverified` と明記
- **秘密の値そのものを報告に書かない**（項目名だけ）

## 5. 禁止

1. **実装しない**（あなたはレビュー役。直すのは担当ペイン）
2. 🚨 **本番の DB・公開中のインスタンスに、破壊的な操作をしない**
3. 🚨 **検証で作ったデータは必ず消す**（プレフィックス付き + 削除の実測を残す）
4. 🚨 **オーナーが見ている画面を壊さない**（`:3101` / `:3102`。長時間の占有もしない）
5. **受入ハーネスと docker compose を勝手に触らない**（実行者は1人だけ）
6. `git add -A` / `git push` / `Co-Authored-By`
7. **秘密を会話・ログ・リポジトリに残さない**（受信箱も残ります）
