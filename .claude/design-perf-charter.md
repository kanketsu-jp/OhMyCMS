## 1. 🚨 面（Surface）の入れ子 — 最優先。ここが今までで最大の事故

> 堀池の指摘（2026-08-13・原文）:
> 「ページ自体に Padding があり、その中で、フォルダ管理としてボーダー（カードタイプ）があり、
> それにも Padding があります。**最もひどいのは、作成セクションで、ここではボーダーのカードコンポーネントの中に、
> ボーダーの Input タグがあります。ボーダーの中にボーダーがあり、そのなかにボーダーがあります。**
> 背景色も全て同じ。しかも**すべて Padding を持ちます**。これを徹底的にやめてください。
> これは**デザイナーとして知識が浅く、コンポーネント単位でしか考えていない典型的な悪い例**です。」

### 規則

**面は1段まで。** 面とは「ボーダー」「背景色の変化」「影」「角丸」のいずれかを持つ箱のこと。

- ページ本体（`bg-background`）は面ではない。ここから**1段だけ**面を作ってよい
- **面の中に面を置かない**。中を区切りたいなら **Divider（`Separator` / `marker`）だけ**
- SP は横幅が狭い。**カードをやめて上下の Divider にする**のが既定
- 入力の中にボーダーを置きたくなったら、**入力側のボーダーを消して `bg-muted` にする**か、
  **親の背景を変える**（堀池の指定どおり）

### 見つけ方（**2本とも**毎回実行する。役割が違うので片方では足りない）

```bash
cd apps/studio

# ① 静的（速い・全ファイル）— ソースのクラス名から探す
node scripts/check-surface-nesting.mjs

# ② 描画実測（遅いが真実）— 実際に描かれた computed style から測る
node scripts/audit-surface-depth.mjs --base http://localhost:3101 --paths /login
node scripts/audit-surface-depth.mjs --base http://localhost:3103 --session <cookie値>
```

**どちらも違反があれば exit 1** します。

#### なぜ2本要るか（片方ずつの弱点。どちらも実測で確認済み）

| | ①静的 | ②描画実測 |
|---|---|---|
| 速さ | 速い（全ファイル） | 遅い（ページ数×画面幅） |
| ログイン | 不要 | 要る（`--session`） |
| **組み合わせで生まれる深さ** | ❌ **原理的に見えない**（layout + page + components の合成結果なので） | ✅ 見える |
| **`className={cn(...)}`** | ❌ **見えない**（下記） | ✅ 見える |
| クラスが最終的に何色に解決されたか | ❌ 見えない | ✅ 見える |
| ボタン・入力の実 px | ❌ 見えない | ✅ 測れる |
| SP のナビ・スクロールの有無 | ❌ 見えない | ✅ 測れる |

🚨 **①の穴（2026-08-13 design が実証）**: 抽出の正規表現が
「`className=` → 省略可能な `{` → **引用符**」を前提にしているため、
`className={cn("...")}` は **`{` の次が引用符でなく `cn(` なので一致しません**。
`className={cn(` は **50箇所 / 16ファイル**あり、**そこは全部ノーチェック**です。

実際にこの穴に隠れていたのが `components/admin/locale-switcher.tsx:20` で、
**layout のヘッダに常時あるので全ページで深さ3を作っていました**
（①は「7件」と報告するが、②は同じコードで深さ3を検出する）。

🚨 **grep で数えただけで「無い」と言わない。** 実際に画面を開いて**目で見る**。
今回の事故は「個々のコンポーネントは正しいのに、**組み合わせを誰も見ていなかった**」ことが原因です。
コンポーネント単位のレビューでは**構造的に検出できません**。**必ずページ単位で見ること。**

#### 🚨 検査が緑でも、緑の意味を確かめる（陽性対照を作る）

> 由来: 2026-08-13。**幅が 0 になってログイン画面の文字が1文字ずつ縦に並んだのに、
> 描画実測の検査は「深さ1・あふれ0・タップ領域OK」で合格を返した。**
> 深さ・あふれ・寸法は**すべて「多すぎる」を測る検査**で、
> **「少なすぎる・狭すぎる」を測る目が1つも無かった**（`knowledge/decisions/verify-the-verifier.md`）。

**検査を書いたら、必ず「わざと壊したもの」を作って、赤が出ることを確認してから緑を信用する。**

これまでに監査スクリプトで見つかった穴は**6件**で、**全部「実際に走らせて」しか見つかっていない**:

| # | 穴 | 症状 |
|---|---|---|
| 1 | CDP ポートを固定していた | 前回の Chrome が生き残っていると**そちらのタブを測っていた** |
| 2 | 待ち時間を固定していた | dev の初回コンパイルに間に合わず**前のページを測っていた** |
| 3 | 面の定義が粗かった | **正解を違反として報告**していた（入力の塗り・選択中の塗り・`kbd`） |
| 4 | 潰れを見る目が無かった | **壊れているのに全項目合格**を返した |
| 5 | 着地パスとセレクタを確認していなかった | リダイレクトされた先で**別のボタンを押して「合格」**を出した。しかも `POST /api/onboarding` が飛び、**共有環境のオンボーディングを完了させてしまった** |
| 6 | 全幅ボタンにも「入力より低い」を当てていた | **正しく作られたログイン画面の 44px ボタンを違反**として出した（§3 の表では全幅は例外） |

🚨 **3・6 が最も危険。** 正解を違反と言う検査は使われなくなり、検査そのものが死ぬ。
🚨 **5 の教訓: 書き込みを伴う検査は、着地パスと「実際に押す要素」を先に出力してから実行する。**

**誤検出を消したら、必ず陽性対照をもう一度当てて「まだ赤が出る」ことを確認する。**
（例外を足すたびに検査は鈍る。鈍っていないことを毎回確かめる）

#### 🚨 「あるか」で数えない。「どの条件で、いくつあるか」で数える

> 由来: 2026-08-14。**同じ日に、同じ形の失敗を design と base2 が別々に踏んだ。**
>
> - **base2**: ログアウトと言語切替をヘッダから降ろすとき、受け皿を SP のドロワーにだけ置いた。
>   ドロワーは `md:hidden` なので、**PC では 0 個**だった。「受け皿はある」は本当だったが、
>   **画面幅ごとに数えていなかった**（commit c9cb0b3 で修正）。
> - **design（私）**: §3「ボタンは入力より低い」を**ページ全体の最大同士**で比べていた。
>   base2 が正しく分離したトークン（ボタン32px / 入力36px）を違反として出した。
>   **同じ `<form>` の中**という条件を落としていた。

**存在の確認は、条件を落とすと簡単に嘘になる。** 数えるときは必ず**条件を添える**:

| ❌ 数え方 | ✅ 数え方 |
|---|---|
| 「ログアウトはある」 | 「**PC で 1 個 / SP でメニューを開いて 1 個**」 |
| 「ボタンが入力より高い」 | 「**同じ `<form>` の中で**ボタンが入力以上」 |
| 「scroll-fade は入っている」 | 「**実際にあふれている箱**のうち、fade があるのが N/M」 |
| 「面は 1 段」 | 「**開いた状態を含めて**（`--click`）1 段」 |

🚨 **条件付きで数えられないものは、まだ検査になっていない。**
「実装した」という報告を受けたら、**どの条件で何個か**を聞き返す。

#### 面の判定基準（2本で揃えること）

**面 = 「4辺すべてに可視の罫線がある箱」「影」「親と違う背景」のいずれか**を持つ、
幅24px・高さ16px 以上の箱。
🚨 **1〜3辺だけの罫線（`border-b` / `border-t`）は Divider であって面ではない。**
区切りは面に数えません。

## 3. ボタンと入力の寸法 — X の実物に合わせる

> 堀池（2026-08-13）:「**作成のボタンの大きさも全然だめです。**」

Mobbin で X の実物を確認した結果（司令塔が実測）:

### ボタンの幅は「文脈」で決まる

| 文脈 | 形 |
|---|---|
| ページ内のフォーム | **内容幅・右寄せ**（全幅にしない） |
| モーダル / SP の主要アクション | **全幅・pill** |
| 編集画面の確定 | **ヘッダ右上の小さい pill**（フォームの下に置かない） |

🚨 **全幅の大きいボタンは、X では「モーダルの中」だけ**です。

### 高さ

**ボタンは入力より低い。** 入力は内容を受ける器なので背が高く、ボタンは操作なので小さい。
**同じ `h-10` で揃えない。**（SP の全幅ボタンだけは指のために大きくする）

#### 🚨 現状（2026-08-13 design が実測。違反の証拠）

`:3101` を Chrome の CDP で描画して computed style から測った値:

| 部品 | 定義 | 実測 |
|---|---|---|
| `Button` size=default | `button.tsx` の `h-8` | **32px** |
| `Input` | `input.tsx` の `h-8` | **32px** |
| 生の `<select>` | 各所の `h-8` | **32px** |

**3つとも 32px で完全に同じ。** 「ボタンは入力より低い」が守られていません。

再現: `node scripts/audit-surface-depth.mjs --base http://localhost:3101 --paths /login`
→ `[§3 ボタンの高さ] ボタン 32px >= 入力 32px` で **exit 1**。

#### 確定値（2026-08-14 確定）

🚨 **2026-08-14: Mobbin が通り、design が X の実物を確認しました（一次観察）。**
**制約から導いた結論と、実物が一致していました。** 以下は伝聞ではありません。

| 観察できたこと | 画面 |
|---|---|
| **入力はボタンより明らかに背が高い**（設定内のフォーム） | [X web / Confirm your password](https://mobbin.com/screens/e734808e-b12f-4909-8c53-36252796628b) |
| **ページ内のボタンは内容幅・右寄せ**（全幅にしない） | 同上 |
| **モーダル内の確定は全幅・pill・黒塗り** | [X web / Enter your password](https://mobbin.com/screens/64f23bfc-b9d4-4ae5-9826-6e761088531a) |
| 🚨 **未入力のとき確定ボタンが「グレー塗り」**（`opacity` で薄くしていない） | [X web / 未入力の Confirm](https://mobbin.com/screens/4ce3b6e8-7654-4de8-b777-bc5b3226c0f6) ／ [同（コード送信後）](https://mobbin.com/screens/6f667884-2731-48d3-b62e-7448c4261171) |
| 🚨 **ラベルが入力枠の中にある**（枠の外に別行で置いていない） | 上記いずれも |
| 🚨 **取消は全幅・白背景・薄い罫線**（塗らない） | [X web / Cancel](https://mobbin.com/screens/590d27bd-be38-43e7-94c8-0a70fd6298ce) |

🚨 **px の絶対値は読み取っていません**（スクリーンショットは縮尺が不定なので、
`x-ui-rules.md` と同じ「目測」になってしまうため）。**下の値は引き続き「制約から導いた値」です。**
**確認できたのは向きと文脈**で、それが**制約からの導出と一致した**、というのが今回の成果です。

| 対象 | 値 | どう決めたか |
|---|---|---|
| **入力の高さ（PC）** | **36px**（`--control-h-pc` を 2.25rem へ） | 下記の導出 |
| **ボタンの高さ（PC）** | **32px**（現状維持） | 同上 |
| 入力・ボタンの高さ（SP） | **44px**（確定済み） | WCAG 2.5.5 + Apple HIG + 憲章 §7 |
| **角丸** | **10px（`--radius: 0.625rem`）現状維持** | 下記 |
| **アクセント色** | **利用者が決める**（設定画面のカラーピッカー・④） | 製品が決める値ではない |
| **無効状態の色** | `muted` 系のトークン（`opacity` をやめる） | 憲章 §3 R4。色そのものを変える |

##### なぜ観察なしで決まるか（PC の高さ）

1. **規則は既に決まっている**: 憲章 §3「**ボタンは入力より低い**」（オーナー由来）
2. **実測**: いま **両方 32px** で、規則を満たしていない
3. **段は既にある**: `24 / 28 / 32 / 36 / 44`（`globals.css` のトークン）
4. **規則の理由がどちらを動かすかを決める**:
   > 憲章 §3「**入力は内容を受ける器なので背が高く**、ボタンは操作なので小さい」
   → **上げるのは入力**。ボタンを下げるのではない
5. → **入力 32px → 36px**（既存の段）、**ボタンは 32px のまま**。**新しい値を発明していない**

##### 角丸を現状維持にする理由

**変える理由が1つも出ていません。** オーナーからの指摘は寸法・書体・配置・情報設計で、
**角丸への言及はありません**。`--radius: 0.625rem`(10px) は `rounded-lg` として全体で一貫しています。
🚨 **「未検証だから変える」は理由になりません。** 観察が入ったら見直します。

##### 🚨 寸法は Tailwind の段から選ぶ。独自の値を作らない

> 堀池（2026-08-14・原文）:「**寸法はあくまでtailwindにあるものにして。
> xなどから参考にして、その中でtailwindにあるサイズで高いものを採用する**」

**Tailwind v4 の間隔は `--spacing`（既定 `0.25rem` = 4px）の倍数**で、`h-<n>` = `calc(var(--spacing) * n)`。
**このプロジェクトは `--spacing` を上書きしていない**ので、**4px 刻み**がそのまま段になります。

**いまのトークンは全部この段に乗っています**（2026-08-14 実測。**独自の値は1つもありません**）:

| トークン | 値 | Tailwind |
|---|---|---|
| `--control-h` | 44px | **`h-11`** |
| `--control-h-sm` / `--control-h-pc-lg` | 36px | **`h-9`** |
| `--control-h-pc` | 32px | **`h-8`** |
| `--control-h-pc-sm` | 28px | **`h-7`** |
| `--control-h-xs` | 24px | **`h-6`** |

### 決め

1. 🚨 **段に無い値を作らない。** `2.6rem` のような中間値を書かない
2. 🚨 **迷ったら「高い方」を採る**（堀池指示）。
   例: PC の入力を 32px(`h-8`) と 36px(`h-9`) で迷ったら **36px**
3. **ただし基準がある場所は基準が優先。**
   SP の 44px(`h-11`) は WCAG 2.5.5 と Apple HIG の値なので、
   「高い方」を理由に `h-12`(48px) へ上げない
4. **トークンのコメントに Tailwind の対応を書く**（`/* 44px = h-11 */`）。
   **段に乗っていることが読んで分かる状態**にする

##### 🚨 この値は差し替え可能です

**Mobbin が通ったら、X の実物と突き合わせて見直します。**
`--control-h-pc` を1行変えるだけで全画面に効く形になっているので、**やり直しのコストは1行**です。
（**トークン化を先にやっておいた理由がこれです**）

---|---|---|
| Button default 高さ | 未確定 | — |
| Button sm / xs 高さ | 未確定 | — |
| Input 高さ | 未確定 | — |
| SP の主要ボタン高さ | 未確定 | — |

## 3c. 管理者の構成画面の手本（Anthropic / WorkOS の SSO 設定）— **v1 用の記録**

2. **§1**「SP は横幅が狭い。**カードをやめて上下の Divider にする**のが既定」。**堀池が見ているのはモバイル**。
   WorkOS の画面は**デスクトップ**で、前提が違う
3. **リスクが非対称**。Divider → 後からカードを足すのは安い。
   カード → 剥がすのは、**2026-08-13 に丸1日かけた作業そのもの**
4. **面の残量**。Divider で区切れば**レベル1を使い切らない**ので、

分かれ目は利用者の種類ではなく「**1項目1値の並び**」か「**構造を持つまとまり**」かで、

| **入力のラベル** | **枠の中** | — | **枠の外・上** | 🚨 **枠の外・上（Believe）** |
| **設定のグループ** | — | **面ゼロ・行だけ** | **薄い塗りの塊** | 🚨 **面ゼロ（Coinbase）** |
| **破壊的操作** | — | **赤い文字** | **Danger Zone で別グループ** | 🚨 **別グループ + 赤い文字（両取り）** |

**なぜそう決めたか:**

- **ラベルは枠の外・上。** X の「枠の中」は**枠が常に見えている前提**の作法。

  **表示モードでは枠が無い**。枠の中にラベルを置くと**表示モードでラベルが消える**。

- **破壊的操作は「別グループ + 赤い文字」。**
  Believe の「見出しで隔離する」は**押し間違いを構造で防ぐ**ので採る。
  Coinbase の「赤い文字」は**色で警告する**ので併用できる。**排他ではない。**

- **空状態は点線の枠 + 見出し + 一文**（`@shadcn/empty` の形と一致）

## 5. パフォーマンス

1. **N+1**: リレーションを行ごとに引いていないか。

## 5b. 🚨 二重送信は `useRef` で根本的に防ぐ

> 堀池（2026-08-13）:「**二重送信は必ず useEffect や useState だけでなく useRef で根本的に防ぐ。**」

**`useState` の `isSubmitting` だけでは防げません。** `setState` は非同期で、
**再レンダーが走るまで値が変わらない**ため、連打された2回目が「まだ false」を読んで通ります。
`useEffect` も同じ理由で後追いです。

```tsx
const inFlight = useRef(false);          // ← 同期的に即座に変わる。これが本体
const [pending, setPending] = useState(false);  // ← 表示のためだけ

async function onSubmit() {
  if (inFlight.current) return;          // 🚨 ここで確実に弾く
  inFlight.current = true;
  setPending(true);                      // spinner / 無効化の表示用
  try {
    await save();
  } finally {
    inFlight.current = false;
    setPending(false);
  }
}
```

**役割を分ける:**
- **`useRef`** — 実際に弾く（同期・再レンダーを待たない）
- **`useState`** — 見た目を変える（`spinner` を出す・ボタンを無効化する）

送信中の表示は **`@shadcn/spinner`** を使う（自作しない）:
`npx shadcn@latest docs spinner` → https://ui.shadcn.com/docs/components/base/spinner

### 見つけ方

```
rg -n 'onSubmit|handleSubmit|onClick.*async' apps/studio/components apps/studio/app | head -40
```

見つけた送信経路それぞれに `useRef` のガードがあるかを確認する。
🚨 **`disabled={isSubmitting}` だけの箇所は違反**（描画が間に合わない）。

### 確認のしかた（実測する）

ボタンを**素早く3回クリック**して、ネットワークタブでリクエストが **1本だけ**であることを見る。
🚨 **コードを読んで「防げているはず」で終わらせない。**

## 6b. 🚨 常設領域に置いてよいのは「毎日押すもの」だけ

> 堀池（2026-08-14・原文）:「ヘッダーに「ログアウト」「言語切り替え」は必要ない。これらはユーザー設定。

### 判断のしかた

**「これを毎日押しますか」に「いいえ」と答えられるものは、常設領域から降ろす。**

| 置き場所 | 何を置くか |
|---|---|
| **常設**（ヘッダ・下部ナビ） | 毎日・何度も使うもの |
| **メニューの中／ユーザーの行** | ときどき使うもの・**自分の設定** |
| **設定画面** | 一度決めたらほぼ変えないもの |

### いま降ろすもの（2026-08-14 実測）

| | いまの場所 | 移す先 |
|---|---|---|
| **ログアウト** | ヘッダ（`layout.tsx`） | 🚨 **メニュー最下部に既にある**（`mobile-nav.tsx:144`）。**ヘッダから消すだけ** |
| **言語切り替え** | ヘッダ（`LocaleSwitcher`） | **メニュー最下部のユーザーの行**へ |

**ヘッダに残すもの**: サービス名（いまどこにいるかの手がかり）と **横断検索**（毎日使う）。

🚨 **これで「個人設定の画面ができるまでヘッダから外せない」という制約が解けます。**
ユーザーの行が受け皿になるので、**画面の完成を待たずに降ろせます**
（`ui-placement-by-frequency.md` の「v0.9 の実装状況」に書いた制約は、この設計で解消）。

## 7. SP（スマートフォン）は別物として見る

### 🚨 タップ領域の測り方（**部品の箱ではなく「領域」で測る**）

> WCAG 2.2 SC 2.5.8 の `target` の定義（一次情報。2026-08-14 に引用を確認）:
> 「**region of the display that will accept a pointer action**,
> such as the interactive area of a user interface component.」

**target は「ポインタ操作を受け付ける領域」であって、部品の見た目の箱ではない。**

- チェックボックス・ラジオは、**関連づけられた `label` を押しても操作できる**ので、
  **`label` の領域が target**。**つまみ自体を 44px にする必要はない**
  （`size-6`(24px) を `min-h-11`(44px) の行で包む形が**正解**）
- 監査（`audit-surface-depth.mjs`）も**この定義で測る**:
  `closest("label")` → `label[for=id]` → 無ければ部品自身、の順で**大きい方**を採る

| 基準 | 要求 | 等級 |
|---|---|---|
| SC 2.5.8 Target Size (Minimum) | 24×24 CSS px | AA |
| SC 2.5.5 Target Size (Enhanced) | **44×44 CSS px** | AAA |

🚨 **本プロジェクトの SP は 44px を満たす**（AA の 24px は法的な下限であって設計目標ではない。
参考にしている X iOS / Coinbase iOS / Believe iOS は**すべて SP**、Apple HIG も 44pt）。

> 由来: 2026-08-14。saml が「24px のつまみを 44px の行で包んだ実装」を監査が違反と報告した件。
> **正しい実装を違反と言っていたのは監査側**だった。
> 🚨 このとき「**部品の種類で例外を作る**（radio だけ 24px 下限にする）」案も出たが、**採らなかった**。
> **例外リストを増やすと、検査が何を見ているかが曖昧になる。規格の定義そのものに寄せる方が網目が細かい。**

> 堀池（2026-08-13）:「ナビなどはヘッダーとして上部ではなく、**指が届きやすい下部**にするべきだが、
> 高さがありすぎると画面を占有するので、ちょうどいいようにする。
> その画面ですぐにしたいアクション（編集、保存など）は**右下**に配置して、
> それだとナビが少なくなるので、**左端にはサイドメニューを表示するためのアイコン**を設けておく。」

- ナビは**下部**。高さは占有しすぎない
- **主要アクションは右下**
- **左端にサイドメニューを開くアイコン**
- カードでなく **Divider**（§1）
- 入力の `font-size` は **16px 未満にしない**（iOS が勝手に拡大する）
- 固定バーには `env(safe-area-inset-bottom)`、`body` に下 padding

🚨 **PC で作ってから SP に縮めない。** 素の CSS がモバイルで、`min-width` だけで広げる。

## 8b. 🚨 「実装した」ではなく「オーナーの画面で見えた」が完了

> 堀池（2026-08-14）:「**なにも反映されてないがどうなっている？**（まだログアウトや言語選択が常に出ていたり）」
> そして同日、**同じことが2回目**だと指摘された:「**これは2回目です。ルールとして追加して。**」

### 何が起きたか（2回とも同じ）

| 回 | 指摘 | 実態 |
|---|---|---|
| 1 | 「横スクロールにグラデーションを付けて」 | **実装済み**。オーナーの見ているビルドが古かった |
| 2 | 「まだログアウトや言語選択が常に出ている」 | **実装済み**。ビルドが **29 コミット分**古かった |

**どちらも design は「実装済みです。ビルドが古いだけです」と報告して終わっていた。**
🚨 **それではオーナーの画面は1ミリも変わらない。**

### 決め

**作ったものは、オーナーが見る環境に届いて初めて完了。**

1. 🚨 **「実装済み・ビルドが古い」を報告の結論にしない。**
   **「いつ焼くか」まで決めて、決まっていなければそれ自体を課題として上げる**
2. 🚨 **オーナーから同じ指摘を2回受けたら、設計や実装ではなく「届け方」を疑う。**
   1回目は行き違い。**2回目は仕組みの欠陥**
3. **オーナーに見せる環境と、こちらが検証する環境を一致させる。**
   ずれるなら、**ずれている事実をオーナーに先に伝える**（黙って古いものを見せない）
4. **見えていないものは「無い」と同じ。** 実装の完了報告に、**どこで見えるか**を必ず添える

### 🚨 実測での確かめ方（毎回これで切り分ける）

```bash
# ① オーナーの見ているビルドはいつのものか
docker inspect ohmycms-studio --format '{{.Created}}'
# ② そのビルド以降に何件入ったか
git log --oneline --since="<①の日時>" | wc -l
# ③ 配信されている実物に、その要素が在るか（grep でなく DOM で見る）
node scripts/audit-surface-depth.mjs --base <オーナーの URL> --paths <対象>
```

🚨 **③ を `grep` で済ませない。** 「文字列が HTML に在る」と「**ヘッダに在る**」は別。
2回目の切り分けでは、`grep` だと `:3102` にも「日本語」が出て**判断を誤りかけた**
（実際はメニューの中へ移動済みで、ヘッダには無かった）。**どこに在るかは DOM で測る。**
