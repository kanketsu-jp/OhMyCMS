# 検査は索引を見る。ただし「走査」と「照合」で直し方が違う

## 背景

このリポジトリは **1 つの作業ツリーを多数のペインで共有**している。検査が `globSync` で
作業ツリーを直読みすると、**他のペインの書きかけ（未追跡ファイル）まで見える**。

2026-08-16 に実際に起きた形（1 日に 3 回、同じ構造）:

| # | 何が起きたか | 誰が落ちたか |
|---|---|---|
| ① | ショートカットの写しが古いまま置かれた | 🚨 ショートカットに触っていない人 |
| ② | MCP の正（`packages/mcp/`）を変えた人が `root:` の外で検査に掛からなかった | 🚨 `apps/studio` を触った無関係な人 |
| ③ | ゴミ箱機能の**未追跡**ファイル（`app/(admin)/admin/trash/` ほか）が検査に見えた | 🚨 そのファイルに触っていない人 |

**共通しているのは「変更した人と、落ちる人が違う」**。①② は `lefthook.yml` の `glob:` で
「どのファイルを触ったら走るか」を直した。③ は「**何を読むか**」なのでここで決める。

## 決めたこと

### 1. 違反を探す走査は、`git` の索引に絞る

`apps/studio/scripts/lib/tracked-files.mjs` の **`trackedGlob()`** を通す（`globSync` を直に呼ばない）。
2026-08-16 時点で **16 本**がこれを使う（`readTracked()` は 24 本）。

- `git ls-files` は**索引**を読むので、**`git add` した新規ファイルは含まれる**
  ＝ **add した瞬間に本人の手元で落ちる**。「add せずに commit する」道は無いので抜け道にならない。
- 実測（別 clone・壊し方 2 通り）:
  🟢 綺麗な木 → exit=0 ／ 🟢 違反を**未追跡**のまま置く → exit=0 ／
  🔴 その同じファイルを `git add` → exit=1 ／ 🔴 **追跡済み**のファイルに同じ違反 → exit=1

### 2. 🚨 宣言と実体を突き合わせる「照合」は、**両側**を索引から読む

**片側だけを索引に移すと、赤の向きが裏返るだけになる。** 実測（`check-audit-coverage`）:

```
ページの列挙だけ索引にし、巡回一覧を作業ツリーのままにした場合:
  変換前 …「実在するのに**巡回していない**ページ 1 件」（未追跡の実体が見えていた）
  変換後 … 「巡回一覧に在るが**実在しない**ページ 1 件」（宣言だけ見えていた）
```

→ 一覧も **`readTracked()`**（`git show :<path>`）で索引から読む。受入は 4 通り全部を測る:

| 状態 | 期待 | 実測 |
|---|---|---|
| ページ未追跡 + 一覧も未 staged | 🟢 緑（どちらもまだ入らない） | exit=0 |
| ページだけ `git add` | 🔴 赤「実在するのに巡回していない」 | exit=1 |
| 一覧だけ `git add` | 🔴 赤「一覧に在るが実在しない」 | exit=1 |
| 両方 `git add` | 🟢 緑 | exit=0 |

**「どちらも入っていないなら緑」が肝**。書きかけの人が、他人を落とさない。

### 3. 🚨 共有ツリーで緑でも、新しい clone で緑とは限らない

同じ日に出た別の形。**写し（生成物）は commit されたのに、それを作れる生成器が未コミット**
だった 30 分がある。共有ツリーでは生成器が手元に在るので緑に見え、**新しい clone では赤**だった。

→ **生成物を `--write` する前に、生成器側の未コミットが 0 行かを見る。**
→ 門の状態を報告するときは、**どのツリーで測ったか**を書く。

### 4. 🚨 「一覧」と「中身」は**別の扉**。両方閉めないと閉まらない

同じ日に、同じ直しを **3 段**やり直した。**1 段目だけで「索引へ寄せた」と報告したのが誤り**だった。

| 段 | 何が漏れていたか | 直し方 | 見つけた人 |
|---|---|---|---|
| ① | **未追跡ファイル**が検査に見える | `globSync` → `trackedGlob`（**一覧**を絞る） | polish |
| ② | 追跡済みファイルの**まだ `git add` していない編集**が見える | `readFileSync` → `readTracked`（**中身**も索引） | toast |
| ③ | 🚨 **索引に在って作業ツリーに無い**ファイルが、黙って一覧から落ちる | 一覧を `git ls-files` から採る（作業ツリーを glob して交差させない） | saml |
| ~~④~~ | ~~一覧と中身で見る場所が違う~~ | 🚨 **取り下げ**（下記） | ~~schema~~ |

🚨 **④ は誤りだった。2026-08-17 に司令塔が書き、同日この文書の下半分（§「索引は
『検査に見せる場所』であると同時に『他人へ配る場所』」）で実測により否定された。**
真因は検査の作りではなく、**索引に半端な削除が staged のまま置かれていたこと**。
消さずに残すのは、**なぜ 4 段目が在ったのか**を次の人が辿れるようにするため。

**なぜ誤りが入ったか**（同じことを繰り返さないために書く）:
schema は司令塔への便で「検査は一覧をどこか別の所から作っているのだと思います。
🚨 **ここは私の推測です。読んで確かめていません**」と、**推測だと明示していた**。
司令塔はそのラベルを落として、**決定の表に 1 行として入れた**。
＝ 🚨 **人が「推測です」と書いたものを、実測が付く前に durable な規約へ昇格させた。**
表に入った瞬間、次に読む人には推測と実測の区別が付かなくなる。

- ① は「**どのファイルを見るか**」、② は「**何が書いてあるか**」。**別の扉**なので、
  片方だけでは閉まらない。実測: `labels-manager.tsx` を staged にせず書き換えると、
  ①だけ直した検査は **落ちた**（＝ 他人の書きかけで、触っていない人が止まる）。
- ③ の実測: 追跡済みファイルを作業ツリーから消すと、旧実装は一覧が **136 → 135 本**に減り、
  それでも「未追跡で飛ばした: 0 本」と出た ＝ 🚨 **見ていないのに「全部見た」と読める**。
  （他人が消している最中・rename の途中・stash した直後に起きる。）

🚨 **どの段も、私（polish）ではなく測った人が見つけた。**
**「寄せた」と報告する前に、①②③のどれを閉めたのかを言えること。**

## やってはいけないこと

- ❌ 新しい検査を `globSync` で書く（`trackedGlob` を使う。20 本を 1 本ずつ直す羽目になる）
- ❌ 照合型の検査で片側だけ索引に移す（**赤の向きが裏返るだけ**で、直っていない）
- ❌ `readTracked()` の `null`（未追跡）を「中身が空」と同じに扱う
- ❌ `git ls-files` が 0 件のときに検査を緑で通す（**git が動いていない合図**。例外で落とす）

## 🚨 これで消えないもの

- 他の人が `git add` した瞬間、そのファイルはこちらの門にも入る。
  **消えるのは「まだ add していない」1 種類だけ。**
- ~~`readdirSync` で集めている検査 6 本は未変換~~ → 🚨 **2026-08-16 中に 4 本を変換した**
  （`raw-api-message` / `page-actions` / `i18n-placeholders` / `items-entry`）。
  変換の理由は、実際に読む範囲を測ったから: **`page-actions` 427 本 / `raw-api-message` 407 本**
  （lib・app・components・stories）＝ **他のペインの書きかけを読める広さだった**。
  「いまは混じっていないだけ」を、その日のうちに閉じた。
  - `mcp-catalog` … saml が自分で直すと宣言（**持ち主が直すほうが安全**）
  - ~~`i18n-load` … 読む先は `i18n/messages` だけ。**まだ変換していない**~~
    → 🚨 **2026-08-16 に変換した**（toast）。読む先が狭いことは、変換しなくてよい理由にならない。
    **辞書はコードと突き合わせる照合型の相手側**なので、片側だけ索引にすると
    **赤の向きが裏返る**（この文書の §「片側だけ移すと裏返る」と同じ形）。
    あわせて `namespacesOnDisk` → **`namespacesInIndex` に改名**した
    （中身が索引になったのに名前が「ディスク」だと、**次の人が作業ツリーだと思って使う**）。
- 🚨 **一覧を索引にしても、中身が作業ツリーなら扉は半分しか閉まらない**（2026-08-16・toast が実測）。
  `trackedGlob`（**どのファイルを見るか**）だけを変えて `readFileSync`（**何が書いてあるか**）を
  残すと、閉まるのは「**未追跡ファイル**」の扉だけで、
  **「追跡済みファイルの、まだ add していない編集」はそのまま読む**。
  実測: `labels-manager.tsx` を **staged にせず**書き換えると `check-i18n-usage` が exit=1
  ＝ **触っていない人のコミットが止まる**。→ **中身も `readTracked` にする。**
- 🚨 **索引から読む検査は、手で叩くと「staged していない自分の変更」が見えない。**
  門（lefthook）は staged で走るのでコミット時は見える。
  **「直したのに検査が古いことを言う」ときは、まず `git add` を疑うこと。**
- 🚨 **囮を持つ検査を直したら、`git add` してから回す**（2026-08-17・auth の実測）。
  staged していないと、**囮は「直す前のファイル」に当たり、
  的が死んでいることに気づけないまま緑になる**。
  実測（`74ef877`）: `layout.tsx` の呼び出しに引数を 1 つ足したので、囮が持つ**完全一致の的**
  （`"userLabel={displayUserLabel(me.ok ? me.data : null)}"`・**4 箇所**）は当たらなくなるはずだった。
  🔴 ところが検査は **緑**で、しかも囮は「**置換 2 件**」＝ **届いたと報告していた**。
  🟢 原因は「索引を読むので、stage していない変更が見えていなかった」。
  🚨 **「緑だから直った」と読んでいたら、的が死んだ検査をそのまま配っていた。**
  - 🚨 **囮の「置換 N 件」は、N ≥ 1 でも安心の材料にならない。**
    **どのファイルに当たったか**（索引の版か、作業ツリーの版か）までは言っていない。
    ＝ **「置換 1 件」は「私が直した版に当たった」を意味しない。**
- 🚨 未追跡は **飛ばす**。空文字にしない（空は「中身が無いファイル」として数えられ、**見ていない 0** を作る）。
  **飛ばした件数は 0 件でも出す。**

## 🚨 索引は「検査に見せる場所」であると同時に「他人へ配る場所」（2026-08-17 追記）

ここまでは **`git add` していないと自分の変更が見えない**（＝ 緑が「見ていない」を意味する）話だった。
**逆向きも在る。** 2026-08-17 に pages が 1 日で 3 通り踏んだので、実測ごと残す。

```
① add せずに検査 …… 緑が「見ていない」になる（この文書の上半分。既に書いてある）
② 🚨 add したまま置く … **他人の門が赤くなる**
③ 🚨 add したまま置く … **他人の commit に自分の変更が入る**
```

### ② 他人の門が赤くなった（実測）

pages が `/admin/reports/manage` の**削除**を索引に置いたまま受入基準を回していた間:

```
schema の commit …… 🥊 check-raw-row-exports
   Error: ENOENT: open 'app/(admin)/admin/reports/manage/loading.tsx'
                🥊 typecheck
   .next/types/validator.ts: TS2307 Cannot find module '…/reports/manage/page.js'
L4 の commit ……… 同じ ENOENT で止まった
```
🚨 **落ちたのは触っていない人**。原因は「索引に**半端な削除**が載っていた」こと
（生成物 `.next/types/validator.ts` が消えたページを指していた）。
🚨 L4 は「検査が一覧を索引から作り、中身を作業ツリーから開いているのでは」と推測したが、
**外れていた**。検査の作りではなく、**半端な索引を全員が読んだ**形。

### ③ 他人の commit に自分の変更が入った（実測・こちらのほうが静か）

```
2172f27「パンくずに罫線文字が戻らないよう、守り手を付ける」…… 8 ファイル
   うち 6 ファイルは **pages の J1 の分**（reports/manage の削除・page-meta・
   audit-surface-depth・reports.json ja/en）
🚨 pages も、その作業者も、git commit を 1 回も打っていない
```
🚨 **②は赤くなるので気づける。③は誰も落ちない。**
commit の題と中身が合わなくなるだけなので、**後から履歴を読む人が
「なぜこの変更が入ったか」を辿れなくなる**。

### ✅ だからこうする

- **`git add` → 検査 → `git commit` を 1 手でやる。**
  索引に置いたまま次の作業へ行かない（**置いている間ずっと、他の 5 人に配っている**）。
- 🚨 **`git commit` はパス指定で打つ**。同日 pages が実測した:
  ```
  git commit -- <自分の 6 本>  … 索引に他レーンの 2 ファイルが載っていたが、
                                  commit に入ったのは **自分の 6 本だけ**
  ```
  ＝ **パス指定なら巻き込まない。** 素の `git commit` は索引に在るもの全部を持っていく。
- **門が落ちたとき、「自分のものか」を切り分ける。**
  同日、pages の commit が `typecheck` で 1 回落ちたが、原因は
  **別のレーンが編集中のファイルが同じ瞬間の木に在ったため**（数分後に rc=0）。
  ＝ 🚨 **共有ツリーでは「落ちた門」が自分のものとは限らない。**
  自分の変更を疑う前に、**落ちた対象のパスが自分のものか**を見る。
