# 文言検査の範囲は「画面に届くか」で決める。`lib/` を丸ごと足さない

> 由来: 2026-08-15。司令塔の調査で「**`check-i18n-hardcoded.mjs` が `lib/` を見ていない。
> `lib/` の中に画面へ出る日本語のリテラルがある**（例: `ApiError(403, …, "権限がありません")`）」
> と指摘された。**範囲を広げるかどうかは design が決める**、という割当だった。

## 決定

**`lib/` を検査対象へ丸ごと足さない。** 範囲は**ファイルの場所ではなく、経路**で決める。

## 🚨 2026-08-16 訂正 — 下の実測の**結論が誤っていました**（前提が崩れています）

**「クライアントは API の生文言を出していません」は誤りです。出ています。**

> 気づいた経緯: [w4A:p1V / storage] が **振る舞いで探し直して 12 ファイル**を見つけた。
> storage 自身も 1 回目は `error?.message` という**書き方**で探して **0 件**と報告していた。

**私の誤りの構造**（下の表を見れば分かるとおり、**関数名で探していました**）:
```
私が測ったこと   apiMessage() の呼び出し … 0 件   ← これ自体は正しい
私が結論したこと 「だから生文言は画面に出ない」   ← 🚨 誤り
実際             **同じ振る舞いが別名で 12 ファイルに実装されている**
                 （messageFrom() など。名前が違うだけ）
```
🚨 **「名前で探すな。振る舞いで探せ」を配った当人が、名前で探して外しました。**

**【測った】2026-08-16（`app/` `components/` 214 ファイル・コメント除去済み）:**
```
error オブジェクトの .message を読んでいる箇所   22 件 / **12 ファイル**
🟢 対照(-) 存在しない語 → 0 件（＝「全部拾う」探し方ではない）
🟢 対照(+) useT/getT を持つファイル → 99 件（＝読めている）
```
**画面まで追跡した実例**（`components/admin/agents-manager.tsx`）:
```
 43  function messageFrom(payload, fallback) { … return payload.error.message }
194  setError(messageFrom(payload, …))     → error state → 画面
```
＝ **戻しているだけではなく、表示に届いています。**
storage の curl 実測では、その文言が **`lib/` の日本語リテラル**でした
（`{"error":{"code":"UNAUTHENTICATED","message":"認証が必要です"}}`）。
🚨 **英語で見ている人の画面に、この日本語が出ます。**

### 訂正しても変わらないこと / 変わること

| | 前 | 後 |
|---|---|---|
| `lib/` を丸ごと検査へ足すか | **足さない**（188 件は**誤検出**だから） | **足さない**（188 件は**真の検出**だが、**一度に赤くすると門が死ぬ**から） |
| 保険の検査 | `apiMessage` という**識別子**を呼んでいないこと | 🚨 **不十分。別名で実装される**（今回そうなった）。**振る舞いで見る**必要がある |
| なりすまし | 経路がある | **無い**（storage が実測で否定。`errorResponse()` は自分で書いた文言だけ返す） |
| 危険の種類 | なりすまし | 🚨 **i18n**（英語の画面に日本語） |

🚨 **結論が同じでも、理由が変われば次の判断が変わります。**
「誤検出だから足さない」なら**永久に足さない**。「門が死ぬから足さない」なら**段階的に足す**。

### 段階（司令塔の判断 2026-08-15・(c) 採用）

```
lib/ は文言でなく **鍵**を持ち、画面が辞書で引く（(c)）
🚨 233 件を一度に触らない。**画面から実際に触れるもの 約 9 件**から
🚨 (a)（message を捨てて fallback だけ）を**つなぎに入れない**
   → INVALID_FIELD 1 つに意味の違う文言が 7 つ在る。潰すと戻せない
```
🚨 **検査を先に入れない。** いま振る舞いの検査を門へ載せると **12 ファイルが赤**になり、
**全ペインが門を回避し始めます**（下の「併せて守ること」の 1 つ目と同じ失敗）。
**直す範囲が減ってから載せる。**

## 実測（当初の記録。🚨 上の訂正を読んでから見ること）

    lib/ の日本語リテラル                     209 件
    うち ApiError(...) の文言                 188 件
    apiMessage() の実呼び出し（コメント除く）   **0 件**
    apiErrorKey() の呼び出し                   10 件

**クライアントは API の生文言を出していません。** `lib/admin/forms.ts` の 2 本が経路を分けています。

| 関数 | 何を返すか | 画面に届くか |
|---|---|---|
| **`apiErrorKey()`** | API の **code** を辞書の鍵へ写す。知らない code は `unexpected` へ倒す（fail closed） | 届くのは**辞書の文言** |
| **`apiMessage()`** | **API の生文言をそのまま**返す | 🚨 **届く。ただし呼び出しが 0 件** |

→ **188 件の `ApiError` の文言は、いま画面に出ていません。**
🚨 **この 1 行が誤りでした（2026-08-16）。上の訂正節を読むこと。**
**`apiMessage()` は使われていませんが、同じ振る舞いが別名で 12 ファイルに在ります。**
`lib/` を検査へ足すと、**そのまま 188 件の誤検出**になり、全ペインの受入が止まります。

🚨 **「ファイルの場所」で範囲を決めると、こうなります。**
`lib/` にあるかどうかは、その文字列が利用者に見えるかを何も言っていません。

## 🚨 `apiMessage()` を消した主たる理由は、i18n ではなく**なりすまし**

> 司令塔（2026-08-15）:「**消す理由は i18n ではなく安全側です。
> `?error=` に任意の文章を渡すとアプリ公式のエラー枠に出せる（なりすまし）。
> これは i18n の範囲論より重い**」

`apiMessage()` は **API の生文言をそのまま返します**。これを `?error=` に載せる作りにすると、
**URL は利用者が自由に書けるので、細工したリンクで任意の文章を
「アプリが出した公式のエラー」として画面に出せます**（2026-08-15 実測）。

    ❌ /admin/…?error=<攻撃者が書いた文章>   → アプリ公式のエラー枠にそのまま出る
    ✅ /admin/…?error=<code>                 → 許可リストに無ければ unexpected へ倒す

**辞書化の話とは別の問題**です。仮に全部の文言を辞書化しても、
**生文言を通す関数が残っていれば、なりすましは成立します。**

副次的に、この関数自身にもハードコードがあります:

    `APIエラーが発生しました (${response.status})`

**呼び出しは 0 件**なので実害は出ていませんでした。**残すと、次の人が「便利な関数」として使います。**

## だから、こうする

1. 🚨 **`apiMessage()` を消す**（主たる理由は**なりすましの経路を塞ぐこと**。i18n は副次）
2. **保険として、`app/**` と `components/**` から `apiMessage` を呼んでいないこと**を検査にする。
   **1 つの識別子を見るだけ**なので安く、誤検出も出ない
3. **`lib/` を丸ごと検査へ足さない**（誤検出 188 件で門が死ぬ）

🚨 **`ApiError` の日本語を辞書化する話とは別**です。あれは**開発者が読むもの**で、
利用者には code 経由で辞書の文言が届いています。**辞書化したくなったら、
まず「誰が読むのか」を決めてから**にしてください。

## 併せて守ること

- **検査の範囲を広げるときは、広げた先の件数を先に数える。**
  今回は **209 / 188 / 0 / 10** を数えてから決めました。数えずに広げると、
  **その日から全ペインが赤い門を回避し始めます**（門が死ぬ）
- 🚨 **「◯◯が見られていない」という指摘は、まず正しいかを測る。**
  当初は「見ていない」は**正しく**、「画面へ出る」は**支持されなかった**と書いた。
  🚨 **2026-08-16 訂正: 後者も正しかった。私の測り方（関数名で探した）が外していた。**
  **指摘を否定した側が、否定の根拠を名前で採っていないかを見ること。**
- 🚨 **同じ振る舞いは、別の名前で必ず実装される。**
  `apiMessage()` を消しても、`messageFrom()` が 12 ファイルに生まれていた。
  **識別子 1 つを見る「安い検査」は、安いぶん、名前が変わると何も見ていない。**
  → 関連: [[trash-and-restore-ui]] §4.5（同じ理由で「鍵の名前で横断検索しない」と決めている）
- 関連: [[checks-must-declare-blind-spots]]（**印字と終了コードは別**／**標本の偏り**）、
  [[i18n-required]]（なぜ全文言が自前の辞書にあるのか）
