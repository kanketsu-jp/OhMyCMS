# 文言検査の範囲は「画面に届くか」で決める。`lib/` を丸ごと足さない

> 由来: 2026-08-15。司令塔の調査で「**`check-i18n-hardcoded.mjs` が `lib/` を見ていない。
> `lib/` の中に画面へ出る日本語のリテラルがある**（例: `ApiError(403, …, "権限がありません")`）」
> と指摘された。**範囲を広げるかどうかは design が決める**、という割当だった。

## 決定

**`lib/` を検査対象へ丸ごと足さない。** 範囲は**ファイルの場所ではなく、経路**で決める。

## 実測（指摘の前提が支持されなかった）

    lib/ の日本語リテラル                     209 件
    うち ApiError(...) の文言                 188 件
    apiMessage() の実呼び出し（コメント除く）   **0 件**
    apiErrorKey() の呼び出し                   10 件

**クライアントは API の生文言を出していません。** `lib/admin/forms.ts` の 2 本が経路を分けています。

| 関数 | 何を返すか | 画面に届くか |
|---|---|---|
| **`apiErrorKey()`** | API の **code** を辞書の鍵へ写す。知らない code は `unexpected` へ倒す（fail closed） | 届くのは**辞書の文言** |
| **`apiMessage()`** | **API の生文言をそのまま**返す | 🚨 **届く。ただし呼び出しが 0 件** |

→ **188 件の `ApiError` の文言は、いま画面に出ていません。**
`lib/` を検査へ足すと、**そのまま 188 件の誤検出**になり、全ペインの受入が止まります。

🚨 **「ファイルの場所」で範囲を決めると、こうなります。**
`lib/` にあるかどうかは、その文字列が利用者に見えるかを何も言っていません。

## 本当の抜け道は 1 つだけ

**`apiMessage()` が呼ばれるようになった瞬間**、サーバの生文言（辞書を通っていない日本語）が
画面に出ます。この関数自身にもハードコードがあります:

    `APIエラーが発生しました (${response.status})`

- 🚨 **`?error=` へ渡してはいけない**とコメントに書いてあります。
  URL は利用者が自由に書けるので、**細工したリンクで任意の文章をアプリ公式のエラー枠に出せます**
  （2026-08-15 実測。これは i18n ではなく**なりすまし**の問題）
- **いま呼び出しが 0 件**なので、実害は出ていません

## だから、こうする

1. **`lib/` を丸ごと検査へ足さない**（誤検出 188 件で門が死ぬ）
2. **`apiMessage()` を消す**（呼び出し 0 件。残すと、次の人が「便利な関数」として使う）
3. 消せない事情があるなら、**`app/**` と `components/**` から `apiMessage` を呼んでいないこと**を
   検査にする。これは**1 つの識別子を見るだけ**なので安く、誤検出も出ない

🚨 **`ApiError` の日本語を辞書化する話とは別**です。あれは**開発者が読むもの**で、
利用者には code 経由で辞書の文言が届いています。**辞書化したくなったら、
まず「誰が読むのか」を決めてから**にしてください。

## 併せて守ること

- **検査の範囲を広げるときは、広げた先の件数を先に数える。**
  今回は **209 / 188 / 0 / 10** を数えてから決めました。数えずに広げると、
  **その日から全ペインが赤い門を回避し始めます**（門が死ぬ）
- 🚨 **「◯◯が見られていない」という指摘は、まず正しいかを測る。**
  今回は指摘のうち「見ていない」は**正しく**、「画面へ出る」は**支持されませんでした**。
  片方だけで動くと、誤検出を配ることになります

  [[i18n-required]]（なぜ全文言が自前の辞書にあるのか）
