# 手順ドキュメントはステップ式で書く。前提を独立させ、スクリーンショットを使わない

## 背景

> 基準日: 2026-08-13

堀池から Anthropic のヘルプ記事（SSO 設定手順）が「手本」として示された。
同じ日に、実際の困りごとが起きている。**「起動できるのに入れない」**——
README には起動手順があったが、**最初のログイン方法が書かれていなかった**。

書いた人は分かっているので気づかない。**読む人は初見**である、という前提が抜けていた。

## 決定

**手順ドキュメントは次の型で書く。基準は「clone した人が、それだけを読んで起動しログインできるか」。**

1. **前提条件を独立した節にする。** 本文の途中に前提を混ぜない
2. **H2 = 大きな作業ひとつ。** その中を `1. 2. 3.` に割り、**「どこを開く → 何を入れる → 次へ」**まで書く
3. **画面名・ボタン名・パスは太字にする。** 文の中で「触る対象」が目立つようにする
4. **注意書きは2種類だけ。** `**注：**`（補足）と `**重要：**`（守らないと壊れる）。
   絵文字の記号を装飾に使わない
5. **最後に「困ったときは」を置く。** 参照先だけでなく、**何を添えて聞くか**まで書く
6. 🚨 **スクリーンショットを貼らない。** 経路を文章にし、UI 要素を太字で示す

## 理由

1. **画面写真は腐る。** 経路の言語化なら、画面が変わっても文の意味が残る。
   写真は「更新されていない写真」が最も害になる（読者は写真を信じる）
2. **前提が本文に混ざると、詰まってから気づく。** 独立していれば着手前に判別できる
3. **太字は、日本語の文中で「触る対象」を切り出す唯一の軽い手段。**
   引用符や括弧は文の意味に使うので、装飾として奪えない
4. **注意書きの種類を2つに絞ると、読み飛ばしても壊れない。**
   記号（⚠️ 🚨）を増やすと、どれが致命的か判別できなくなる

## 影響

- **README を「初見の人が読む文書」として書き直す。**「最初のログイン方法」を必ず含める
- **`AGENTS.md` §5 のコマンドインデックスには、この型を当てない。**
  あれは索引であって手順書ではない（圧縮されていることに価値がある）
- v1 の SSO 設定ドキュメントは、この型で書く
- 🚨 **この型は「手順」にだけ当てる。** 決定ログ・調査結果・領域の総覧は対象外
