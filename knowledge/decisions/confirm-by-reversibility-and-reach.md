# 確認を出す基準は「戻せない」か「一度に多数へ及ぶ」

> 由来: 2026-08-17。toast が**画面から起こせる削除 13 件**を数え、
> **確認の有無が「戻せなさ」と対応していない**ことを実測で出した。
> 関連: [[action-button-and-edit-mode]]（破壊的な操作は ▾ の中）／[[every-element-must-earn-its-place]]

## 0. 決めたこと

**確認ダイアログを出すのは、次のどちらか 1 つでも当たるときだけ。両方外れるなら出さない。**

```
① 戻せない …… ゴミ箱に入らない（その表が `deleted_at` を持たない）
② 一度に多数へ及ぶ … 次の 3 つのどれか
   a. **選んでまとめて実行する**（選択を間違えていても、実行するまで気づけない）
   b. **物理削除で cascade が発火し、他の行も消える**（＝ 戻せない範囲が広がる）
   c. 🚨 **論理削除でも、他の多数の行から見え方が変わる**
      → **確認は出す。ただし危険色にはしない**（戻せるので）
```

🚨 **「戻せなさ」だけで決めない。** それが今回いちばん大事な訂正。

### 🚨 ①の判定も、列の有無ではなく「削除の実装」で決める（2026-08-17 追記）

**`deleted_at` の列が在っても、その削除が物理削除なら戻せない。**

```
🔴 toast は「戻せる 6」に `policy-permissions` を入れた（根拠: `directus_permissions` に列が在る）
🟢 【引いた】`lib/admin/permissions-api.ts:348`
   `db("directus_permissions").where({ id }).delete()` ＝ **物理削除**
   （列は 設問300 で足したが、**削除の経路はそれを使っていない**）
＝ 🚨 **`policy-permissions` は①（戻せない）。確認が要る**（いまは無い）
🟢 対照 同じ数え方で他の 3 系統を引くと **全部 論理**:
   files `lib/files/service.ts` … 論理 2 / 物理 0
   folders 同上 `:1223` … `softDelete.update({ deleted_at: db.fn.now() })`
   labels `lib/labels/service.ts:370` … 論理 1（**物理 2 は割り当ての側**）
＝ **数は 取り消せない 7 → 8 ／ 戻せる 6 → 5**
```

🚨 **この穴と、下の②bの穴は同じ形**——**スキーマは「できること」しか言わない。
実際に何が起きるかは、削除を書いている行にしか無い。**

### 🚨 ②b の判定を、スキーマだけで済ませない（**この決定を自分で当てて見つけた穴**）

**`ON DELETE CASCADE` が在っても、その削除が論理削除なら発火しない。**

```
🔴 私は最初、この決定の §2 で labels を「②に当たらない」と書いた。
   確かめに行くと `ohmycms_label_assignments.label → ohmycms_labels` は **CASCADE**
   （`20260815010000_create_labels_and_folder_color.ts:55`）
   ＝ 一瞬「②bに当たる。確認は要る」と読んだ。
🟢 さらに引くと `lib/labels/service.ts:370` は
   `update({ deleted_at: db.fn.now() })` ＝ **論理削除**。**CASCADE は発火しない**
   ＝ ②b では**ない**。当たるのは ②c（**見え方だけが多数から消える**）
```

🚨 **順番を固定する: ① スキーマの cascade を引く → ② その削除が物理か論理かを引く
→ ③ 手前で止めていないかを引く。**
**どれか 1 つでも飛ばすと間違える**（cascade を見ないと見落とし、論理削除を見ないと過剰に付け、
手前の門を見ないと「起きないこと」を警告してしまう）。

### 🚨 ③ 手前で止めていないかを引く（2026-08-17 追記・**3 回目の同じ形**）

**cascade が在り、物理削除で、実際に消える——3 つとも本当でも、結論が違うことがある。**

```
🔴 私は §2 に「roles の本文に **『この役割の割り当ても消えます』** と書く」と指定した
🟢 【toast が引いた】`lib/admin/permissions-api.ts:202-224` `deleteRole` は、消す前に数えている:
   `directus_users.role` に 1 人でも居る → **409 ROLE_IN_USE**
   `directus_access.role` に 1 行でも在る → **409 ROLE_HAS_ASSIGNMENTS**
   ＝ 🚨 **割り当てが在るロールは、そもそも削除が通らない**
   ＝ **消せるのは割り当てが 0 件のロールだけ。割り当ては 1 件も消えない**
＝ 🔴 **私の文面は「起きないこと」を警告する画面になっていた**
✅ 正しい本文は「**元に戻せません**」だけ。
   「割り当てが在ると削除できません」は**ダイアログではなく失敗時のエラー**の役目
   （辞書に既に在る: `errors.role_has_assignments`）
```

🚨 **①②③はすべて「できる」と「実際に起きる」の取り違え**である:
```
① スキーマだけ見た … cascade が**在る**（= できる）→ 発火**する**と読んだ
② 列だけ見た …… `deleted_at` が**在る**（= できる）→ 戻**せる**と読んだ
③ 手前を見なかった … 消**せる**（= できる）→ 消**える**と読んだ
```

## 1. なぜ 1 軸では足りないか

```
🔴 toast の実測（2026-08-17・HEAD e76ee1b）
   画面から起こせる削除 … 13 件（DELETE 11 ＋ form POST 2）
   取り消せない 7 … agents / policies / roles / users-policy /
                    trash(完全削除) / 表の削除 / 関連の削除
   🚨 そのうち確認が在るのは **1 件**（trash の完全削除）
   戻せる 6 …… file-detail / file-tile-menu / files-table(まとめて) /
                folder-grid / labels / policy-permissions
   🚨 そのうち確認が在るのは **2 件**（labels ／ files-table のまとめて削除）
＝ 🚨 **確認の有無が、戻せなさと対応していない**
```

**ここで「戻せるのに確認が在る 2 件は間違いだ」と読むと、直し方を誤る。**
`files-table` のまとめて削除は**ゴミ箱へ入るだけ＝戻せる**が、**一度に何件でも動く**。
危ないのは戻せなさではなく **件数**——**選択を間違えたことに、実行するまで気づけない**。

🚨 だから軸は 2 本。**①だけを基準にすると、この 1 件を「余分」として外してしまう。**

## 2. いまの状態を、2 軸で並べ直す

| | 判定 | いま | どうする |
|---|---|---|---|
| agents / policies / roles / users-policy / 表の削除 / 関連の削除 | ①に当たる | 確認**無し** | 🔴 **足す** |
| 🚨 policy-permissions | ①（**列は在るが物理削除**） | 確認**無し** | 🔴 **足す**（toast の分類を訂正） |
| roles | 🚨 **①のみ**（cascade は在るが、割り当てが在ると 409 で止まる） | 確認**無し** | 🔴 **足す。本文は「元に戻せません」だけ** |
| trash の完全削除 | ① | 確認在り（danger） | 🟢 そのまま |
| files-table のまとめて削除 | ② | 確認在り（既定色） | 🟢 そのまま |
| labels | 🚨 **②c**（論理削除だが、多数のファイルから見え方が消える） | 確認在り（既定色） | 🟢 **そのまま**（色も既定のまま） |
| file-detail / file-tile-menu / folder-grid | どちらも外れる（**論理削除を実装で確認済み**） | 確認無し | 🟢 そのまま |

🚨 **roles は「②に見えて②でない」例。** `directus_access.role` は **ON DELETE CASCADE** だが、
`deleteRole` が**手前で 409 を返す**ので発火しない（§0 の③）。
＝ **スキーマも、削除の行も、両方見て、さらに手前の門まで見て、はじめて判定できる。**

## 2.5 🚨 押すのが安い UI ほど、戻せないものを置かない（2026-08-17 追記）

**格子・チップ・トグルのように「1 クリックで切り替わる」形は、押すのが安い。
安い操作で、戻せないものを消してはいけない。**

```
由来: 権限の格子（行＝コレクション／列＝4 アクション）を設計していて気づいた。
   【引いた】権限の削除は **物理削除**（`lib/admin/permissions-api.ts:348` `.delete()`）
   ＝ 🚨 **マスを「条件つき → なし」に 1 回押すと、書いた行フィルタ JSON ごと消える**
   ＝ **格子が「フィルタを消す機械」になる**
```

🚨 **確認を出す／出さないを、同じ UI の中で分ける。**

```
すべて → なし …… 確認しない（**消える情報が無い**。作り直せば同じ状態）
条件つき → なし … **確認する**（①戻せない）＋ 🚨 **消えるものを本文に見せる**（その JSON）＋ danger
なし → すべて …… 確認しない（**足すだけ**）
```

🚨 **「危険な操作だから全部に確認」でも「格子だから全部無し」でもない。**
**同じマスでも、いまの値によって失うものが違う。** 判定は §0 の①②をマスごとに当てる。

## 3. 色は 1 軸（戻せるかだけ）

**`tone="danger"` にするのは①（戻せない）のときだけ。②だけで当たったものは既定の色。**

```
🚨 **警告色（`warning`）は作らない。** base2 が Directus で見た「削除＝危険 / アーカイブ＝警告」の
   2 段階は採らない。理由:
   ・この PJ に `warning` のトークンも variant も無い（＝ パレットに手を入れる別の判断）
   ・**②で当たったものを「警告色」で括ると、また「同じ顔で違う意味」になる**
     （まとめてゴミ箱へ入れる ＝ 戻せる。離脱の確認 ＝ 入力が消える。別の話）
🚨 実測（toast）… いま `variant="destructive"` は 3 件／`warning` は 0 件
```

## 4. 文面の型

```
題 …… 何が起きるかを 1 行（「完全に削除しますか」「ゴミ箱へ入れますか」）
本文 … ① **戻せるかを必ず書く**（「ゴミ箱から戻せます」／「元に戻せません」）
      ② **及ぶ範囲を書く**（「{count} 件」／🚨「この役割の割り当ても消えます」）
ボタン … 進める側は**その操作の動詞**（「削除する」「ゴミ箱へ入れる」）。
      🚨 **「OK」にしない**（何が起きるか、ボタンだけで分からなくなる）
やめる … `AlertDialogCancel` の既定（`common.action_cancel`）。**焦点はこちらに当てる**
```

🚨 **`window.confirm` を使わない。** ボタンが OS の言語で出るため
（`AGENTS.md` §3.8「全文言が自前の辞書にある」への違反。実コードは 2026-08-17 に 0 件へ）。

## 5. やらないこと

- ❌ 「戻せなさ」だけで確認の要不要を決める（**②を落とす**）
- ❌ 一括操作なのに確認を出さない（**選択の間違いに気づけない**）
- ❌ 戻せて 1 件ずつ・**他へ及ばない**操作に確認を出す（**押す回数が増えるだけ**）
- ❌ 🚨 **`ON DELETE CASCADE` を見ただけで②bと判定する**（**論理削除なら発火しない**）
- ❌ 🚨 **`deleted_at` の列が在るだけで「戻せる」と判定する**（**削除の実装が使っていないことがある**）
- ❌ 警告色を足す（**トークンごと足す判断は別**）
- ❌ cascade を画面のコードだけで判定する（**スキーマを引く**）

## 6. レビュー観点

- [ ] その操作は①（戻せない）か②（多数へ及ぶ）に当たるか。**両方外れるなら確認は出さない**
- [ ] ②の判定に **cascade を引いたか**（`ON DELETE CASCADE` の有無）
- [ ] 🚨 そのうえで **その削除が物理か論理かを引いたか**（論理なら cascade は発火しない）
- [ ] 🚨 ①の判定を **列の有無ではなく、削除を書いている行**で決めたか
- [ ] 本文に「戻せるか」と「及ぶ範囲」の 2 つが書いてあるか
- [ ] 進めるボタンが動詞になっているか（「OK」でないか）
- [ ] 色を①だけで決めているか（②で danger にしていないか）
