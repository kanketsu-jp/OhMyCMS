# 90 日の掃除は SQL が正本。TypeScript は薄い口で、ファイルだけが例外

## 決定

1. **正本は SQL 関数**（`ohmycms_purge_trash()`）。保持日数・対象表の導出・除外・走行の記録を、
   **すべてそこに 1 つだけ**置く。TypeScript（`lib/trash/purge.ts`）は**呼ぶだけ**。
2. **対象の一覧をコードに書かない。** `information_schema` から「`deleted_at` を持つ表」を実行時に引く。
3. **除外は「消してはいけない側」だけ**を、理由つきで SQL に書く。
4. **`directus_files` は例外**。SQL では実体を消せないので除外し、**TypeScript 側**で
   `deleteStoredObjects(id)` → 行、の順に消す。

関連: [[deleting-a-file-is-two-deletes]]（順番は「実体 → 行」）／
[[trash-and-restore-ui]]（ゴミ箱の画面）／[[soft-deleted-names-stay-taken]]（名前を空けない）

## なぜ SQL が正本か

掃除は **`pg_cron` が呼ぶ**。cron は TypeScript を呼べないので、規則を TS に置くと
**同じ規則が 2 箇所**になる（正本と写しが別々に腐る）。
＝ **1 箇所に書いて、2 つの口から呼ぶ**。TS 側の口は「アプリから手で走らせたいとき」用。

🚨 **走行の記録も SQL の中でやる。** 記録が TS 側に在ると、
**cron から走ったときだけ記録が残らない**（＝「まだ 1 度も走っていない」と同じ顔になる）。

🚨 **保持日数（90）も SQL が正本**（`ohmycms_trash_retention_days()`）。
画面の「あと何日」も `retention_days` もそこを読む。別々に持つと、
**掃除が消したあとも画面が「あと N 日」と言う**ずれ方をする。

## なぜ対象の一覧を書かないか

一覧をコードに書くと、**`deleted_at` を足した人が掃除の一覧を直し忘れたときに黙って掃除されない**。
実行時に引けば、**足し忘れが構造的に起きない**。

その代わり「**列は在るが消してはいけない表**」を分けられないので、除外リストが要る。3 つの条件:

1. **1 件ごとに理由を書く**（名前だけ並べない）
2. **空でも黙らない**（戻り値の `skipped` が毎回出る。**空の除外は「全部消す」**なので）
3. **除外に書いた表が実際に `deleted_at` を持つか**を毎回見て、`rotten_skips` として返す

🚨 最初は `directus_activity`（監査）を除外に入れたが**外した**。
【測った】その表は `deleted_at` を持たないので**対象候補に入らない**＝ 除外に書いても意味が無く、
**初日から条件 3 に当たっていた**。**将来のために名前を置くと、警告が鳴りっぱなしになって読まれなくなる。**

## ファイルだけが例外（storage の指摘・2026-08-16）

【測った】`deleted_at` を持つ表 **19 個**に `directus_files` が入っている。
**SQL からは storage（local FS / S3 / R2）に手が届かない**ので、
`ohmycms_trash_purge_skip()` に**理由つきで**入れ、ファイルは `purgeExpiredFiles()`（TS）が消す。

**なぜ除外するか**: 実体の場所は**行の中にしか無い**ので、**行を先に消すと辿れなくなる**。
🚨 **この一文はここに残す。** 消すと、理由の在り処が
**SQL の `reason` 文字列 1 行だけ**になる——**そこは決定ではなく実装なので、腐っても誰も気づけない**
（storage の指摘）。

🚨 **ただし「どう消すか」（順番・キーの在り処・孤児の検出）は
[[deleting-a-file-is-two-deletes]] に在る。ここには書き写さない**
——**2 箇所に書くと、片方だけ直って腐る**。

**「ファイルは掃除しない」ではなく「SQL では掃除できない」。**
🚨 **除外の理由に「なぜ SQL では書けないか」を書く。** 書かないと、次の人が調べ直す。

## 落ちたときは、例外を再送出しない（意図した形）

再送出すると**トランザクションごと巻き戻り、記録も消える**（＝ 黙って失敗する）。
**途中まで消した分は確定する**が、**何が起きたかは `error` に残る**ほうを採った。

### 🚨 ただし、最初の実装では「残る」が嘘だった（2026-08-16・反証）

`20260817040000` は**本体全体**を `begin … exception when others then … end` で囲んでいた。
plpgsql の例外ブロックは**暗黙のサブトランザクション**なので、例外が起きると
**そのブロックでやったことが全部巻き戻る**——**記録を作る `insert` も一緒に**。
ハンドラの `update` は**もう存在しない行**を狙うので 0 行更新。
＝ 🚨 **落ちると記録が 1 行も残らず、「まだ 1 度も走っていない」と同じ顔になっていた。**

🚨 **なぜ気づかなかったか。** 受入が「**例外が返るか**」までしか見ていなかった。
「**落ちたことを、あとから読めるか**」を足した瞬間に赤が出た。
＝ **返り値は見ていたが、残ったものを見ていなかった。**

直しは `20260817050000`（`insert` を例外ブロックの外へ出す）。
🚨 **共有 DB への適用はまだ**（2026-08-16 時点）。**それまでは、落ちても記録は残らない。**

## 🚨 消した数は、消えた数ではない（toast の指摘・2026-08-16）

`deleted` は**掃除自身の `delete` が消した行数**であって、**消えた行の総数ではない**。

【測った】90 日超のラベル 1 件＋その割り当て 1 件で掃除を呼ぶと、
**ラベルも割り当ても消える**（外部キーの ON DELETE CASCADE）のに、記録は
`{"ohmycms_labels": 1, "ohmycms_label_assignments": 0}` と書いた。

🚨 **数そのものは直していない。** 正しく数えるには前後で全表を数えるかトリガで拾うしかなく、
**どちらも掃除自体より重い**。→ `cascade_may_delete`（**その数の外側で消えうる表**）を結果に出す
（`20260817060000`）。＝ **数が嘘をつかないようにするのではなく、
数が何を数えていないかを一緒に出す。**

## 落ちたことを、人が読める場所へ出す

`lastPurgeRun()` を **認証済みの `GET /api/trash`** に `last_purge` として載せる。

🚨 **`/api/health` には載せない。**【測った】`app/api` の `route.ts` **65 本**のうち
`requireActor` を呼ぶのは **50 本**で、**health は 0**（＝ 認証不要）。
そのファイル自身が「詳細はログにだけ出す」と決めている——**運用状態を誰でも読める形にしない**。

🚨 `null`（まだ 1 度も走っていない）と `deleted_total: 0`（走って何も無かった）は**別のこと**。
その区別を API の形で保つ。**画面は design の担当。**

## 共有 DB での実測（2026-08-16）

使い捨ての DB で測れないもの（**本当に予定どおり動くか**）は、共有 DB で測った。

- `cron.job` … jobid 1 / `0 19 * * *` / active / db=cms。🚨 **`cron.timezone` は `GMT`** なので
  **04:00 JST は 19:00 と書く**（`04:00` と書くと 13:00 JST に走る）
- 🔴 **予定どおり走った** … 走行記録が 1 → 2 に増え、`started_at` が **04:00:00**
  （＝ 手で呼んだ分と区別が付く。**「予定が入った」と「予定が動く」は別**）
- 🔴 **わざと落として、記録に残ることを実測した**（使い捨ての表に、削除で必ず落ちるトリガを付けた）。
  `error` が走行記録に入り、件数も増えた。🟢 対照 直せば `error` は null に戻る。
  🚨 **本物の表は 1 つも壊していない。本物の行の削除も 0 件**
- 🚨 **関数を差し替えた後に、予定と除外を引き直した**（作り直すと中身が変わるため）

## 実測（2026-08-16・使い捨ての postgres）

受入は **pg_cron が呼ぶのと同じもの（SQL 関数）を直接呼ぶ**。
TS 経由で測っても、**薄い口を測っているだけ**で cron の振る舞いを見ていない。

- **OK 34 / NG 0**。走らせる前に「記録 0 件」／🔴 90 日超は消える／🟢 90 日以内は残る／
  🟢 論理削除でない行は残る／🔴 **あとから足した表も自動で対象**／
  🔴 `directus_files` の行は**消えない**（🟢 対照 **同じ走行で** zz の 90 日超は消える）／
  2 回目は 0 件でも**記録は 2 件**／除外の表を落とすと `rotten_skips` が鳴る
- 🟢 対照 **薄い口からも同じ形が返る**（口が 2 つとも生きている）
- 判定はすべて **id**。共有 DB のポート（5436）を渡すと exit 2 で止まる
- 🔴 落ちたら `error` が返り、**`lastPurgeRun` から読める**（🟢 対照 直せば `error` なし）
- 🔴 ラベルと割り当てで **CASCADE の取りこぼし**を再現（🟢 対照 ラベル自身は 1 と数える）
- 🔴 壊して赤も測った: 保持日数を 3650 へ／**除外の照合を外す**／**対象の導出を 1 表に固定**／
  **除外リストを空にする**／**`cascade_may_delete` を出さない版** の 5 通り。
  🟢 対照 壊さなければ 34/34 緑
  🚨 **1 回は「違う理由で赤」になった**（前の走行記録が残った台で回した）。**台を作り直して測り直した**
- up → down → up が 1:1（表 32 → 2 → 32）

## 🚨 まだ決まっていないもの

- 🚨 **`…050000` と `…060000` を共有 DB へ適用すること**（予告制・**まだ**）。
  それまでは **落ちても記録が残らない版**を cron が毎朝呼んでいる
- **`last_purge` を画面へ出すこと**（API までは在る。**画面は design**）
- **`ohmycms_label_assignments` を掃除してよいか**（対象候補 19 表のうちの 1 つ）。
  割り当ては「それ自体を消さない」設計なので、**toast の判断**。**まだ聞いていない**
- 🚨 **ファイルは、いま誰も消していない。**【引いた】`purgeExpiredFiles()` を呼ぶ場所は
  **0 本**（🟢 対照 同じ引き方で `runPurge` は **2 本**＝探し方は当たる。単位はファイル）。
  TS 側なので `pg_cron` からは呼べず、**口が在るだけで 1 度も通っていない**。
  🚨 **cron が回り始めると SQL の掃除だけが定期的に走る**ので、
  **「除外した」と「掃除されている」を同じ緑で語らせないこと**（司令塔の指摘）
- ~~**`cron.schedule` はまだ入れていない**（許可制）。`create extension pg_cron` も未実行で、
  **この postgres の image に pg_cron が在るかも確かめていない**~~
  🚨 **2026-08-16 に 3 つとも反転した**（storage の指摘で気づいた）。【測った】:
  pg_cron 拡張 **1**（🟢 対照 実在しない拡張 **0**）／ `cron.job` **1 件**（`0 19 * * *`・active）／
  走行記録 **5 件**（うち id2 は **04:00 に cron が動いた分**、id4 は **わざと落とした分**）。
  image は storage が作った（`docker/Dockerfile.pgcron`）。
  🚨 **「未実行」と書いたままにすると、次の人がもう 1 回入れようとする。**
