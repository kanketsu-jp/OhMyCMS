# アクションボタンは1つ。表示モードと編集モードを分ける

> 由来: 2026-08-15 堀池さん（原文）:
> 「**アクションボタンは一つのボタン＋右に「chevron-down」アイコン。これを押下すると
> オプションが表示される。一つのボタンはその時で変わる。編集中では「保存」など。
> `/admin/profile` などでは「名前を保存」としているが、それは廃止。
> アクションボタンで「編集する」を押下する。全てにおいて基本は編集モードと表示を分ける**」

## TL;DR

- **主ボタンは画面に 1 つだけ。** 右に `chevron-down` を付け、**押すとオプションが出る**
- **主ボタンはモードで変わる。** 表示中 →「編集する」／編集中 →「保存」
- **「〇〇を保存」のような固定文言は廃止。** モードで変わるので、名前を持たせない
- **既定は、表示モードと編集モードを分ける**
- 🚨 **例外を認めるかは未決**（§7）。**例外の節はそこだけに置いてある**

---

## 1. 形

```
[ 主ボタン ▾ ]     ← 1 つのまとまり。右端が chevron-down
   押す           → 主アクションが走る
   ▾ を押す       → オプションが開く
```

- 🚨 **`components/ui/button.tsx` の `Button` を使う。** 素の `<button>` にしない。
  理由: base が持つ `active:not-aria-[haspopup]:translate-y-px`（押すと 1px 沈む）を継承するため。
  素の要素だと**押した手応えが色だけになり、PC では出ない**
  （`tree-connector-lines.md` §4 の「Button でないなら active は hover と同じか、より濃く」）
- **置き場所は既存の枠をそのまま使う**（新しい枠を作らない）:
  ```
  PC  #header-primary-action   （ヘッダ右）
  SP  #mobile-primary-action   （下部ナビの 3 つ目）
  ```
  🚨 **PC と SP で別の枠**。片方だけ見て「主アクションが無い」と判断しないこと
  （2026-08-15 実測: SP で `#header-primary-action` は **DOM 上 2 本・見えている 0 本**、
  同時に `#mobile-primary-action` が **見えている 2 本**。片方だけ見て 0 と誤報した）

## 2. モードの境目

| | 表示モード | 編集モード |
|---|---|---|
| 入力欄 | **読めるが変えられない** | 変えられる |
| 主ボタン | **「編集する」** | **「保存」** |
| 抜け道 | — | **「やめる」**（§4） |

**境目の定義**: **保存されていない変更を持ちうるか**。
持ちうるなら編集モード、持ちえないなら表示モード。
🚨 **「設定画面だから」のような画面の種類で決めない。** その画面で何が起きるかで決める。

## 3. ▾ の中に入れるもの

```
✅ その画面で **たまにしか使わない** 操作
✅ 🚨 **破壊的な操作**（削除など）— 誤って押されないよう、必ず ▾ の中
❌ その画面の**主目的**（それは主ボタン）
```

- 堀池さん 2026-08-15（283 A）: **コレクション画面の「削除」は ▾ の中へ。主ボタンは別のもの**
- 🚨 **主ボタンが 2 つ並んでいる画面は、頻度で主を決める**
  （`ui-placement-by-frequency.md` と同じ判断軸）

**実測（2026-08-15・PC 25 ページ）: 主アクションが 2 本並ぶ画面は 2 枚**

| 画面 | 現状 | 決め方 |
|---|---|---|
| `/admin/files` | 「ファイルを追加」「フォルダを作る」 | 主＝**ファイルを追加**／▾＝フォルダを作る |
| `/admin/collections/<c>` | 「フィールド追加」「コレクション削除」 | 主＝**フィールド追加**／▾＝**削除**（283 A） |

🚨 **`/admin/files` の主を「ファイルを追加」にした根拠は推測です。**
**押された回数を測る仕組みが無い**（ログを取っていない）。
理由: フォルダは入れ物で、ファイルはその中身なので、中身を足す回数のほうが多いだろう、という推測。
**測れるようになったら差し替えること。**

## 4. 編集モードから抜ける道

🚨 **「やめる」を必ず置く。** 置き場所は **▾ の中ではなく、主ボタンの隣**。

理由: **抜け道を隠すと、変更を捨てたい人が保存してしまう**。
▾ を開かないと出てこないものは、**急いでいる人には無いのと同じ**。

## 5. 対象（実測）

**2026-08-15 実測: 「最初から編集できる」画面は 15 / 25 枚**（PC・見えていて disabled/readonly でない入力を持つ）

```
collections/new ／ collections/<c> ／ files/new ／ files/new-folder ／ files/<id> ／
labels ／ profile ／ settings/agents ／ settings/general ／ settings/policies ／
settings/policies/<id> ／ settings/roles ／ settings/sso ／ settings/storage ／ settings/users
🟢 対照 残り 10 枚は入力 0（一覧・詳細の表示だけ）＝ この数え方は「全部」を返していない
```

🚨 **＝ 表示モードを新設する対象が 15 枚（全体の 6 割）。**

**保存の効き方**: 15 枚のうち **「押した瞬間に効く」画面は 0 枚**。
```
実測: fetch / XHR を横取りして「送ろうとしたか」だけを見た（送信はしていない）
🟢 対照(+) フック自身が検出できることを確認（`__probe__` を 1 件記録）
→ 疑いのあった `settings/policies/<id>` も **0 件**（行ごとのボタンで編集する形だった）
```
＝ **全画面が「まとめて保存」**。モードの意味が画面ごとに変わることはない。

## 6. 廃止するもの

```
❌ 「名前を保存」のような **固定の文言**（`profile_name_save` 等）
   → 主ボタンはモードで変わるので、**画面ごとの名前を持たせない**
❌ 本文の中に置かれた保存ボタン
   実測（2026-08-15）: **2 箇所**（`/admin/labels`「作る」／`/admin/collections/<c>`「追加」）
   🚨 どちらも「一覧＋その場で足すフォーム」なので、
      **「編集する」ではなく「追加」が主アクション**になる型。単純に寄せられない
```

## 8. 🚨 この規約が当たらない場面

- **cva（`class-variance-authority`）の定義そのもの** — どの要素に付くかは**使う側**が決めるので、
  「Button か」の判定は定義側ではできない。**呼び出し側で判定する**
- **入力を持たない 10 枚** — 表示モードしか無いので、モードの分離が要らない
- **一覧＋その場で足すフォーム**（§6）— 主アクションが「編集する」にならない

## 9. レビュー観点

- [ ] 主ボタンは画面に 1 つか（2 つ並んでいないか）
- [ ] `Button` を使っているか（素の `<button>` で沈み込みを失っていないか）
- [ ] PC と SP の**両方の枠**で出ているか
- [ ] 主ボタンの文言がモードで変わるか（固定の「〇〇を保存」になっていないか）
- [ ] 破壊的な操作が ▾ の中に在るか
- [ ] 編集モードに**抜け道**が在るか（▾ の中に隠していないか）
- [ ] §7 が未決のままなら、**未決と書いてあるか**
