# 秘密の置き場所は「復元可能性」で決める（ハッシュ化できるものだけ GUI 可）

## 背景

オーナーの方針で「起動に必要な環境変数を最小にし、それ以外は GUI(オンボーディング/設定画面)で
設定する」ことになった。このとき **秘密(S3 のアクセスキー / Google OAuth のシークレット)も
GUI へ移すか** が論点になった。「鍵をコピペで設定できる方が親切」という理由で GUI 化したくなる。

## 決定

**秘密の置き場所は好みではなく「復元できる必要があるか」の一点で決める。**

| 種類 | 例 | 置き場所 |
|---|---|---|
| **照合するだけ**（一方向ハッシュにできる） | セットアップパスワード / 利用者のパスワード | **GUI 可**（DB に scrypt ハッシュで保存） |
| **平文が要る**（署名・認証・外部 API 呼び出し） | `S3_SECRET_ACCESS_KEY` / `GOOGLE_CLIENT_SECRET` | **環境変数のまま** |

理由: S3 へ署名するには**平文の鍵が要る**のでハッシュにできない。DB へ入れるなら平文か、
可逆暗号のどちらか。可逆暗号にするなら**その暗号鍵をどこに置くのか**が戻ってきて、結局
環境変数が要る。

🚨 **したがって GUI へ移しても環境変数は減らない**（鍵置き場が1本増える）。
そのうえ **DB という新しい漏洩面が足される**。差し引きで確実に悪化する。

## DB へ移すと新しく増える漏洩経路（実測ベース）

1. 🚨 **バックアップに写る。** 環境変数は `pg_dump` に写らないが、DB の値は**全ダンプに入る**。
   ダンプは本番より雑に扱われがち(コピー・共有・保管)なので、ここが一番効く。
2. 🚨 **応答の許可リストが「書き忘れると漏れる」形。** `lib/settings/service.ts` の `getSettings()` は
   手書きの許可リストで、`setup_password` は**誰かが覚えていたから**返却対象から外れている。
   秘密の列を足して返す型に1行書き忘れたらブラウザまで届く([[no-nested-surfaces]] と同じく
   「2箇所に書いたら片方が腐る」形)。
3. **接続テストのエラー文。** GUI で鍵を入れる設計には「接続テスト」が必ず付き、AWS SDK の
   例外文には**エンドポイント・バケット・アクセスキーID**が入る。例外をそのまま返すと漏れる。

## 具体例（このリポジトリ）

- `ohmycms_settings.setup_password` … **ハッシュ → GUI 可**。実際 scrypt ハッシュで保存済み。正しい。
- `S3_SECRET_ACCESS_KEY` / `GOOGLE_CLIENT_SECRET` … **平文が要る → 環境変数のまま**。
- `AUTH_SECRET` … そもそも**不要**（署名鍵は `setup-session.ts` が
  セットアップパスワードから派生させており、`AUTH_SECRET` はどこからも読まれない残骸）。

## どうしても GUI で秘密を扱うなら満たすべき条件

1. **書き込み専用**。GET で値を返さず、「設定済み / 未設定」だけ返す。
2. 手書きの許可リストに頼らない。秘密は**別テーブルへ分け、既定で返らない構造**にする
   (「書き忘れたら漏れる」を「書かないと出ない」へ反転させる)。
3. 保存は環境変数の鍵で暗号化する。🚨 **その時点で環境変数は減っていない**ことを明記する。
4. 接続テストの失敗は一般化した文言 + エラーコードのみ。SDK の例外文を出さない。
5. DB バックアップを「秘密を含むもの」として扱いを格上げする。

→ 1〜5 を全部満たせないなら、環境変数のままが安全。

## 「どこに保存しているか」は値を出さずに見せられる

`lib/settings/service.ts` の `sources`(項目ごとに `database` / `environment` / `default` を返す)が、
**値を出さず出所だけ見せる**仕組み。ストレージ設定画面はこれを流用し、保管先の種別・
エンドポイントのホスト名・バケット名・接続の成否(真偽値)だけを見せ、
アクセスキーは**存在の有無だけ**を出せばよい。

## 【2026-08-14 更新】この決定は反転した。S3/Google/SMTPの秘密もDB(GUI)で扱えるようにした

**この決定（環境変数のまま）は覆した。** オーナー指示（2026-08-14）:
「必要最低限以外のものは全て env 最小化・GUI/MCP でオンボ後に設定できるようにする」。

`lib/settings/secret-box.ts`（AES-256-GCM暗号化）と `lib/settings/service.ts` の
`getSecretSetting()` によって、S3アクセスキー・Google OAuthクライアントシークレット・
SMTPパスワードもDBに暗号化して保存し、GUI/MCPから設定できるようにした。
env はもう最初の1回だけ（または鍵の保管）に要るだけになった。

### 上の「満たすべき条件」5つの達成状況（正直な棚卸し）

1. **書き込み専用（GETで値を返さない）→ 達成。** `getSettings()` は秘密項目について
   `*_set: boolean` だけを返す。平文を返す `getSecretSetting()` はサーバ内部専用。
2. **秘密を別テーブルへ分け、既定で返らない構造にする → 未達。** オーナー判断
   （2026-08-14）で、既存の `ohmycms_settings` テーブルに同居させる方式をこのまま採用し、
   別テーブル化は先送りにした。`lib/settings/service.ts` の `SECRET_KEYS` という**手書きの
   許可リスト**で秘密項目を判定しているため、🚨 **将来、新しい秘密設定キーを足す人が
   この許可リストへの追記を忘れると、平文のままDBへ書かれ、`getSettings()` の一般の
   `resolve()` 経路を通ってレスポンスに出てしまうリスクが残っている。**
3. **保存は環境変数の鍵で暗号化する → 達成。** AES-256-GCM、鍵は `OHMYCMS_SECRET_KEY`
   （`lib/settings/secret-box.ts`）。🚨 **envはゼロにならない**（この鍵1本は環境変数に残る）。
4. **接続テストの失敗は一般化した文言のみ → 今回の作業で対処。** S3操作の例外が
   秘密（アクセスキーID等）を含んだままサーバログへ出ていた実際の漏れ経路を塞いだ
   （`lib/storage/s3.ts` の `toStorageError()` と `lib/schema/api.ts` の
   `errorResponse()` 最後の砦のログ縮小。`scripts/verify-secret-safe-logging.ts` で実測）。
5. **DBバックアップを「秘密を含む」扱いに格上げする → 未対応。** v2 のバックアップ設計時
   （`docs/design/api-abuse-lock-and-otel.md` と同様の設計メモ、または v2 実装時）に
   必ず扱うこと。DBダンプには暗号化済みの秘密が含まれるため、ダンプの保管・アクセス制御も
   「秘密を含むファイル」として扱う必要がある。

## 【2026-08-15 追記】反転には例外がある — ライセンス発行鍵は env のまま

🚨 **上の反転（「秘密も GUI(DB) へ」）を、すべての秘密に機械的に当てはめないこと。**
**ライセンスの発行鍵 `OHMYCMS_LICENSE_SIGNING_KEY` は環境変数のままにする**（司令塔が承認・2026-08-15）。

この追記が要る理由は、**反転の反転だから**。書かないと、次に読む人が
「env に秘密が残っているのは古い形だ」と判断して**善意で DB へ移してしまう**。

### 例外にする判断軸は 2 つ

1. 🚨 **反転の根拠は「利用者がオンボード後に設定する項目を GUI にする」ことだった。**
   S3 のアクセスキー・Google のクライアントシークレット・SMTP のパスワードは、
   **そのインスタンスの持ち主が自分で入れる値**。だから GUI が正しい。
   **ライセンスの発行鍵は利用者が設定しない**（利用者は検証しかしない。発行するのは売る側）。
   → **反転の対象に、そもそも入っていない。**

2. 🚨 **`pg_dump` 一つで、過去に売った全ライセンスを偽造できる。**
   この決定が元々挙げていた漏洩経路①「バックアップに写る」が、ここでは**最大の被害**に直結する。
   他の秘密は「そのインスタンスの資源が漏れる」で止まるが、発行鍵は
   **プロダクト全体の収益構造が壊れる**。被害の範囲が 1 インスタンスを超える。

### 一般化した言い方

> **秘密を DB へ移してよいかは「誰が設定するか」と「漏れたとき被害がどこまで及ぶか」で決める。**
> 設定するのが利用者本人で、被害がそのインスタンスに閉じるなら DB（GUI）でよい。
> **設定するのが提供者側で、被害が全利用者へ及ぶものは env に置く。**

詳細は `docs/design/license-keys.md` §7。
