# 開発サーバを外部へ公開しない（公開するのは本番ビルドだけ）

## 背景

オーナーから「同じ wifi のモバイルから見たい」「ngrok で見れるようにして」と言われ、
司令塔が **`:3102`（`bun run dev` の開発サーバ）** を ngrok で公開した。

🚨 **開発ビルドには `dev-login` が生きている。**

```
POST /api/auth/dev-login              → 200   任意のメールでセッションが作れる
POST /api/auth/dev-login?admin=true   → 200   🚨 誰でも管理者ポリシーを付与できる
```

**URL を知っていれば、パスワードもメールも不要で全データを読み書きできる状態**を
**約1時間8分**（18:33〜19:41）作った。基盤担当が見つけて報告し、司令塔が停止した。

### なぜ気づけなかったか

司令塔は**同じ日に何度も**「本番ビルドでは `NODE_ENV` が埋め込まれ、`dev-login` の分岐は
デッドコード削除されるので存在しない」と説明し、**それを安全の根拠にしていた**。

基盤担当の指摘:

> 「本番は安全」は正しくても、「**公開されているものが本番とは限らない**」が抜けていた。

さらに悪いことに、司令塔は `:3102` を案内するとき
**「dev-login が使えるので1タップで入れます」と利便性として説明していた**。
**便利さとして説明した性質が、そのまま穴だった。**

## 決定

> 基準日: 2026-08-13

**外部（LAN の外・トンネル・公開 IP）へ出してよいのは本番ビルドだけ。開発サーバは出さない。**

| 対象 | 外部公開 | 理由 |
|---|---|---|
| `bun run dev`（開発ビルド） | ❌ **禁止** | `dev-login` が生きている。`NODE_ENV != production` の分岐がすべて有効 |
| `docker compose up`（本番ビルド） | ⭕ 条件つき | `dev-login` はビルドごと消えている |
| 受入ハーネスの `studio-acc` | ❌ **禁止** | `ALLOW_DEV_LOGIN=true` で焼いてある |

### 本番ビルドを公開するときの条件

1. **セットアップ用パスワードを既定値のまま公開しない**（既定は開発用の弱い値）
2. **公開する前に、その URL で `dev-login` が 404 であることを実測する**
   （🚨 「本番ビルドだから無い」で済ませない。**実際に叩いて確かめる**）
3. **公開している間の記録を残す**（トンネルのアクセスログを取る。取れないなら
   「侵入の有無を確認できない」と最初から認識しておく）
4. **用が済んだら落とす**

## 理由

**開発ビルドは「開発者の手元にある」ことを前提に、意図的に鍵を外してある。**
その前提が崩れる場所（外部公開）へ持ち出すと、外した鍵がそのまま穴になる。

「便利だから」で公開すると、**便利さの正体が防御の欠如であること**を見落とす。

## 影響

- モバイルで確認したいときは **本番ビルド（`docker compose up`）を公開する**
- 本番ビルドはログイン手段が要るので、**セットアップ用の入口が先に必要**
  （→ [[shared-resources-are-exclusive]] とは別に、MVP ④ の実装が前提になる）
- 🚨 **ローカルの LAN 内（`192.168.x.x`）は別扱い**。ここは開発サーバでよい。
  禁じているのは**インターネットへ出すこと**

## 教訓

- 🚨 **同じ事実を「安全の根拠」と「便利さの説明」の両方に使っていたら、どちらかが間違っている。**
  今回は「dev-login が無い/ある」を、本番の安全性の根拠と dev の利便性の説明に同時に使っていた
- **公開する前に「これは何のビルドか」を実測する。** 起動したコマンドを覚えているだけでは足りない
- **アクセスログを取れない経路で公開しない。** 事後に「侵入されたか」を確かめられない

## 事後の確認（2026-08-13）

- `directus_users` 42件 — すべて受入ハーネス（`acc-*`）と各担当の検証用。**外部由来と分かるものは 0**
- `directus_collections` — **0件**
- 🚨 **ngrok のアクセスログは残っていない**（起動メッセージのみで終了）。
  **「侵入されなかった」とは言えない。「DB に痕跡が見当たらない」までしか言えない**

## 🚨 この決定が在るリポジトリに、この決定を可能にする設定が入った（2026-08-16）

```
09db7b6（12:56）… `apps/studio/next.config.ts` に
   allowedDevOrigins: ["kmdr-dev-2.ngrok.app"]
   コメント …「開発サーバを ngrok 越しに見るときだけ要る」
```

**ngrok を廃止した日に削除した**（このコミット）。

🚨 **決定を書いた人と、その決定を破る設定を入れた人は、同じでも起こる。**
**決定は、書いただけでは守られない。**

🚨 **見つかり方も残す**: 別の担当が「旧 URL の掃除」で `grep ngrok` を打ち、
**5 ファイル**が出た。そのうち 2 本は**この決定と事故の記録**（＝ **消してはいけない側**）で、
1 本が**この設定**（＝ **消すべき側**）だった。
**同じ語が、両側に付いていた。** 語で数えて一括で消していたら、経緯のほうが消えていた。

🚨 **`allowedDevOrigins` を足したくなったら、まずここを読むこと。**
Cloudflare Tunnel へ移っても同じ。**外へ出してよいのは本番ビルドだけ。**
（LAN 内 `192.168.x.x` は別扱い＝上記のとおり。）
