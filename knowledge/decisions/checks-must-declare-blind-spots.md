# 検査は「何を見ていないか」を言えて初めて検査になる

> 由来: 2026-08-14 の一晩。UI 監査・i18n 検査の両方で、**「違反なし」が嘘だった**ことが 4 回起きた。
> どれも検査が壊れていたのではなく、**検査が見ていない範囲があることを誰も言えていなかった**。

## 決定

**自動検査の「緑」を、条件抜きで報告しない。**

報告するときは必ず次の 3 つを添える。添えられないなら、それはまだ検査になっていない。

1. **どの対象を見たか**（ページ・ファイルの**一覧を実測で作る**。手で書いた一覧を信じない）
2. **どの状態で見たか**（閉じたまま／開いた状態、選ぶ前／選んだ後、ログイン前／後）
3. **何を見ていないか**（見られない種類のもの。例:「英語のリテラルは見ていない」）

## なぜ

**検査の緑は「安全である」ではなく「この検査が見た範囲で問題が出なかった」という意味しか持たない。**
範囲を言わずに緑を渡すと、受け取った側は前者だと解釈する。**そこが事故になる。**

「壊れた検査」は落ちるので気づける。**「範囲の狭い検査」は緑を出し続けるので気づけない。**
後者のほうが危険で、実際に本番相当の環境へ違反が残った。

## 実際に起きたこと（2026-08-14・4件）

| # | 見ていなかったもの | 症状 |
|---|---|---|
| 1 | **`className={cn(...)}` の中身** | `check-surface-nesting.mjs` が 50 箇所 / 16 ファイルを取りこぼし、面の入れ子が素通り |
| 2 | **`.ts` ファイル** | `check-i18n-hardcoded.mjs` が `.tsx` だけを見ており、route handler の**日本語の直書き 7 件**が素通り。画面にそのまま出ていた |
| 3 | **ファイルを選んだ後の状態** | UI 監査が `<input type="file">` に一度もファイルを載せておらず、選んだ瞬間に**面が3段**になる違反が隠れていた |
| 4 | **22 ページ中 15 ページ** | UI 監査の対象パスが手書きの 7 件だけだった。外れていた側に**本物の違反**（本文エディタの面2段）があった |

いずれも「**全部を見ている**」と口では言っていた。**一覧を実測で作っていなかった**のが共通点。

## 🚨 「見慣れた数字」は測っていないのと同じ

> 2026-08-15、一晩で**3回**同じ形を踏んだ:
> 1. **書体**: computed が `notoSansJP`（生成名）に変わったのに、検査は人が読む綴りしか知らず全ページで誤報
> 2. **区切りの重複**: PC の Surface は**カード**なので上下の辺が並ぶのは当たり前なのに、区切りとして数えた
> 3. **コミットの範囲**: 自分のコミットが「25 ファイル」と**自分で出力しておきながら見ていない**。
>    直前の別コミットが正当に 25 だったので、**見慣れた数字だったから確かめるのをやめた**
>    （結果、他ペインの機能 24 ファイルを自分のコミットに巻き込んだ）

**数字を出したら、期待値と突き合わせるまでが1つの動作。** 出しただけで読まないなら、測っていない。

- 🚨 **「前回もこの数だった」は根拠にならない。** 前回と今回で対象が同じである保証がない
- 🚨 **共有状態は、自分が触った部分だけ見ても分からない**（git の索引・DB・作業ツリー）。
  「自分のものが入っているか」ではなく「**自分のもの以外が入っていないか**」を見る
- コミット前は `git status --porcelain` を読む。`git add <path>` は**十分条件ではない**

## 🚨 「検査が赤い」と「自分が壊した」は別。**まずエラーのファイル名を読む**

> 2026-08-15、同じ形が**1日に3回**出た。3 人とも**自分の変更を疑ってから**ファイル名で気づいている。
>
> | 落ちたもの | 実際の原因 |
> |---|---|
> | `tsc` が `.next/dev/types/routes.d.ts` で落ちる | **生成物が書きかけで壊れていた**。`tsconfig.json` が `.next/dev/types/**/*.ts` を include している |
> | `tsc` が `lib/auth/saml/verify.ts` で落ちる | **他ペインが書いている最中**。再実行したら通った |
> | `check-shortcuts` が落ちてコミットできない | **他ペインが承認リストを更新する前**だった |

**共有ツリーでは、自分が触っていないものが自分の手元で赤くなる。**

- 🚨 **エラーのファイル名で切り分ける**:
  `apps/studio/lib/...` → 誰かのコード ／ **`.next/...` → 生成物。誰のコードでもない**
- 🚨 **生成物は `git status` にも `git diff` にも出ない。**
  **リポジトリを見ても原因が分からない**形なので、**コミットでは直らない**（再生成が要る）
- 🚨 **「戻したら直った」は原因の証明にならない。**
  実例（同日・design）: 自分の変更を stash したら `tsc` が通り「自分が原因」と読みかけたが、
  **もう一度入れて測ったら通った**。**戻している間に、相手も動いている。**
  → **A/B は 1 回では足りない。入れ直して再現するかまで見る。**

### 🚨 赤の分類は 4 つ。**4 つ目は「誰も壊していない」**

    ① 自分が壊した
    ② 他人が壊した（未コミットの編集・作業ツリーに置いた一時ファイル）
    ③ 検査そのものが壊れていた（探し方を間違えた・対象を 1 件も拾えていない）
    ④ 🚨 **誰も壊していない**（生成中・一時的）

**④ を ①② と混ぜると、居ない犯人を探すことになる。**
実例（同日）: 作業者が `tsc` の **exit 2** を報告 → 中身は `.next/dev/types/routes.d.ts` の
構文エラーで、**Next が生成中のファイルが千切れていた**。**同じコマンドを回したら exit 0。**

**`.next/...` で落ちたときの手順**（司令塔・2026-08-15）:

    もう一度回す
      → 直った   **一時的**（生成中だった）。**報告しない**
      → 直らない **まだ壊れている**。**消して入れ直す**（共有物なので、勝手にやらず司令塔へ）

🚨 **「一時的」と「止まった」を分ける手順を持たずに `.next` を消すと、
待てば直ったものを消したことになる**（司令塔が自分でそう申告している）。

🚨 **ただし「更新時刻が古い＝壊れている」ではない。** 実測（2026-08-15 20:19・design）:

    .next/dev/types/routes.d.ts の更新  19:59（**20 分前**）
    tsc                                 **exit 0**

**更新が止まっていても、中身が正しければ通る**（再生成が要るのは、
そのルートに触ったときだけ）。**分かれ目は時刻ではなく、もう一度回した結果そのもの。**
時刻は「なぜ直らないのか」を調べる材料であって、**判定には使えない**。

## 🚨 守りが見ている値と、実装が使う値は同じか

> 2026-08-15。環境変数を見て安全と判断する守りがあったが、**実装は DB を優先**していた。
> **守りが緑でも、実装は別の値で動く。**
>
> 同じ形を design も 2 件持っていた（実測して 1 件は直し、1 件は「見ていない」と書いた）:
>
> | 検査 | 見ている値 | 実装が使う値 | 結果 |
> |---|---|---|---|
> | 巡回の網羅 | ディスクの `page.tsx` | **ルーティング** | `_private/` を**巡回漏れと誤検出**（Next は URL にしない） |
> | 高さのトークン化 | class 文字列 | **計算後の高さ** | `style={{height:32}}` は**素通り** |

**「そのファイルに何と書いてあるか」と「動くときに何が使われるか」は、別の問い。**

- **検査を作ったら、実装がその値を本当に使っているかまで遡る**
- **ずれを塞げないなら、「見ていない」と検査自身に書く**。
  書かないと**緑の意味が過大に読まれる**（「この検査が緑＝高さは全部トークン経由」など）
- 🚨 **ずれには 2 方向ある**。**誤検出**（正しいものを違反と呼ぶ→検査が使われなくなる）と
  **取りこぼし**（緑が嘘になる）。**同じ日に両方出た。**

## 🚨 「その検査は赤を出せるのか」を確かめる

> 2026-08-15。「`bun run lint` は何も検査していない」という指摘を、私は
> **「314 ファイル見ている」と数えて否定した**。それでは足りない、と toast ペインが続けた:
> **全部が warning の設定なら、たくさん見ていても一度も止めない。**
> 実際に壊して確かめた結果:
>   未使用変数 + 未定義識別子 → `0 errors, 2 warnings` **exit 0**（止めない）
>   未定義の JSX 部品        → `1 error react/jsx-no-undef` **exit 1**（止める）
> → **error 級だけが止める。未使用変数ではコミットは止まらない。**

**「対象を見ているか」と「落ちるか」は別の問いで、後者を確かめないと門にならない。**
数だけ数えて「動いている」と言うのは、緑を条件抜きで報告するのと同じ形。

- 🚨 **`bunx <名前>` は、その名前がローカルに無いと npm から他人のパッケージを取ってくる。**
  `bunx lint` / `bunx build` / `bunx test` はいずれも実在する npm パッケージ。
  **リポジトリのスクリプトは `bun run <script>` で呼ぶ。**
  （toast ペインが実際に踏み、「測ったつもりで別のものを測っていた」）

## 🚨 「利用者が見ている画面」を測っているか

> 2026-08-15。監査は**英語の画面を測っていた**。headless Chrome の `Accept-Language` は既定で `en`
> なので、locale を固定しない限りそうなる。堀池さんが見ているのは日本語。
> **同じ意味でも文字幅が違う**（「設定」2文字 と "Settings" 8文字）ので、
> あふれ・タップ領域・書体の判定は**誰も使っていない画面についての数字**だった。
> 日本語に切り替えた途端、**本物の違反が2件**出た（うち1件は直したはずの再発）。

- **測る前に、利用者と同じ条件にする**（言語・ログイン状態・画面幅・データ）
- 🚨 **既定値は「開発者にとっての既定」であって「利用者の既定」ではない。**
  headless の言語、空のデータベース、管理者権限——どれも黙っていると開発者側に寄る

## 🚨 死角を「印字する」ことと、「落とす」ことは別

> 2026-08-15。この文書は「**0 件は探し方を併記して、異常なしか未検査かを区別する**」と定めている。
> **私（design）は、それを半分しか実装していなかった。**
>
>     audit-surface-depth.mjs:1080  log(`発見: … → 🚨 見つからず（検索: …）`)
>     :1084                          return { …, missing }
>     :1150                          discovery = await discoverDynamicPaths(cdp)  ← **以後どこでも使わない**
>     :1540                          process.exit(1)                              ← 違反の件数だけで決まる
>
> **探し方は印字されているのに、何も発見できなかった実行が exit 0 で通る。**
> 人が目で追えば気づくが、**CI と受入は終了コードしか見ない**。
> polish が指摘するまで、**誰も気づかなかった**（私自身がこの規律の作者なのに）。

**「書いてある」は「効いている」ではない。** 死角を宣言したら、**その宣言が終了コードに届いているか**を
必ず確かめる。届いていない宣言は、**読む人にだけ負担をかけて、機械には無視される**。

- 🚨 **警告は集計ブロックへ出す。** 途中のログ行は流れて誰も読まない。
  受入で読まれるのは**末尾の「対象: N 件 / 違反なし」の周辺**だけ
- **「測っていない」には理由を添える**（「行数 N < 21 のためページ送りは測っていない」）。
  理由が無いと、次の人が推測で埋める
- **落とすか警告に留めるかは選んでよい。** ただし**選んだことを書く**——
  落とさないと決めたなら「なぜ落とさないか」を同じ場所に残す
  （例: ページ送りで落とすと、DB の中身が少ないペイン全員が止まる）

## 🚨 標本が偏っていると、ルールが正しくても何も見つからない

> 同じ日。`/admin/content/[collection]` を**毎回「空のコレクション」で測っていた**。
> 発見の実装が `uniqueHrefs.find(...)`＝**最初に一致した href** を採るため、
> 0 行のコレクションが先に当たっていた。
> 一覧は**行ごとに `<Button>` を描く**ので、**0 行なら壊れていても 200 が返る**。
> 結果、**本番が落ちる不具合が誰にも見えないまま残った**。

**「ルールが正しいか」と「その標本で発火しうるか」は別の問い。**
検査対象を自動で選ぶなら、**選ばれた標本が、その欠陥を出せる形かどうか**まで見る。

- **境界を含む標本を選ぶ**（0 件 / 1 件以上 / ページ送りが起きる件数）
- **標本が要件を満たさないなら、緑ではなく「測れなかった」にする**
- 🚨 **常設の標本を1つ決めて、消さない。** 実例: 行のあるコレクションが共有 DB から
  一度消え、**この形の 500 が誰にも再現できない時間帯**があった（`zz_probe_actions` を常設にした）
- 消す前の手順と、常設の一覧は [permanent-fixtures-are-not-junk](./permanent-fixtures-are-not-junk.md) にある。

## 🚨 「0 件」は、合格とは限らない

> 同じ日。locale の cookie を無条件に置いたら `file://`（対照ファイル）で
> **検査そのものが落ち**、出力は「**0 件**」になった。**一瞬「合格」と読みかけた。**

**落ちた実行の 0 と、正常な実行の 0 は、見なければ区別できない。**
- 🚨 **陽性対照が黙ったら、まず検査の故障を疑う**（実装が直ったのではなく、測れていない）
- 「問題なし」としか言えない検査は、**自分が壊れたことを教えられない**
- 数の前に**終了コードと標準エラー**を見る

### 🚨 0 は 2 種類ではなく **3 種類**ある（2026-08-15 追加）

ここまで「**異常が無い 0**」と「**見ていない 0**」の 2 つを区別してきたが、**3 つ目があった**。

| 0 の種類 | 意味 | 見分け方 |
|---|---|---|
| 異常が無い 0 | 対象を見た。違反も無かった | 対象件数を併記する |
| **見ていない 0** | 対象が拾えていない（glob 誤り・未実行・落ちた） | **0 件ガード**で落とす |
| **まだ出番が来ていない 0** | 対象は見ていて異常も無いが、**その規則が要る場面がまだ出ていない** | **その規則が例外・救済である**かどうか |

由来: 例外表の内訳を出したら 3 行が **0 件**で、「**一度も効いていません**」と報告された。
これは「死んでいる」と読める書き方だった。実際は候補 133 件に対象が含まれており
（`components/ui/dialog.tsx` も候補内）、**例外は「違反になりかけたもの」にしか効かない**ので
0 が正常だった。

🚨 **例外・救済・フォールバックの 0 を「不要」と読んで消すと、次に候補が出たとき正解が違反として落ちる**
（憲章 §1「正解を違反と言う検査は使われなくなる」）。
**消す前に「対象は見ているか」を測る。** 見ているなら、**その 0 は消す理由にならない。**

出力にはそう書く: `0 件 <規則名>（この例外が要る場面がまだ出ていない。対象は見ている）`

## 🚨 直した直後の緑は、「自分の見立てが正しかった」証拠にならない

> 2026-08-15。SP でパンくずが幅 0 に潰れる不具合で、仕様に
> **「原因は Breadcrumbs に `flex-1` が無いこと」**と書いて渡した。
> 作業者は指示どおり `flex-1` を足し、**加えて別のファイルも直し**、結果は緑になった。
> **見立てが当たったように見えた。** 1 変更ずつ戻して測ったら、そうではなかった:
>
> | 状態 | 幅 0 の件数 |
> |---|---|
> | 両方とも修正前 | 4 |
> | **`flex-1` だけ** | **4（1 件も減っていない）** |
> | もう一方だけ | **0** |
> | 両方 | 0 |
>
> 真因は「PC 用のボタンが SP でも描かれ、パンくずの幅を先に取っていた」ことだった。
> **分離しなければ、効かない変更を「効いた修正」として記録に残していた。**

**変更が 2 つ以上入ったら、「直った」は「どちらが直したか」を答えていない。**

- 🚨 **原因の見立ては仕様に書いてよい。ただし書いた時点で、それは検証すべき仮説になる。**
  作業者は仮説を疑わない（指示だから従う）ので、**疑うのは渡した側の仕事**
- **1 つずつ戻して測る。** `git checkout -- <path>` で戻す → 測る → 戻す、を変更の数だけ
- 🚨 **効かなかった変更は落とす。** 残すと「これが効いている」という誤った記録になり、
  次の人が触れなくなる（[[every-element-must-earn-its-place]] と同じ理由）
- **見立てが外れていたことは、直った報告と同じ場所に書く。** 当たった前提で次の設計が積まれる

## 🚨 「禁止」は書いただけでは守られたことにならない

> 同じ日。委譲の仕様に「**コミットしない**（こちらが検証してから行う）」と明記したが、
> 作業者はコミットしていた。中身は正しく、他人のファイルも巻き込んでいなかったが、
> **こちらが測る前に HEAD へ入っていた**。

**禁止を書くことと、守られたかを確かめることは別の動作。**
帰責は指示側にある（禁止を書いただけで、確認の手順を持っていなかった）。

- 委譲から戻ったら、**検証に入る前に `git log --oneline -1` と `git status --porcelain` を見る**
- 🚨 **境界を狭く切りすぎると、作業者は正解のファイルに触れない。**
  同じ件で「触ってよいのは A だけ」と切ったが、真因は B にあった。
  作業者が B を直したのは**正しい判断**で、境界の方が誤っていた。
  → 触ってよい範囲は「**原因がそこにあると確信できる範囲**」で切る。
  確信が無いなら、**禁止するのは壊してはいけないものだけ**にする

## 🚨 コードの無いコメントは、両方無いより悪い

> 同じ日。`/login` の 44px 対応が戻されていたが、**なぜそうしたかのコメントだけが残っていた**。
> 読むと「対処済み」に見えるので、**次の人は確かめない**。

**説明だけが残った箇所は、直っていない箇所より見つかりにくい。**
実装を戻すなら、その理由のコメントも一緒に消すか、「戻した経緯」に書き換える。

## 🚨 記録の「いつ・誰が」を `git blame` で確かめない（整形した人が決定者になる）

由来: 2026-08-15。例外表の 6 行に「決定/日付/担当」を後から足した人が、

確かめようとして `git blame` を引いたら、**2026-08-15（その人自身のコミット）**と出た。

```

git log -S → その文字列が **最初に入ったコミット**（＝ dabd7da・2026-08-13）
```

`decided:` を足したことで行が書き換わり、blame がその人へ移っていただけ。

**アンチパターン**
- ❌ 記録の日付を blame で検証して「食い違っている」と報告する
- ❌ 逆に、blame が自分を指すのを見て「自分が決めたことになっている」と直してしまう
  （**正しい記録を、間違った道具で壊す**）

**レビュー観点**
- [ ] 「いつ決まったか」を引くのに `git log -S` を使ったか（blame で済ませていないか）
- [ ] その行が後から整形・追記されていないか（されていれば blame は使えない）

## 併せて守ること

- **対象の一覧はコマンドで作る。** 例: `find 'app/(admin)' -name page.tsx`。
- 🚨 **その一覧に「画面でないもの」が混ざっていないか見る。**
  実測 2026-08-16: `page.tsx` 29 本のうち **2 本は `redirect` するだけ**（`admin/` と `admin/folders/`）。
  **分母を 29 と書くと、2 枚ぶん薄まる。**
  手で書いた一覧は、ページが増えたその日から嘘になる
- **一覧に入れられないもの（動的な id が要るページ等）は、その旨をコードのコメントに書く。**
  「入れられなかった」を黙っていると「入れ忘れ」と区別がつかない
- **状態を作る手段を検査に持たせる。** 開く（`--click`）・ファイルを載せる（`--file`）が無ければ、
  その状態については**何も言っていない**
- 🚨 **誤検出を消したら、必ず陽性対照を当て直す。** 例外を足すたび検査は鈍る。
  鈍っていないことを毎回確かめる（実際、誤検出を直す過程で**新しい誤検出を自分で作り込んだ**）
- 🚨 **違反を上げる前に「実装側が正しい可能性」を1回潰す。**
  正しい実装を違反と呼ぶと、検査そのものが使われなくなる。
  一晩で 7 件の誤検出を出し、うち 1 件は**訂正が間に合わず、誤った修正依頼を出してしまった**
- **検査を広げるときは、広げた直後にわざと壊した入力を通して赤が出るか見る。**
  広げただけで満足すると、広げた範囲を実は見ていないことがある
- 🚨 **間違いの向きが、被害の見え方を変える。訂正するときは向きまで見る。**
  実例（2026-08-16）: トーストの上限について「**4 件目以降が見えない**」と書いた。
  実装は `[...toasts, item].slice(-3)` なので、**溢れるのは古いほう**——20 件消したら
  **1〜17 件目が誰にも届かない**。**逆の向きに書くと「後半が見えないだけなら
  大したことない」と読めてしまい、影響の大きいほうを小さく見せる。**
  → **数が合っていても向きが逆なら、判断は逆に倒れる。**
- 🚨 **「無い」と結論するとき、その根拠を *名前* で採っていないか。**
  実例（2026-08-16）: `apiMessage()` の呼び出しが **0 件**なのを根拠に
  「生文言は画面に出ない」と結論した。**同じ振る舞いが `messageFrom()` という
  別名で 12 ファイルに在った。** 呼び出し 0 件という数字自体は正しかった。
  → **正しい数字の上に、誤った結論が建つ。** 数を検算しても気づけない。
  **「無い」の根拠が識別子1つなら、振る舞いで採り直す。**
  → 関連: [[i18n-check-scope-is-what-reaches-the-screen]]（この事故そのもの）
- 🚨 **「入れた」でも「効くと測った」でもなく、「その分岐が実際に通ったのを見た」まで数える。**
  由来: 2026-08-16 司令塔。検査の作り方が 6 段になった最後の 1 つ。
  ```
  ① 囮を置く ② RED/GREEN ③ 1 対 1 ④ 見逃す入力を作って通す（対照が死んだら落とす）
  ⑤ 記述が古くなったら鳴る（できないなら理由を書く） 🚨 ⑥ **足した分岐が通ったのを見る**
  ```
  🚨 **死んだ条件は出力に出ない**（`undefined === 0` は永久に false）。
  ①逃げ道（`or`）と ②文字のまま出る は出力に出るが、③死んだ条件は**何も起きない**。
  **出力を眺めても気づけない。その分岐が通る条件を作って走らせるしかない。**

  **【測った】2026-08-16・自分が今日足した分岐を数えた**（3 本の検査・11 分岐）:
  ```
  最初に通していたのは 7 / 11。**通していない 4 つを、1 つずつ通した**
  🚨 そのうち 1 つ（比率の下限）は、素直に壊すと **床が先に鳴って**条件にならなかった
     → 列挙が **50〜117** に収まる範囲（`app/` だけ = 107）を探して、
       **比率の下限だけが効く条件**を作った（床 50 は超え・平均 2,071 は下限超え）
  ```
  🚨 **「守りが 3 つ在るなら、RED も 3 通り要る」**——1 つの壊し方では 1 つしか測れない。
- 🚨 **守りは 3 つの壊れ方に対応する。1 つでは足りない。**
  ```
  🚨 比率（走査 ÷ 候補）… **形が変わる**（範囲が広がる / 判定が狭まる）
  🚨 平均（文字数 ÷ 本数）… **本数はそのままで痩せる**（読み込みが壊れる）
  🚨 床（実測値から遠い絶対値）… **丸ごと減る**（走査が途中で止まる）
  ```
  実例（2026-08-16）: 比率と平均だけのとき、**候補 394→64 / 列挙 214→41（8 割が消えた）**でも
  比率 0.641（許容内）・平均 4,886（下限超え）で **exit 0** だった。
  🚨 **分子と分母が一緒に減ると、比率も平均も動かない。**
  そして「絶対値は腐る」は正確には **実測値に近い絶対値**の話。
  214 に対する 150 は腐りやすく、**50 は腐らない**（下回ることを想定しない値だから）。
- 🚨 **他人の検査を測るとき、部品だけ取り出さない。取り出したなら、そう書く。**
  実例（2026-08-16）: `check-surface-nesting` の見逃す形を出すのに、
  **`SURFACE_PATTERNS` の正規表現だけを抜き出して**文字列に当て、「`cn()` は見逃す」と報告した。
  🚨 **実際は拾えていた。** `scanLine` が `className=` 以降の**リテラルを全部連結**してから
  判定するため。**しかもその連結は、私自身の指摘で入ったものだった**（自分が入れた守りを忘れた）。
  ```
  ❌ 部品（正規表現・1 つの関数）を取り出して測り、**検査の結論として書く**
  ✅ **入口の関数を、本物の引数で呼ぶ**
  ✅ どうしても部品だけなら 🚨 **「◯◯だけ測った。全体は未実施」と書く**
  ```
  🚨 **同じ日、toast は同じ状況で「正規表現だけ測った／検査全体は未実施」と明示して渡した。**
  **私は明示せずに断定した。差はそれだけで、結果は「相手が実測して止める」になった。**
  **両方向に外していた**（`cn()` は拾えるのに「見逃す」、
  「変数に入れる」は**別行なら見逃す**のに「拾う」と書いた）。
- 🚨 **関数を呼ぶときは、引数の数と戻り値の形を先に読む。**
  同じ日の続き: `scanLine(file, line, n)` を **1 引数**で呼び、戻り値のオブジェクトを
  truthy 判定した → **全部「拾う」**。
  🟢 **対照(-)（面でないクラス）まで「拾う」と出たので気づけた。**
  **対照が無ければ「全部拾える。私の報告は全部誤り」と、逆向きに誤報していた。**
- 🚨 **「いつも過検出だった」は、安全側に倒れている証拠にならない。**
  **取りこぼしは出てこないので、数えられない。**
  実例（2026-08-16）: 私の検出は 3 回続けて過検出だった（12→2 / 4→1 / 9 件とも誤検出）。
  **「だから安全側だ」と書きかけた。** 司令塔の指摘:
  「**3 回続けて過検出だったことと、道具が安全側に倒れていることは、別の主張です**」。
  ```
  ✅ **取りこぼしは「実演」できる。** 検出器が拾うべきものを**自分で作って通す**
  ```
  **やってみた**（見出しの評価語を探す検出器に、選択肢を方向づける見出しを 6 通り与えた）:
  ```
  🚨 見逃す 「B は手間がかかる」「A のほうが素直」「C は現実的ではない」
            「B を選ぶと苦しくなる」「A が自然」「C は重い」  … **6/6 取りこぼし**
  🟢 対照(+) 「B は危ない」→ 拾う（＝ 検出器自体は動いている）
  ```
  🚨 **＝ 私の検出器は、語彙のリストでしか見ていない。方向を持つ言い方は無限に在る。**
  **全 123 見出しを目で読んで取りこぼしは見つからなかったが、それは「無い」ではなく
  「私の目でも見つからなかった」。** 実演のほうが、目より確実に限界を示せる。
- 🚨 **「オブジェクトが在る」を「中身が在る」と読まない。空のコレクションは truthy。**
  実例（2026-08-16）: 配信 CSS を歩く walk を
  `if (r.cssRules) { walk(r.cssRules); continue }` と書いた。
  **空の `CSSRuleList` も truthy** なので、ネストを持たない `CSSStyleRule` が全部
  `continue` で飛び、**1169 件在るのに 0 件**と出た。
  → 「そういうプロパティは無い」と読みかけた。**`&& r.cssRules.length` が要る。**
  🟢 気づけたのは**対照を 2 つ置いたから**（`.flex` が引けること／在るはずのないクラスが 0 件）。
  **対照が無ければ、この 0 は「無い」として外へ出ていた。**
- 🚨 **門に載っている検査を書き換える間、共有の作業ツリーに「整合しない中間状態」を置かない。**
  実例（2026-08-16）: `scan()` の戻り値を `counts` → `{counts, 除外, 生の行}` へ変える作業を
  **2 手に分けた**。1 手目（本体だけ新形）と 2 手目（囮を `.counts` に直す）の**間**、
  `Object.keys(scan(...))` が常に 3 を返すので **囮2 が 4 通りとも誤検出 → 自己検査が落ちて exit 1**。
  **別のペインがその窓で走らせ、全員のコミットが止まった。**
  🚨 **自分の手元では一瞬でも、共有ツリーでは誰かがその瞬間に走らせる。**
  **門に載せた直後ほど、巻き込む範囲が広い。**
  ```
  ✅ 門に載っているファイルは **1 手で書き換える**（複数回の編集に分けない）
  ✅ 分かれるなら **別の worktree で作って、完成品だけを置く**
  🚨 **「本体を壊して → 測って → 戻す」という検証も、戻すまでずっと窓**
     （私は今日この手法を 4 回使った。**窓を作りながら「窓を作るな」を書いていた**）
     → 検証も `git worktree add --detach` で切った台の上でやる
  ```
  **再現も worktree でやった**（共有ツリーに 2 度目の窓を作らないため）。
  🟢 対照: 切った直後の台がそのままで緑であることを先に確認 → 囮の `.counts` だけ外したら
  **報告された症状と 4 つの名前まで一致**した（＝【推測】を【測った】に変えられた）。
- 🚨 **`root:` を書いた lefthook の検査は「毎回走る」ではない**（2026-08-16 実測）。
  staged が `root` の外だけなら **`glob:` が無くても (skip) で緑**。
  → **「コミットが緑だった」は、触った場所によって意味が変わる。**
  **何が走ったかを出力で見る**か `--all-files` で確かめる
