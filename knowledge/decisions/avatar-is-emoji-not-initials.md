## 決定

利用者のアバターは **SSO のプロフィール画像 → 利用者が選んだ絵文字 → 既定の絵文字** の順で出す。
**メールアドレスから頭文字を作らない。**

> 🚨 **2026-08-17 追記: 上の「順で出す」は、設問 315 A で「利用者が切り替えられる」へ変わった。**
> **下の §「315 で変わったこと」を読むこと。** 元の文は消していない（**反転した経緯を残すため**）。
> **変わっていないのは「メールから頭文字を作らない」の部分だけ。**

## なぜ

堀池さん（`.temp/2026-08-13/idea.md` L36・原文）:
> 「ユーザーのアイコンは絵文字にして。もちろん Google などの SSO を使う場合はそのプロフィール画像にする」

🚨 **直す前は、アバターがメールアドレスの1文字目を出していた**
（`components/admin/user-menu.tsx` の `label.slice(0, 1).toUpperCase()`。`label` は `userLabel`＝メール）。
**メールを画面に出さないための仕組みが別にあるのに、頭文字という形で漏れていた。**
絵文字にする作業の半分は、この静かな経路を消すことだった。

## どう作ったか

| 置き場所 | 理由 |
|---|---|
| `directus_users.avatar_emoji`（**varchar(32)**・nullable） | 利用者ごとの値なので利用者の行に持つ |
| 一覧は `lib/admin/avatar-emojis.ts` の**1本だけ** | 画面と API が同じものを見る。**画面で絞ってサーバが何でも受ける形にしない**（`AGENTS.md` §3.5） |
| 既定の絵文字は `lib/admin/user-label.ts` の定数 | 🚨 **辞書に入れない**。記号は言語で変わらない（`components/admin/shortcuts.ts` の `MOD_SYMBOL` と同じ理由） |

🚨 **列の長さを 1〜4 にしないこと。** 絵文字は肌の色や ZWJ の合成で**複数コードポイント**になる。
実測: `👩‍💻` は `1f469 / 200d / 1f4bb` の **3 つ**。短い列にすると**保存はできたのに文字が壊れる**。
一覧には合成絵文字を意図的に4個入れてある（`🧑‍💻` `👩‍💻` `👨‍🍳` `🐻‍❄️`）——**短くされたら壊れると分かるように**。

## やらないと決めたこと

- **頭文字を作る仕組みを新設しない。** 絵文字にする以上、要らない。
  参考にした別プロジェクトは `avatar-initials.ts` でメールの1文字目を見ており、
  先方自身が「**2本目の静かなメール経路だった**」と認めている
- **「既定に戻す」ボタンを作らない。** 既定の 🙂 が一覧に入っているので、**同じことが1タップでできる**
  （`every-element-must-earn-its-place`）
- **選択中を塗らない。** `✓` で示す（塗ると面が1段増える。憲章 §3b）

## 🚨 内部の管理者にも変えさせる

`local-admin@localhost` を「画面に出さない」からといって、**変更を拒否しない**。
2026-08-15 に `PATCH /api/auth/me` へ `LOCAL_ADMIN_EMAIL` の拒否を入れ、
**本番で堀池さんがアイコンを変えられなくなった**（`40d9eb3` で外した）。

**画面に出さないのはメールアドレスという文字列だけ**で、**その人は実在して、実際に操作している**。
表示の規律を、権利を奪う根拠にしない。

## 315 で変わったこと（2026-08-17）

**設問 315「Google の写真と絵文字を切り替えられるようにするか」→ 堀池さん回答 **A: 切り替えられるようにする**。**
備考（原文）:
> 「**ssoの場合デフォルトはそのアカウントの画像だが未設定とわかる場合ランダムに。**」

つまり **2 つ**変わる:

1. **固定の優先順位をやめる。** いまは画像が常に勝つ（`displayUserPicture` が非 null なら画像）。
   これを **利用者が選べる**ようにする。
2. **SSO で画像が「未設定」と分かるときは、既定を 🙂 でなく**ランダム**にする。**

### 🚨 実装の前に測った制約（auth・2026-08-17。**推測ではない**）

| 測ったこと | 結果 |
|---|---|
| 画像はどこに入るか | 専用の列ではなく **`directus_users.auth_data`（JSON）の `picture`**。書くのは `lib/auth/sessions.ts:43`（更新）と `:63`（新規）、読むのは `lib/auth/context.ts:124` の `authDataPicture()` |
| 来なかったとき何が入るか | **`null`**（`lib/auth/google.ts:129` … `typeof payload.picture === "string" ? payload.picture : null`）。🚨 **既定の URL を代わりに入れる処理は無い** |
| **切り替えの保存先** | 🚨 **無い**（🟢 対照: 出鱈目な列名で同じ探し方 → 0 件。＝ **「見ていない 0」ではない**）。いまは表示側の固定の優先順位だけ |

### 🚨 「未設定とわかる場合」は、認証の種類で結論が割れる

```
SAML …… 🟢 **必ず判定できる**
   `SamlIdentity` 型に**画像の欄が無い**（`verify.ts:26-33` … nameId / email / firstName / lastName / groups）
   `auth_data` に書くのも `groups` だけ（`:254` / `:305`）
   ＝ **SAML で入った人の `picture` は常に null** ＝ **未設定と確実に分かる**
Google … 🚨 **コードからは判定できない**
   Google が `picture` を**送らなければ** null になり判定できるが、
   **既定のアバターの URL を送ってきたら、その URL がそのまま入る**
   ＝ **「本人が設定した画像」と「Google の既定画像」が、うちからは同じ顔で見える**
   🚨 **URL を見て既定かどうかを判定する処理は 1 つも無い**
```

🚨 **どちらなのかは、本物の Google SSO を通さないと分からない**（design も「測れていない」と申告した点）。
**推測で「Google も判定できる」と書かないこと。**

### 実装するときに要るもの（**未着手**）

1. **切り替えの保存先**（利用者ごと。`avatar_emoji` と同じく `directus_users` の列が素直）
2. **ランダムの母集合**は `lib/admin/avatar-emojis.ts` の一覧を使う（**画面と API が同じものを見る**・上の表と同じ理由）
3. 🚨 **ランダムは「毎回変わる」ではなく「一度決めたら固定」**にすること。
   毎回変えると、**同じ人が画面ごとに違う顔になる**（利用者は自分を見失う）
4. 🚨 **Google の「未設定」を判定できないまま、Google の人にランダムを当てない。**
   当てると **本人が設定した画像を上書きする**。SAML の人だけに当てるか、堀池さんへ問い直す
