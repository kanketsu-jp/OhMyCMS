# UI の置き場所は「操作の頻度」で決める

## 背景

管理画面のヘッダに「日本語 / English」の切替ボタンが常設されていた。
これをボタングループにするか、ドロップダウンにするか、という話から出た判断。

> 堀池（2026-08-13）:
> 「**そもそも言語設定は頻繁に変えるものではないので、オンボーディングで選択させて、
> 以降は個人設定で変更させる。**」

## 決定

> 基準日: 2026-08-13

**画面の常設領域（ヘッダ・サイドバー・ツールバー）へ置いてよいのは、頻繁に使うものだけ。**

| 頻度 | 置き場所 |
|---|---|
| 毎日・何度も使う | **常設**（ヘッダ / サイドバー / ツールバー） |
| ときどき使う | 1 階層下（メニューの中・ページ内） |
| **一度決めたらほぼ変えない** | **オンボーディングで一度選ばせ、以降は個人設定** |

**言語設定はいちばん下の段**に当たる。したがって:

- 初回ログイン時のオンボーディングで選ばせる
- 以降の変更は**個人設定の画面**から
- **ヘッダに常設しない**

## 理由

1. **常設領域は有限で、しかも一番目立つ。** そこを「ほぼ押さない要素」が占めると、
   毎日使う操作が押しにくくなる。とくにモバイルでは致命的。
2. **選択肢が増えると常設は破綻する。** 言語は将来さらに増える予定なので、
   ボタンを並べる形は最初から詰んでいる。
3. **「変えられる」ことを常時見せる必要がない。** 一度決めたものは、
   変えたくなったときに探せれば足りる。

## 影響

- ヘッダから言語切替を外す
- **オンボーディング（初回ログイン時の1回きりの画面）が要る。** ここで言語を選ばせる
- **個人設定の画面が要る。** 言語のほか、将来の個人向け設定はここへ集める
- 既定の言語は環境変数（`OHMYCMS_DEFAULT_LOCALE`）→ 全体設定（DB）→ 個人設定 の順で解決する。
  個人が選んだものが最優先

### 🚨 v0.9 時点の実装状況（決定と実装がまだ揃っていない）

**この決定は正しいが、v0.9 では最後の一段（個人設定）が入っていない。**
後から読んだ人が「決定と実装が違う」と混乱するので、いまの姿を残しておく。

| 決定 | v0.9 の実装 |
|---|---|
| オンボーディングで言語を選ばせる | **入っている**（選んだ値は**全体設定**の `default_locale` に入る） |
| 以降は個人設定で変更する | 🚨 **未実装。** `directus_users` に言語の列が無い |
| ヘッダから言語切替を外す | 🚨 **外していない。** 外すと一般利用者が言語を変える手段がゼロになるため |

解決順も、実装は **Cookie → Accept-Language → 全体設定（DB）→ 環境変数 → 既定値** で、
上の記述（環境変数 → 全体設定 → 個人設定）とは**順序も段数も違う**。
個人設定の段が無く、Cookie が事実上その代わりをしている。

🚨 **`LocaleSwitcher` をヘッダから外せるのは、個人設定で言語を変えられるようになってから。**
先に外すと、一般利用者は言語を二度と変えられなくなる（オンボーディングは1回きりなので）。
**個人ごとの言語列を足すのは v1.0。**

> 由来: 2026-08-13。auth 担当が「決定に従ってヘッダから外す」を進めようとして、
> 個人設定が存在しないことを実測で見つけた。あわせて ui 担当が
> **全体設定の `default_locale` がどこからも読まれていなかった**ことを見つけて繋いだ
> （[[verify-the-verifier]] の 8 件目）。**決定を実装へ写すときは、
> 決定が前提にしている段が本当に在るかを先に確かめる。**

## この判断の使い回し方

**「これはヘッダに置くべきか」で迷ったら、まず頻度を聞く。**
「毎日押しますか」に「いいえ」と答えられる要素は、常設領域から降ろす。

同じ理屈が効きそうなもの（都度判断する）:
テーマ（ライト/ダーク）/ タイムゾーン / 表示密度 / 通知の設定。

- 2026-08-13 堀池の指示（原文は §背景に引用）
