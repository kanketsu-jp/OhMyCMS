# 「まだ許可されていない」は、ログイン画面へ送らない

> 由来: 2026-08-16。SSO で**認証には成功した**が、許可リストに無い利用者が `/admin` に留まり、
> **押せる項目が並び、押すたびに 403** が返っていた（onboard が使い捨ての実体で実測）。

## TL;DR

- **`/login` へ送らない。** その人は**認証に成功している**
- **`/admin` にも留めない。** 押すたびに 403 は「壊れている」に見える
- ✅ **専用の画面で受ける**:「**このアカウントは、まだ許可されていません**」
- 🚨 **ログアウトの導線を必ず置く**（無いとその人は詰む）
- 🚨 **これはデータの漏れではない**（実測。§3）

---

## 1. 決定

```
認証済み × 未許可 … ✅ **専用の画面**（ナビ・サイドバーを出さない）
   文  「このアカウントは、まだ許可されていません。管理者に連絡してください」
   🚨 **ログアウトの導線を置く**（別のアカウントで入り直せる）
未認証 ……………… `/login` へ送る（**いままでどおり**）
```

## 2. なぜ `/login` ではないか

🚨 **`/login` へ送るのは「嘘の導線」。**
その人は**認証に成功している**ので、**もう一度ログインしても何も変わらない**。
「ログインしたのに、またログイン画面」＝ **何度でも同じことを繰り返させる**。

🚨 **認証（誰か）と認可（何ができるか）は別の問い。画面もそれに従う。**

**文言を「権限がありません」にしない理由:**
```
🚨 「**まだ**許可されていません」＝ **状態**であって、その人の欠陥ではない
   ＝ **あとで入れるようになる**ことが伝わる
```

## 3. 🚨 これはデータの漏れではない（実測 2026-08-16・onboard）

```
未許可の SSO 利用者が /admin を開いたとき:
  🟢 一覧の行 **0** ／ 実在のコレクション名 **0 本** ／ 利用者らしきもの **0**
  🟢 対照 管理者 … 一覧 1 ／ 実在の名前が見える
  🟢 対照 未認証 … /login へ送られる
  🚨 引き算 … 管理者 **120 文字** − 未許可 **89 文字** = **31 文字**
             ＝ 差は「実在するコレクションの名前と行」だけ
＝ **中身は空の器。構造も人も漏れていない**
```

🚨 **サービス名が見えるのは「新しい漏れ」ではない**——
🟢 **対照の未認証（`/login`）でも見出しに出ている** ＝ **ログイン前から公開されている情報**。
**分けなければ、既に公開しているものを塞ぎに行くところだった。**

🚨 **「引き算できる形で数を出す」のが効いた**（120 − 89 = 31）。
**「漏れていない」より「差はこれだけ」のほうが強い。**

## 4. 🚨 画面が 1 枚増えることについて

`every-element-must-earn-its-place`（置くものには理由が要る）に照らしても、**増やす**。
**この画面は「認証済みだが未許可」という状態を伝える唯一の場所**で、他のどこにも置けない。

❌ **ナビ・サイドバーは出さない。**
**押せるものが 1 つも無い画面に、押せない項目を並べない。**

## 5. 🚨 ボードへ出さないと決めた（**その判断も記録する**）

```
① **データの漏れではない**（§3 の実測）
② 🚨 **設計の原則から答えが出る**（認証 ≠ 認可）＝ **堀池さんに聞くまでもない**
③ 回答待ちが 14 件在った。**原則で決まるものを積むと、決まるものまで遅れる**
```

🚨 **「聞かなかった」ことを書き残す。**
書かないと、次の人が「**なぜ聞かなかったのか**」を辿れず、
**もう一度ボードへ出す**か、**勝手に変える**かのどちらかになる。

## 6. この決定が当たらない場面

- **許可リストそのものの設計**（誰が許可するか・どこで許可するか）は別の問い
- **`proxy.ts` で分岐するか layout で分岐するか**は実装の判断（auth の領域）。
  🚨 ただし `auth-session-jwt-cookie.md` のとおり、**認可の最終判断は middleware/proxy ではなく
  Server 側か DB**。この画面は**見せ方**であって、**守りではない**

## 6.5 実測（2026-08-16・`2563d0f`）— 🚨 **別の目（base2）が測った分を正とする**

```
🟢 ① 管理者 ……………… `/admin/collections`・本文に「コンテンツ / ファイル / 設定 …」
🔴 ② 認証済み × 未許可 … その画面（「まだ許可されていません／…／ログアウト」）・form 1 / ボタン 1
🟢 ③ 未認証 …………… `/login`（＝ **既存の分岐を壊していない**）
🔴 ④ 🚨 ログアウト → `/login` → **そのあと `/admin` を開き直しても `/login`**
     ＝ **セッションが切れている**
```

🚨 **④は design の測定では足りていなかった。**
design は「押すと `/login` に着く」までで、**「着いた」と「切れた」を分けていなかった**
（**自分で書いた受入基準を、自分で満たしていなかった**）。

🚨 **base2 の理由づけが、そのまま次に使える:**
**「あなたを疑っているのではない。**同じ計器で測ると同じ穴を通る**ので、別の目で測る」**

### 🚨 ナビが無いことは「要素の数」で示さない

```
🔴 base2 の 1 回目 … `#left-sidebar, [data-slot=left-sidebar]` の数
   → 🚨 **管理者の画面でも 0**（＝ 選択子が実物に当たっていない。**根拠にならない**）
🟢 使える形 …… **本文の語**
   管理者 …「コンテンツ ファイル 設定 コレクション …」が**在る**
   未許可 …「まだ許可されていません … ログアウト」**だけ**（**ナビの語が 1 つも無い**）
```
🚨 **対照（管理者）が同じ 0 を出したので気づけた。片側だけなら通っていた。**

## 7. レビュー観点

- [ ] 未認証は `/login`、認証済み未許可は専用画面——**2 つが混ざっていないか**
- [ ] その画面に**ログアウトの導線**が在るか
- [ ] ナビ・サイドバーを出していないか
- [ ] 🚨 **見せ方を直しただけで「守った」と読んでいないか**（守りはサーバ側）
