# ゴミ箱と復元の画面（箱の形は決める。中に何が並ぶかは未決）

> 由来: 2026-08-15 堀池さん（原文・設問283 の注記）:
> 「**全ての削除はソフトデリート。ゴミ箱を新設する。何日前のものを消すか？も設定する。
> デフォルトは９０。**」

## TL;DR

- **削除は消さない。ゴミ箱へ入れる**
- **ゴミ箱は 1 画面**。`/admin/trash`
- **復元は 1 手**（開かずに、行から直接）
- **保持日数は設定画面に置く。既定 90 日**
- 🚨 **そこに何が並ぶか（＝復元が何を戻すか）は未決**（§5）。**箱の形とは別の問題**
- 🚨 **完全削除は「活動の記録」も一緒に消す**（CASCADE）。**実装前に設問291 を決める**（§5）

ゴミ箱を入れるとき、**「削除」＝ゴミ箱へ入る、と読めるかどうか**が画面ごとに変わる。

## 2. ゴミ箱の置き場所と形

```
場所   /admin/trash
入口   🚨 **左サイドバーの最下段**（`ui-placement-by-frequency.md`: 頻度の低いものは下）
形     一覧。1 行 = 消したもの 1 つ
列     何を / どこから / いつ消したか / **あと何日で完全に消えるか**
```

🚨 **「あと何日」を出す。** 「いつ消したか」だけだと、利用者が保持日数を暗算することになる。

## 3. 復元の導線

```
🚨 **行から直接 1 手**（開かなくても戻せる）
   理由: ゴミ箱に来る人は「戻したい」が目的。**開いて確かめる**のは例外
確認   **要らない**（復元は元に戻す操作で、失っても困らない）
🚨 完全に消す … **確認を出す**（こちらは取り消せない）
```

**アクションボタンの規約（`action-button-and-edit-mode.md`）に合わせる:**
```
主ボタン   「復元」
▾ の中     「完全に消す」   ← 🚨 破壊的なので必ず ▾ の中
```

🚨 単位    日。**0 を許すか**は §5 と一緒に決める（0 ＝ 即時完全削除になるため）
空にする   ゴミ箱の画面の ▾ の中。**確認を出す**

## 4.5 🚨 押したあとに知らせる（ゴミ箱より先にやる）

**2026-08-15 実測: 削除の 9 箇所のうち、7 箇所は成功しても何も言わない**
（`router.refresh()` するだけ ＝ **黙って行が消える**）。

```
🟢 対照 DELETE の箇所 9 件（0 なら探し方が壊れている）
知らせ在り 2 件（file-tile-menu / labels-manager）／ 🚨 無し **7 件**
```

🚨 **これはゴミ箱の前提を壊す。**
```
いま        押す → 黙って行が消える
ゴミ箱の後  押す → 黙って行が消える（**同じ**）
＝ **ゴミ箱に入ったことが、どこにも出ない。作っても誰も気づかない**
```

**足す先（7 箇所）:**
```
components/admin/agents-manager.tsx:202          components/admin/policies-manager.tsx:67
components/admin/file-detail-manager.tsx:71      components/admin/policy-permissions-manager.tsx:130
components/admin/folder-grid.tsx:63              components/admin/roles-manager.tsx:63
components/admin/users-policy-manager.tsx:83
🚨 行番号は動く。**ファイル名と「DELETE の直後」で探すこと**
```

### 🚨 鍵は共通にしない。名前は**その画面の言葉**に合わせる

```
✅ 各画面が**自分の鍵**を持つ
❌ 全画面で 1 つの共通鍵を使う
```

**理由**: 設問288 が **B（仕組みの表だけがゴミ箱）** になった場合、
**戻せる削除と戻せない削除が混ざる**。そのとき**共通鍵だと、片方だけ文言を変えられない**。

**🚨 2026-08-16 訂正: 当初この節は「名前を `<名前空間>.deleted` で揃える」と書いていた。**
**実装者（agents-manager 担当）が、その場で穴を見つけた**（消さずに残す）:

> この画面の語彙は**全部「失効」**（`revoke_button` / `revoke_failed` / `revoked_badge`）。
> `deleted` という名前に「失効しました」を入れると、**名前が中身を語らない**。
> 🚨 **`*.deleted` で横断して探す人は、この画面を取りこぼす。**

**＝ 名前を揃えると、揃えた名前のほうが嘘になる画面が在る。**

**直した規則:**
```
✅ 鍵の名前は **その画面が使っている動詞**に合わせる（deleted / revoked / removed …）
🚨 **横断して探すときは、鍵の名前で探さない。**
   **`DELETE` を投げている場所**から探す（この文書の 9 箇所も、そうやって見つけた）
```
🚨 **名前で探せる前提を置くと、語彙が違う画面を静かに落とす。**
**探し方のほうを、名前に依存しない形にしておく。**

🚨 **いまは「削除しました」で書く。** ゴミ箱が入ったら、**対象の鍵だけ**
「ゴミ箱へ移動しました」へ変える。**同じ場所を 2 回触らないための順序。**

### 🚨 その場で戻す導線は、作れない（確定）

```
🟢 対照 toast.tsx に action / ボタンを受ける口 … **無い**
🟢 対照 同ファイルに toast.success の定義      … 在る（＝この探し方は動いている）
```

**2026-08-15 確定（toast の持ち主 + 司令塔）: これは「口を足す」で済む話ではない。**

```
トーストの仕様（🚨 **堀池さんの指示**なので、担当が勝手に変えられない）:
  ・**3 秒で消える**（プログレスバー連動）
  ・**押す操作は置けない**
  ・**同時に 3 枚まで**
```
🚨 **＝「元に戻す」を置くには、堀池さんが決めた部品の仕様そのものを変えることになる。**
**担当者が判断できる範囲を超えているので、ユーザーへ出す。**

**したがって、この文書は「戻すには必ずゴミ箱まで行く」を前提にしている**（§3）。
🚨 **その前提が変わったら、§3 の導線（1 手で戻す）の価値が変わる**
（その場で戻せるなら、ゴミ箱まで来る人は少なくなるため）。

### 🚨 まとめて削除したときの知らせ

**トーストは同時に 3 枚まで。** 一覧で 20 行まとめて消すと、**最後の 3 件しか見えない。**

> 🚨 **2026-08-16 訂正（消さずに残す）**: 当初ここに「**4 件目以降は見えない**」と書いていた。
> **溢れるのは古いほうで、新しいほうではない。** 4 枚目が出ると 1 枚目が押し出される形なので、
> 実際に消えるのは **最初の N−3 件**。
> **＝ 誰にも届かないのは「先に消した分」。**
> 誤りの向きが逆だったので、**「後半が見えないだけなら大したことない」と読める**危険があった。
>
> **【読んだ】根拠**（2026-08-16・`components/ui/toast.tsx`）:
> ```
> 20:  const TOAST_LIMIT = 3
> 100: currentToasts = [...currentToasts, item].slice(-TOAST_LIMIT)
> ```
> 新しいものを**末尾に足して、末尾 3 件を残す** ＝ **押し出されるのは先頭（古いほう）**。
> 🚨 ブラウザで動かして確かめたわけではない（コードを読んだだけ）。ただし `.slice(-3)` に
> 読み方は 1 通りしかない。

```
20 件消す → 見えるのは 18・19・20 件目だけ。**1〜17 件目は誰も見ていない**
🚨 1 行ごとに 1 枚出す形にしない。**「N 件を削除しました」と 1 枚にまとめる**
🚨 失敗が混ざる場合はなおさら。**失敗が古いほうに居ると、押し出されて消える**
   （通知は「終わったこと」だけ。直す必要があるものはその場に残す
   → `toast-for-events-page-for-what-needs-fixing.md`）
```
（`/admin/content/<c>` と `/admin/settings/users` は、実測で **削除が 20 個ずつ**並んでいる画面）

## 5. 🚨 未決 — そこに何が並ぶか（＝復元が何を戻すか）

**箱の形は決まるが、中身は決まらない。** 設問288 の回答待ち。

**なぜ未決か（他ペインの実測が根拠）:**

```
🚨 [toast] 削除時に **ラベルの割り当てを物理削除**している
          → 行を残しても、**ゴミ箱から戻すとラベルが 1 つも付いていない**
🚨 [storage] 削除時に **保管先の実体を消している**（原本・圧縮版・変換版）
          → 実体も残す … **90 日ぶんの容量を持ち続ける**（R2 の課金）
          → 実体は消す … 🚨 **「戻したのに開けない」**
```

🚨 **＝ ソフトデリートは「行を残す」だけでは成立しない。**
**削除のときに、行と一緒に消しているものが在る。**
**それを 1 つずつ「戻るのか / 戻らないのか」決めないと、「復元」が嘘になる。**

**決まっていない問い:**

| 問い | 誰が決めるか |
|---|---|
| 利用者が作ったコレクションの行も、ゴミ箱に入るか | 設問288（schema の領域） |
| 復元は「行だけ」か「関連（ラベル・実体）ごと」か | 判断ボード |
| ファイルの実体を 90 日持つか（容量 vs 開けない） | 判断ボード |
| 90 日で消すのは誰か（**cron が無い**） | 未割り当て |
| 🚨 **完全削除で監査の記録も消えてよいか** | **設問291** |

### 🚨 完全削除は、監査の記録も一緒に消す（設問291）

**【測った】司令塔が DB の外部キーに直接聞いた（2026-08-15）:**
```
コレクションを消す → 🚨 そのコレクションの活動記録が全部消える（CASCADE）
利用者を消す       → 「誰がやったか」が空になる（SET NULL）
```
🚨 **＝ 不都合な記録は、対象ごと消せば消せます。** 監査として改ざん耐性がありません。

```
いまは発火しない … ソフトデリートなら外部キーは動かない
🚨 発火する瞬間  … **「90 日で完全に消す」が走ったとき**（＝ この文書を実装すると起きる）
```
🚨 **この文書は「90 日で完全に消す」を前提に書いてあるので、
実装する前に 291 を決めること。** 決める前に作ると、**記録が消える経路を自分で開きます。**

🚨 **90 日で消す仕組みが無い。** `AGENTS.md` §3.6:
「常駐プロセス / cron はリクエスト単位の Next.js では素直に書けない」。
**仕組みが無いのに「自動で消えます」と画面に書かない**こと。
**書くなら「次に誰かが開いたときに消える」など、実際の動きを書く。**

### A: 利用者が作った表も、ゴミ箱に入る

**画面側で変わること:**
```
文言    🚨 **揃えられる。** 全部の削除が戻せるので、押したあとは
        どの画面でも「ゴミ箱へ移動しました」で統一できる
        （§4.5 の「鍵は画面の動詞に合わせる」は**そのまま**。
          🚨 **揃うのは "意味" であって "鍵の名前" ではない**）
確認    削除の前に確認を出さない（戻せるので）。**「完全に消す」だけ確認**
一覧    「何を」の列に、利用者が付けた**コレクションの表示名**を出す
        表示名が無いときは **生の識別子**を出す
        🚨 根拠は**この家の既存の作法**: `fieldLabel`（`lib/schema/labels.ts:23`）が
           「辞書が null → 生の識別子」で動いており、検査 `field-labels` がそれを固定している
           （2026-08-16 実測: 門の出力に「✅ 辞書が null → 生の識別子」）
        🚨 `synthetic-ids-are-not-contacts` は**引かない**。あれは
           **利用者のメールアドレス**（`local-admin@localhost` / `<uuid>@saml.invalid`）の話で、
           コレクションの名前とは対象が違う（**一度ここに引いて、読み直して外した**）
入口    サイドバー最下段の 1 つだけ（§2 のまま）
```
**残る問い**: 復元が「行だけ」か「関連ごと」か（§5 の 2 行目。**A でも B でも残る**）

### B: 仕組みの表だけが、ゴミ箱に入る

🚨 **画面側の仕事が増える。** 理由は 1 つ——**戻せる削除と戻せない削除が混ざる**。

```
🚨 押す前   **区別が要る**
            戻せない削除 … **確認を出す**（取り消せないので）
            戻せる削除   … 確認を出さない
            ＝ **同じ「削除」ボタンが、画面によって挙動が変わる**
🚨 押した後 **文言を分ける**
            戻せる   →「ゴミ箱へ移動しました」
            戻せない →「削除しました」
            🚨 §4.5 で**鍵を画面ごとに分けておいたのは、これが理由**。
               共通鍵にしていたら、ここで片方だけ変えられない
一覧      利用者のコレクションは**ゴミ箱に出てこない**
入口      🚨 **「何が入らないか」が利用者に分からない。**
          ゴミ箱の画面に 1 行、対象の範囲を書く
          （書かないと「消したのにゴミ箱に無い」と読まれる）
```

🚨 **B でいちばん危ないのは、ボタンの見た目が同じことです。**
```
❌ どちらも「削除」で、押してみないと戻せるか分からない
✅ 🚨 **戻せないほうの文言を変える**（例:「完全に削除」）か、**確認で区別する**
   → どちらを採るかは、B が確定してから 1 問として出す
```

### 🚨 A / B のどちらでも**やってはいけない**こと

```
❌ 「戻せるかどうか」を、画面の種類（設定画面／一覧画面）で決める
   → 新しい画面がどちらに入るか誰にも分からなくなる
     （`action-button-and-edit-mode.md` §7 と同じ判断軸）
❌ ゴミ箱に「自動で消えます」と書く（**cron が無い**。§5 の最後）
❌ 完全削除を実装する（🚨 **設問291 が先**。監査の記録が CASCADE で消える）
```

## 5.6 🚨 289 の回答が来たときの設計 — **誰が 90 日後に消すか**

**事実**: 定期実行の仕組み（cron・常駐・`setInterval`）は **0 件**。

🚨 **この問いは、画面の 1 つの列に直接効く。** §2 の「**あと何日で完全に消える**」。

```
A 使ったついでに少しずつ消す
   🚨 **「あと 0 日」と出たのに、まだ在る**ことが起きる（誰も使わなければ消えない）
   → 列の意味を変える: 「あと何日」ではなく **「◯月◯日以降に消えます」**
     🚨 **時点を約束せず、境目だけ言う**
   → ゴミ箱の画面に 1 行: **「誰かが操作したときにまとめて消えます」**
     （`AGENTS.md` §3.6 の理由をそのまま書かない。**利用者に仕組みの話をしない**）
   ✅ 先例が在る（🟢 **開いて確かめた**・2026-08-16）:
     `lib/auth/saml/client.ts` の `purgeExpiredSamlRecords()`
     コメント原文「期限切れの記録を落とす。**ログインのたびに少しずつ掃除する（cron を持たないため）**。」

B 画面から手で「今すぐ空にする」
   🚨 **「あと何日」を出してはいけない。** 押さなければ永久に残るので、**日数が嘘になる**
   → 列は「**いつ消したか**」だけ
   → 🚨 **「空にする」を ▾ の中に隠さない**（§4 では ▾ の中に置いたが、
     B では**これが唯一の削除手段**になるので、隠すと誰も消せない）
     → **B が確定したら §4 を書き換える**

C 定期実行の仕組みを作る
   ✅ 「あと何日」が**そのまま正しい**（§2 のまま。画面側の変更なし）
   🚨 画面側は何も変わらないが、**止まったときに画面が嘘をつく**
   → 最後に走った時刻を設定画面に出すか、は C が確定してから 1 問
```

🚨 **A / B のどちらでも、いまの §2「あと何日」は書き換えになる。**
**C だけが、いまの設計をそのまま使える。**

## 5.7 🚨 290 の回答が来たときの設計 — **戻したとき何が戻るか**

**事実**: ファイルを 1 件消すと動くものは **4 つ**（①実体 ②DB の行 ③ラベル ④ロゴ）。
**行だけ残すと、戻るのは②だけになりかねない。**

🚨 **そして、いちばん効く事実がこれ**（🚨 **中継せず、自分で測り直した**）:
```
【測った】2026-08-16・design（文言は design の領域なので、受け取らず自分で数えた）
  文言の総数            ja **798** / en **798**
  ja で「戻せない」系    **1 件** → `richtext.undo` = 「元に戻す」（エディタの取り消し。無関係）
  🚨 en で対応する語     **0 件**（cannot be undone / irreversible / permanently）
  🟢 対照(+) 「削除」を含む ja  33 件（0 なら読めていない）
  🟢 対照(-) 在るはずのない語   0 件（0 なら全部拾う探し方ではない）
＝ **この製品は、いま「戻せない」を言う語彙を持っていない。日本語も英語も。**
```
🚨 **司令塔から届いた数は「791 文言」だった。私が数えたら 798。**
**結論は同じ（語彙が無い）だが、数が 7 違う。** どちらの母集合が正しいかは確かめていないので、
**ここには自分で数えた値だけを置く**（`i18n/messages/{ja,en}/*.json` の文字列値のみ）。
🚨 **英語側 0 件は、届いた事実には無かった。** 数え直さなければ出てこなかった。

```
A 全部戻る（ラベルも実体も残す）
   ✅ **「元に戻す」が言葉どおり**。画面側で新しく説明することが無い
   🚨 ラベルの「使用数」に**消したファイルが混ざる**
   → ラベルの画面で、使用数の隣に **「（ゴミ箱の分を含む）」** を出すか、
     **ゴミ箱の分を数えない**か。🚨 **どちらでも、数の意味を画面に書く**
     （数だけ出すと、利用者が「合わない」と思う）

B 見た目だけ戻る（実体は消す）
   🚨 **戻したファイルが開けない。** ＝ **復元が成功したのに、失敗している**
   → 🚨 **ゴミ箱に入った時点で「中身は戻りません」と出す**（戻したあとでは遅い）
   → 一覧の行に **「中身なし」の印**を付ける
   → 🚨 **新しい語彙が要る**（上記のとおり、この製品は「戻せない」を言えない）
   → 復元ボタンの文言を変える: 「復元」ではなく **「一覧に戻す」**
     （**中身が戻らないものを「復元」と呼ばない**）

C ファイルはゴミ箱の対象外
   🚨 **同じ「削除」で、ファイルだけ戻らない** ＝ 288 の B と**同じ形の危険**
   → ファイルの削除だけ **確認を出す**（他は出さない）
   → 確認の文面に **「元に戻せません」**（🚨 **新しい語彙。いま無い**）
   → ゴミ箱の画面に **「ファイルは入りません」**の 1 行
   🚨 **いちばん「間違って消した」が起きやすいものが、守られない側に残る**
```

🚨 **B と C は、どちらも「元に戻せません」という語彙を新設する。**
**A だけが、いまの語彙のままで済む。**
🚨 **その場で戻す導線は、どの案でも作れない**（§4.5 のトースト制約）。

## 5.8 🚨 291 の回答が来たときの設計 — **監査の記録も消えるか**

```
A 記録は消さない（記録側に写しを持つ）
   🚨 **消したはずの名前が、活動の記録に残る**
   → 画面側: 記録の一覧で、**もう存在しないものの名前**が出る
     → 🚨 **リンクにしない**（押しても 404）。**文字のまま出す**
     → 「（削除済み）」を付けるか → **A が確定してから 1 問**
   → 完全に消すときの確認文に 1 行: **「操作の記録は残ります」**

B 一緒に消えてよい
   ✅ 画面側の変更は無い
   🚨 ただし**画面に「記録が残ります」と書いてはいけない**（嘘になる）
   🚨 そして **不都合な記録は、対象ごと消せば消せる**（本文 §5 の警告のまま）
```

🚨 **A なら「削除済みのものが画面に出る」経路が新しくできる。**
**その表示のしかたは、いまどの規約にも書かれていない。**

## 6. 🚨 この規約が当たらない場面

- **設定値の変更**（保存の上書き）— 削除ではないので、ゴミ箱に入らない
- **まだ保存していない編集の破棄**（「やめる」）— これは編集モードの話（別の規約）
- **利用者が作ったコレクション自体の削除** — §5 の 1 行目が決まるまで、当てない

## 7. レビュー観点

- [ ] 🚨 **削除を押したあと、利用者に何か伝わるか**（黙って行が消えていないか。§4.5）
- [ ] 🚨 知らせの鍵が**画面ごとに分かれて**いるか（共通鍵にしていないか）
- [ ] 🚨 鍵の名前が**その画面の動詞**に合っているか（`deleted` に「失効しました」を入れていないか）
- [ ] 🚨 まとめて削除したとき、**1 件ずつトーストを出していないか**
      （同時 3 枚まで。溢れると **古いほうから消える** ＝ 先に消した分が誰にも届かない）
- [ ] 復元が **1 手**でできるか（開かないと戻せない形になっていないか）
- [ ] 「完全に消す」が ▾ の中に在り、**確認**が出るか
- [ ] 「あと何日で消えるか」が出ているか（消した日だけになっていないか）
- [ ] 🚨 **復元して、消す前と同じに戻るか**（ラベル・実体・関連。§5 が決まってから）
- [ ] 画面に「自動で消えます」と書いていないか（**仕組みが無い**うちは書かない）
- [ ] §5 が未決のままなら、**未決と書いてあるか**
- [ ] 🚨 **その削除で、活動の記録も一緒に消えないか**（設問291。完全削除で CASCADE が発火する）
