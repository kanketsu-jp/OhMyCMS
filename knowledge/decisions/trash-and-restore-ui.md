## TL;DR

- **削除は消さない。ゴミ箱へ入れる**
- **ゴミ箱は 1 画面**。`/admin/trash`
- **復元は 1 手**（開かずに、行から直接）
- **保持日数は設定画面に置く。既定 90 日**
- ✅ **4 問とも確定**（2026-08-16）: 288A 利用者の表も対象 / 289C 定期実行 / 290A 全部戻る / 291A 監査は消さない

- ✅ **その先の 3 件も決めた**（2026-08-16・§5.5）:
  **2 段以上は全部戻す**（件数を出す）／ **完全削除済みは「空のまま戻す」か「やめる」** ／
  **まとめて復元は 1 回だけ聞く**（🚨 **10 件・+7 件・空 2 件の 3 つの数を出す**）
- 🚨 **戻せない行（主キーの無い表）も一覧に出す**。出さないと**「消えた」と区別が付かない**。
  復元ボタンの代わりに理由を 1 行

- 🚨 **実装は schema の土台（`deleted_at` と読む側の入口）の後**（§5.10）

## 2. ゴミ箱の置き場所と形

```
場所   /admin/trash
入口   🚨 **左サイドバーの最下段**（`ui-placement-by-frequency.md`: 頻度の低いものは下）
形     一覧。1 行 = 消したもの 1 つ
列     何を / どこから / いつ消したか / **あと何日で完全に消えるか**
```

🚨 **「あと何日」を出す。** 「いつ消したか」だけだと、利用者が保持日数を暗算することになる。

### 🚨 「何を」の列は、表示名か id かで**揺れる**（2026-08-16 に穴が出た）

```
【実装】`lib/trash/service.ts` の `displayName()`
   表示名（`DISPLAY_FIELDS`）が在れば **それ** ／ 無ければ **主キー（id）**
＝ 🚨 **同じ列に、2 種類のものが出る**
```

🚨 **これを外の文言と噛み合わせないと、「在ると言われたのに見つからない」が起きる。**

**実際に出た例**: schema が `ITEM_EXISTS_TRASHED` を作り、文言を
**「同じ *ID* の項目がゴミ箱にあります」**にした。
→ 🚨 **表示名が在る行では、ゴミ箱に id が 1 文字も出ていない** ＝ **ID で探せない**。

**決定: ゴミ箱の外から「ゴミ箱に在る」と言う文言は、`displayName()` と同じ文字列を使う。**
```
✅ 「同じ ID の項目「**◯◯**」がゴミ箱にあります」（◯◯ = displayName と同じ）
   → 表示名が在れば表示名、無ければ id ＝ **どちらでも一覧と一致する**
❌ ゴミ箱に「ID」列を足す … 大多数の行では表示名で足りるのに、**常に 1 列ぶん重くなる**
   （`every-element-must-earn-its-place`）
❌ id で絞り込めるようにする … 🚨 **文言から辿れない**（利用者はその機能を知らない）
```

🚨 **これは design の設計の穴だった。** 列を 4 つに決めたとき、
**「何を」が 2 種類のものを出すことを、この決定に書いていなかった。**

### 🚨 鍵は共通にしない。名前は**その画面の言葉**に合わせる

```
✅ 各画面が**自分の鍵**を持つ
❌ 全画面で 1 つの共通鍵を使う
```

**理由**: 設問288 が **B（仕組みの表だけがゴミ箱）** になった場合、
**戻せる削除と戻せない削除が混ざる**。そのとき**共通鍵だと、片方だけ文言を変えられない**。

**🚨 2026-08-16 訂正: 当初この節は「名前を `<名前空間>.deleted` で揃える」と書いていた。**
**実装者（agents-manager 担当）が、その場で穴を見つけた**（消さずに残す）:

> この画面の語彙は**全部「失効」**（`revoke_button` / `revoke_failed` / `revoked_badge`）。
> `deleted` という名前に「失効しました」を入れると、**名前が中身を語らない**。
> 🚨 **`*.deleted` で横断して探す人は、この画面を取りこぼす。**

**＝ 名前を揃えると、揃えた名前のほうが嘘になる画面が在る。**

**直した規則:**
```
✅ 鍵の名前は **その画面が使っている動詞**に合わせる（deleted / revoked / removed …）
🚨 **横断して探すときは、鍵の名前で探さない。**
   **`DELETE` を投げている場所**から探す（この文書の 9 箇所も、そうやって見つけた）
```
🚨 **名前で探せる前提を置くと、語彙が違う画面を静かに落とす。**
**探し方のほうを、名前に依存しない形にしておく。**

🚨 **いまは「削除しました」で書く。** ゴミ箱が入ったら、**対象の鍵だけ**
「ゴミ箱へ移動しました」へ変える。**同じ場所を 2 回触らないための順序。**

### 🚨 その場で戻す導線は、作れない（確定）

```
🟢 対照 toast.tsx に action / ボタンを受ける口 … **無い**
🟢 対照 同ファイルに toast.success の定義      … 在る（＝この探し方は動いている）
```

**2026-08-15 確定（toast の持ち主 + 司令塔）: これは「口を足す」で済む話ではない。**

```
トーストの仕様（🚨 **堀池さんの指示**なので、担当が勝手に変えられない）:
  ・**3 秒で消える**（プログレスバー連動）
  ・**押す操作は置けない**
  ・**同時に 3 枚まで**
```
🚨 **＝「元に戻す」を置くには、堀池さんが決めた部品の仕様そのものを変えることになる。**
**担当者が判断できる範囲を超えているので、ユーザーへ出す。**

**したがって、この文書は「戻すには必ずゴミ箱まで行く」を前提にしている**（§3）。
🚨 **その前提が変わったら、§3 の導線（1 手で戻す）の価値が変わる**
（その場で戻せるなら、ゴミ箱まで来る人は少なくなるため）。

### 🚨 まとめて削除したときの知らせ

**トーストは同時に 3 枚まで。** 一覧で 20 行まとめて消すと、**最後の 3 件しか見えない。**

> 🚨 **2026-08-16 訂正（消さずに残す）**: 当初ここに「**4 件目以降は見えない**」と書いていた。
> **溢れるのは古いほうで、新しいほうではない。** 4 枚目が出ると 1 枚目が押し出される形なので、
> 実際に消えるのは **最初の N−3 件**。
> **＝ 誰にも届かないのは「先に消した分」。**
> 誤りの向きが逆だったので、**「後半が見えないだけなら大したことない」と読める**危険があった。
>
> **【読んだ】根拠**（2026-08-16・`components/ui/toast.tsx`）:
> ```
> 20:  const TOAST_LIMIT = 3
> 100: currentToasts = [...currentToasts, item].slice(-TOAST_LIMIT)
> ```
> 新しいものを**末尾に足して、末尾 3 件を残す** ＝ **押し出されるのは先頭（古いほう）**。
> 🚨 ブラウザで動かして確かめたわけではない（コードを読んだだけ）。ただし `.slice(-3)` に
> 読み方は 1 通りしかない。

```
20 件消す → 見えるのは 18・19・20 件目だけ。**1〜17 件目は誰も見ていない**
🚨 1 行ごとに 1 枚出す形にしない。**「N 件を削除しました」と 1 枚にまとめる**
🚨 失敗が混ざる場合はなおさら。**失敗が古いほうに居ると、押し出されて消える**
   （通知は「終わったこと」だけ。直す必要があるものはその場に残す
   → `toast-for-events-page-for-what-needs-fixing.md`）
```
（`/admin/content/<c>` と `/admin/settings/users` は、実測で **削除が 20 個ずつ**並んでいる画面）

## 5. 🚨 **決まる前に測った材料**（2026-08-16 に全部確定。判断の根拠として残す）

**なぜ未決か（他ペインの実測が根拠）:**

```

**削除のときに、行と一緒に消しているものが在る。**

### 🚨 完全削除は、監査の記録も一緒に消す（設問291）

**【測った】司令塔が DB の外部キーに直接聞いた（2026-08-15）:**
```
コレクションを消す → 🚨 そのコレクションの活動記録が全部消える（CASCADE）
利用者を消す       → 「誰がやったか」が空になる（SET NULL）
```
🚨 **＝ 不都合な記録は、対象ごと消せば消せます。** 監査として改ざん耐性がありません。

```
いまは発火しない … ソフトデリートなら外部キーは動かない
🚨 発火する瞬間  … **「90 日で完全に消す」が走ったとき**（＝ この文書を実装すると起きる）
```
🚨 **この文書は「90 日で完全に消す」を前提に書いてあるので、
実装する前に 291 を決めること。** 決める前に作ると、**記録が消える経路を自分で開きます。**

🚨 **90 日で消す仕組みが無い。** `AGENTS.md` §3.6:
「常駐プロセス / cron はリクエスト単位の Next.js では素直に書けない」。
**仕組みが無いのに「自動で消えます」と画面に書かない**こと。
**書くなら「次に誰かが開いたときに消える」など、実際の動きを書く。**

🟢 「一緒に戻す」 … `{"restored":2}` ／ 戻す前 親 1・子 1 → 戻した後 親 0・子 0 ／ ゴミ箱 0 件
```
🚨 **測っていない範囲（「1 形・1 段で動いた」を「全部動く」と読ませないため）:**
```
🚨 **m2m は測っていない** … 【schema の実測】`relation-form.tsx` が出せるのは **m2o と o2m だけ**。
   **m2m（中間表）は画面から作れない** ＝ **当面は起きない**
   （**o2m は同じ FK を逆から見たもので、物理の形は m2o と同じ**）
🚨 **2 段以上（A→B→C）は測っていない** … 台は **1 段**だけ
   ＝ §5.5 A の「**2 段以上は全部戻す**」は、**まだ動いていない**
🚨 **完全削除済みを指す形（missingReferences）も測っていない** … 台では 0 件だった
```

🚨 **出た穴（未解決・schema へ照会中）**: `trashedReferences[].targetLabel` が
**`"collection"`** という値だった。**指し先の名前ではない。**
設計の文言は「この項目は **◯◯** を指しています」なので、**そのままでは意味が通らない**。
   → 消えていれば ③ へ
③ **一緒に戻すか選ばせる**
   ┌ 「この項目は **◯◯** を指していますが、◯◯ もゴミ箱にあります」
   │  ✅ **一緒に戻す**（主ボタン）
   │  ▾ **これだけ戻す**（🚨 指し先が空のまま戻る）
   └  🚨 **「これだけ戻す」を ▾ の中へ**（`action-button-and-edit-mode.md` §3。
        **壊れた状態で戻すほうが破壊的**なので）
```
🚨 **「一緒に戻す」を主ボタンにする理由**: 備考が「関連するものも復活するか」と
**復活させる側を先に書いている**。そして**指し先が空の行を戻すのは、戻したことにならない**。

#### ✅ 上の 3 件、決めた（2026-08-16・design）

**A. 指し先が 2 段以上つながっているとき（A→B→C が全部ゴミ箱）… 全部戻す**

```
🚨 理由は §290A の「一緒に戻す」を主にしたのと**同じ**:
   **1 段だけ戻して B が空なら、戻したことにならない**
確認は **1 回**（段ごとに聞かない）。🚨 ただし **件数を必ず出す**:
   「**◯◯ と、関連する 12 件**を一緒に戻します」
🚨 **数を出さずに「関連するものも」とだけ書かない。**
   **12 件なのか 1200 件なのか分からないまま押させることになる**
```

**B. 指し先が完全削除済み（90 日経過）で戻せないとき … 押す前に言う**

```
「この項目が指していた **◯◯** は、**完全に削除されています**。
  戻すと、その欄は **空** になります」
  ✅ **空のまま戻す**（主ボタン）
  ▾ **やめる**
```
🚨 **ここでは「これだけ戻す」が ▾ に来ない。** §290A と逆に見えるが、理由が違う:
**あちらは「一緒に戻す」という選べる道が在った。ここには無い**
（指し先はもう存在しないので、選択肢は「空で戻す」か「戻さない」の 2 つだけ）。

**C. 複数まとめて復元したとき … まとめて 1 回だけ聞く**

```
🚨 1 件ずつ聞かない（10 件選んだら 10 回。**トーストは 3 枚まで**・§4.5）
形（**内訳を数で出す**）:
   「**10 件**を戻します。
     うち **3 件**は関連するものも一緒に戻ります（**+7 件**）。
     🚨 **2 件**は指し先が完全に消えているので、**欄が空になります**」
   ✅ **戻す**（主ボタン）
   ▾ **関連するものは戻さない**
```
🚨 **「10 件戻します」だけでは足りない。** 実際に動くのは 17 件で、
**2 件は壊れた状態で戻る**。**押す前に、その 3 つの数を出す。**

#### 🚨 戻せない行（主キーが無い表・設問307）

**ゴミ箱に出す。ただし復元ボタンを持たせない。**

```
❌ 一覧に出さない … 🚨 **利用者から見て「消えた」と同じ**
   （schema の指摘と同型: **戻す道が無いものは、無いのと区別が付かない**）
✅ 出して、**復元ボタンの代わりに理由を 1 行**:
   「この表は**主キーを持たない**ため、戻せません」
```
🚨 **列を足して「戻せる／戻せない」を出さない。** 大多数は戻せるので、
**ほぼ全部同じ値が並ぶ列**になる（`every-element-must-earn-its-place`）。
**戻せない行にだけ理由が出る**形で足りる。

**🚨 この節で新しく増えた未決（**私では決められない**）:**
```
・A の「関連する N 件」が **極端に多い**とき（例: 1000 件超）… **止めるか、そのまま出すか**
  🚨 **数を出す決定はした**が、**上限は決めていない**
```

## 6. 🚨 この規約が当たらない場面

- **設定値の変更**（保存の上書き）— 削除ではないので、ゴミ箱に入らない
- **まだ保存していない編集の破棄**（「やめる」）— これは編集モードの話（別の規約）
- **利用者が作ったコレクション自体の削除** — §5 の 1 行目が決まるまで、当てない

## 7. レビュー観点

- [ ] 🚨 **削除を押したあと、利用者に何か伝わるか**（黙って行が消えていないか。§4.5）
- [ ] 🚨 知らせの鍵が**画面ごとに分かれて**いるか（共通鍵にしていないか）
- [ ] 🚨 鍵の名前が**その画面の動詞**に合っているか（`deleted` に「失効しました」を入れていないか）
- [ ] 🚨 まとめて削除したとき、**1 件ずつトーストを出していないか**
      （同時 3 枚まで。溢れると **古いほうから消える** ＝ 先に消した分が誰にも届かない）
- [ ] 復元が **1 手**でできるか（開かないと戻せない形になっていないか）
- [ ] 「完全に消す」が ▾ の中に在り、**確認**が出るか
- [ ] 「あと何日で消えるか」が出ているか（消した日だけになっていないか）
- [ ] 🚨 **復元して、消す前と同じに戻るか**（ラベル・実体・関連。§5 が決まってから）
- [ ] 画面に「自動で消えます」と書いていないか（**仕組みが無い**うちは書かない）
- [ ] 🚨 **復元を押したとき、指し先が消えていたら「一緒に戻すか」を聞いているか**（290 の備考・§5.5）
- [ ] 🚨 「これだけ戻す」が **▾ の中**に在るか（**壊れた状態で戻すほうが破壊的**なので）
- [ ] 🚨 **監査ログが「90 日で消す」の対象に入っていないか**（「ログは常に必要。」）
- [ ] ラベルの**使用数**に、ゴミ箱の分を含むかどうかが**画面に書いてある**か
- [ ] 🚨 **その削除で、活動の記録も一緒に消えないか**（設問291。完全削除で CASCADE が発火する）
