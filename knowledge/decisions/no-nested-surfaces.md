# 面（Surface）は1段まで。入れ子を構造的に禁止する

> 由来: 2026-08-13 堀池「**ボーダーの中にボーダーがあり、そのなかにボーダーがあります。
> 背景色も全て同じ。しかもすべて Padding を持ちます。これを徹底的にやめてください。**」
> 「**これはデザイナーとして知識が浅く、コンポーネント単位でしか考えていない典型的な悪い例です。
> 必ずルールを見直して。洗礼させて。**」

## TL;DR

**「面」は1画面に1段だけ。面の中に面を置かない。**

- **面（surface）= 親と違う「境界」を持つもの。** 罫線・背景色・影・角丸のどれかを持てば面
- ページ本体を **レベル0**、その上に置ける面を **レベル1** とし、**レベル2 を作らない**
- **入力欄・ボタンは「面」ではない。** 面の上に乗る部品。ただし**面の中に入れるなら罫線を外す**
- **SP ではカードを使わない。** 上下の **Divider だけ**で区切る

---

## 1. 何が起きたか（実物）

`/admin/folders` の実装（2026-08-13 時点）:

```
ページ（padding あり）
└─ カード「フォルダ管理」        ← 罫線 + padding      ← レベル1
   ├─ 作成セクション             ← 罫線 + padding      ← 🚨 レベル2
   │  ├─ 入力欄「フォルダ名」    ← 罫線                ← 🚨 レベル3
   │  └─ セレクト「親なし」      ← 罫線                ← 🚨 レベル3
   └─ 「フォルダはまだありません」← 罫線 + padding      ← 🚨 レベル2
```

**罫線が3重。背景はすべて同じ白。padding も全段が持っている。**

SP ではこれが横幅を食い、**中身が入る領域が実質半分**になっていた。

### なぜ起きたか

**コンポーネント単位でしか考えていないから。**
`Card` は「罫線と padding を持つ」、`Input` は「罫線を持つ」、と部品ごとに正しく作られている。
**それを組み合わせたときに何が起きるかを、誰も見ていなかった。**

---

## 2. ルール

### 2-1. 面のレベルは 0 と 1 だけ

| レベル | 何か | 持ってよいもの |
|---|---|---|
| **0** | ページ本体 | 外周の余白のみ |
| **1** | セクション（カード / パネル / モーダルの中身） | 罫線 **または** 背景 **または** 影のうち**1つ**、と padding |
| **2 以上** | 🚨 **作らない** | — |

**「レベル1 の中にもう1つ区切りが要る」と思ったら、それは面ではなく Divider で表現する。**

### 2-2. 面の中に入る部品は、境界を持たない

面（レベル1）の中に `Input` / `Select` / `Textarea` を置くとき:

```
❌ 罫線つきの入力欄をそのまま置く（罫線が2重になる）

✅ 選択肢A: 入力欄の罫線を外し、背景で区別する
   面 = 白 + 罫線  →  入力欄 = bg-zinc-100（罫線なし）
   面 = bg-zinc-50 →  入力欄 = 白（罫線なし）

✅ 選択肢B: 面の側の罫線を外し、入力欄の罫線を残す
   面 = 背景色だけ（罫線なし）→ 入力欄 = 罫線あり
```

🚨 **どちらか一方。両方に境界を持たせない。**

### 2-3. padding を二重に持たせない

**余白は「外側の器」が持ち、中身は持たない。**

- レベル1 の面が padding を持つ → その中の部品は**自分で padding を持たない**
- `children` や props で受け取るコンポーネントは、**余白を自分で持たない**か、
  **外から殺せる**ようにする（`className` で上書きできる形）
- 🚨 **各コンポーネントの JSDoc に「余白を持つ / 持たない」を明記する**

### 2-4. SP ではカードを使わない

> 堀池: 「**SP の場合は横幅が狭まりますし、そもそもカードタイプではなく上下の Divider のみでいい。**」

- SP（狭い幅）: **罫線で囲まない。上下の Divider だけ**で区切る。左右の padding はページ外周の1回だけ
- PC（広い幅）: カードにしてよい（**ただしレベル1まで**）
- 切り替えは**コンテナクエリ**で（idea.md §レスポンシブ）

### 2-5. 「空です」の表示に面を作らない

```
❌ 「フォルダはまだありません。」を罫線つきの箱に入れる
✅ 一覧が入る場所に、そのままテキストとして置く（面を増やさない）
```

**空の状態のために面を1つ増やすのは、いちばん割に合わない。**

### 2-6. 画面に固定されたバーは、面に数えない

`position: fixed` の要素は **out of flow** で、親の面の中に積まれるのではなく**画面に貼られる**。
DOM 上どこに書かれていても、視覚的な入れ子は作らない。

かつ**不透明でないと下の内容が透ける**ので、背景は必須。使うのは
**ページ本体と同じ `bg-background`**（別の色を当てると、そこで初めて面になる）。

- 対象: SP の下部ナビ（`components/admin/mobile-nav.tsx`）のような固定バー
- 区切りは上辺の罫線1本だけ（`border-t`）。4辺で囲まない（囲むと面になる）

🚨 **静的検査はこれを自力で判別できない。** `check-surface-nesting.mjs` は
「`components/admin/**` は必ず `<Surface>` の中」という前提で走るため、
**固定バーを違反として報告した**（2026-08-13 実際に起きた）。
`fixed` と `inset-x-0` の組み合わせを許容リストへ入れて解消してある。

> 憲章 §1:「正解を違反と言う検査は使われなくなり、検査そのものが死ぬ。**偽の赤は偽の緑と同じくらい高くつく。**」

🚨 **例外を足したら、検査が鈍っていないことを必ず確かめる。**
このときは、わざと `rounded-lg border bg-card shadow-md` を書いた要素を
`components/admin/folders-manager.tsx` に足して、**まだ赤が出ること**を見てから戻した。

## 3. 実装で構造的に守る（気をつける、で守らない）

🚨 **「レビューで気をつける」では必ず破れる。** 部品ごとに正しく作られていても、
組み合わせで破れるのがこの問題の性質だから。

やること:

1. **面を出すコンポーネントを1つに限定する**（例 `<Surface>`）。
   `Card` を直接使わせず、必ずこれを通す
2. **`<Surface>` は入れ子を検出したら開発時に警告する**
   （React の Context で「自分は面の中か」を持ち回り、レベル2 で `console.warn`）
3. **入力系は面の中に入ったら自動で罫線を外す**（同じ Context を見る）
4. **Storybook に「面の中に面」「面の中の入力欄」のケースを置き**、目で見て確認できるようにする

## 4. 手本

X の実装（`https://mobbin.com/flows/d9ad499d-c39a-4a80-ac48-5b03d5454b60`）:

- **リストは罫線で囲まない。** 行と行の間の Divider だけ
- 入力欄は**背景色で区別**し、罫線を持たない
- 面が重なるのは**モーダル**のときだけ（それも1段）

---

## 5. レビュー観点

- [ ] 面（罫線・背景・影のどれかを持つもの）が**2段以上**重なっていないか
- [ ] 面の中の入力欄が、**面と同じ境界の出し方**をしていないか（罫線 in 罫線）
- [ ] padding を持つ器の中で、中身も padding を持っていないか
- [ ] SP 幅でカードになっていないか（Divider になっているか）
- [ ] 「空です」の表示のために面を増やしていないか
- [ ] **コンポーネント単体ではなく、実際の画面を見て確認したか**（これが本題）
