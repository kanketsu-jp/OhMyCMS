# 否定形の検証は「検出できること」を先に確かめる

## 背景

このプロジェクトの受入基準は否定形が多い。「他人の行が見えない」「script が実行されない」
「イメージに Node.js が入っていない」——どれも**何かが起きないこと**を確かめる形をしている。

否定形は放っておくと必ず通る。**1日で5回、別々の理由で空振りした。**

| # | 何が起きたか | なぜ「出なかった」のか |
|---|---|---|
| 1 | 一覧に他人の行が混ざらないので PASS と判定しかけた | **データが無かった**。A がまだ1行も作っていなかったので 0 件が返っていた |
| 2 | `/api/health` が 200 なので Docker は健全と報告した | **機能が動いていなかった**。health は DB しか見ておらず、`sharp` は壊れたまま 500 を返していた |
| 3 | リレーション経由の漏れが「まだ塞がっていない」と報告した | **古いものを見ていた**。稼働中のコンテナが修正の3時間前のビルドだった |
| 4 | `command -v node` が値を返すので「Node.js が残っている」と判定しかけた | **判定基準が間違っていた**。`oven/bun` が `node` という名前で bun へのシンボリックリンクを置いている |
| 5 | `curl :3101/api/health` が 200 なので「本番スタックは動いている」と報告した | **判定基準が事実の一部しか写していなかった**。API は通るが、内部 fetch をする管理画面は全ページ 500 だった |
| 6 | 二重送信の検査を書き、「未防御は 16 件」と数えた | **検査の網目から漏れていた**。`method: "POST"` のように引用符が続く前提の正規表現だったため、`method: editing ? "PATCH" : "POST"` を見落とした。本当は 17 件だった |

1〜3 は「本当は見えるはずのものが見えていない」、4 と 5 は「壊れているのに通ったように見える」。
向きは逆だが、**判定基準が事実を写していない**という点で同じものだ。

6 はどちらとも違う**3つ目の型**で、**検査そのものに死角がある**。
1〜5 は「測り方が事実を写していない」だが、6 は**測りに行っていない**。
見落とした 1 件は権限の保存（`policy-permissions-manager.tsx:106`）で、
**このリストの中でいちばん壊れると困る経路**だった。

🚨 **検査を書くと安心してしまう。** 落とせる形にした瞬間、
その出力（16 件）を**事実そのものとして扱ってしまった**。
検査は事実ではなく**事実についての主張**であり、他の主張と同じだけ疑う必要がある。

5 は**規約を書いた側**が踏んだ。ポートの割り当てを決めるとき、`/api/health` が 200 なのを見て
「一致させなくても動く」と結論した。実際は `/admin` が 500 で、**MVP ⑤ が RED のまま数時間過ぎた**。
`AGENTS.md §4`「curl でソースが取れたを表示確認と書かない」は作業者向けに書かれていたが、
**規約や決定を書くときにも同じだけ効く**。

🚨 **判定基準そのものが間違っていると、PASS も FAIL も意味を持たない。**
3 は「正しい修正を差し戻す」ところまで行きかけた。**偽の赤は偽の緑と同じくらい高くつく。**

## 決めたこと

**否定形を確かめる前に、その手順が本当に検出できることを示す。**

具体的には、否定形の隣に必ず次のどれかを置く。

### 1. 対照実験（いちばん強い）

**同じ手順で、検出されるはずのものを実際に検出してみせる。**

SVG の XSS を確かめたときは、`Content-Disposition: attachment` が付いていて
「script が実行されなかった」ことを見た。それだけでは、私の検出方法が壊れているのか
防御が効いているのか区別できない。そこで**同じ SVG を正しい MIME で inline 配信して**、
`document.title` が `PWNED-BY-SVG` に変わることを確認した。
ペイロードは生きていて、検出方法も動く。**だから「実行されなかった」は本物だと言える。**

権限の検証も同じ形にしている。A では `null` が返ることの隣に、
**管理者では同じ URL で値が返る**ことを必ず置く。データは実在していて、
クエリの組み方も正しい。**遮断だけが効いている**と言える。

### 2. 肯定形とセットにする

「他人の行が見えない」は、**自分の行は見える**ことと対にして初めて意味を持つ。
全部 403 にすれば否定形はすべて通るが、それは CMS として壊れている。

### 3. 判定基準が事実を写しているか疑う

`command -v node` は「Node.js があるか」を測っていない。「`node` という名前の
実行可能ファイルが PATH にあるか」を測っている。この2つは違う。

  ❌ `command -v node || echo NO_NODE`  … シムがあると「ある」に見える
  ✅ `find / -name node -type f`         … 実体のバイナリを数える（0 件だった）
  ✅ `readlink -f $(command -v node)`    … 正体を見る（`/usr/local/bin/bun` だった）

同じ形で失敗したものがもう1つある。ビルドの鮮度を
「修正コミットで入った関数名を grep して数える」で判定しようとしたが、
その関数は **export されていない module-local 関数**で、Turbopack が名前を圧縮するため
ビルド成果物には残らない。**最新でも 0 件**になる。

  ✅ ビルドコンテキストを `git archive <sha>` にする（コンテキストがその commit そのものになる）
  ✅ イメージに `LABEL org.opencontainers.image.revision` を焼き、`docker inspect` で読む
  ✅ それでも最後は**振る舞い**で確かめる（管理者では見えて一般ユーザーでは見えない）

**ラベルは着手前の足切り、対照実験は結論の担保**。役割が違うので両方置く。

### 4. 検査を書いたら、**検査の網目**を疑う

検査スクリプトを書くと「これで漏れない」と感じるが、それは**書いた人が想像できた書き方**しか
捕まえない。想像の外にある書き方は、**違反として報告されずに消える**。ゼロ件は
「違反が無い」ではなく「私の正規表現に当たらなかった」かもしれない。

同じことを一日に二度やった。

  ❌ `/className=\{?["'\`]/`                     … `className={cn("…")}` を読み落とす（50 箇所が無検査だった）
  ❌ `/method:\s*["'](POST|PATCH|DELETE)["']/`  … `method: editing ? "PATCH" : "POST"` を読み落とす
  ✅ `className` 以降の**文字列リテラルを全部連結**してから判定する
  ✅ 「`method:` と**同じ行に**変更系の語がある」で見る（値の形を仮定しない）

どちらも**値がどう書かれるかを仮定した**のが原因だった。
**構文の形を仮定するほど網目は粗くなる。** 迷ったら、粗く拾って**許容リストで絞る**方に倒す
（面の検査は実際にこの形にしてある）。

確かめ方は §1 と同じで、**対照実験**が要る。

  - **わざと違反を書いて、検査が落ちることを見る**（面の検査はこれで網目の穴が2つ見つかった）
  - **検査が数えた件数を、別の手段で数え直す**（`rg` の素の件数と突き合わせる）
  - **件数が想定と1件でも違ったら、差分の1件を必ず開く**

🚨 **検査を新設したコミットでは、検査が落ちるところまで見てからコミットする。**
「違反なし」で終わったコミットは、**検査が動いた証拠を何も残していない**。

## やらないこと

- **`unverified` を放置しない。** 確かめられないなら「なぜ確かめられないか」を書く。
  「たぶん大丈夫」は書かない
- **否定形だけの報告をしない。** 🟢 と 🔴 を並べて出す
- **1つの指標で「動いている」と言わない。** `/api/health` は DB しか見ていない。
  画面が描画されるかは**認証つきで実際にページを引いて確かめる**（本文のバイト数まで見る）
