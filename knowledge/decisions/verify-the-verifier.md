# 否定形の検証は「検出できること」を先に確かめる

## 背景

このプロジェクトの受入基準は否定形が多い。「他人の行が見えない」「script が実行されない」
「イメージに Node.js が入っていない」——どれも**何かが起きないこと**を確かめる形をしている。

否定形は放っておくと必ず通る。**1日で5回、別々の理由で空振りした。**

| # | 何が起きたか | なぜ「出なかった」のか |
|---|---|---|
| 1 | 一覧に他人の行が混ざらないので PASS と判定しかけた | **データが無かった**。A がまだ1行も作っていなかったので 0 件が返っていた |
| 2 | `/api/health` が 200 なので Docker は健全と報告した | **機能が動いていなかった**。health は DB しか見ておらず、`sharp` は壊れたまま 500 を返していた |
| 3 | リレーション経由の漏れが「まだ塞がっていない」と報告した | **古いものを見ていた**。稼働中のコンテナが修正の3時間前のビルドだった |
| 4 | `command -v node` が値を返すので「Node.js が残っている」と判定しかけた | **判定基準が間違っていた**。`oven/bun` が `node` という名前で bun へのシンボリックリンクを置いている |
| 5 | `curl :3101/api/health` が 200 なので「本番スタックは動いている」と報告した | **判定基準が事実の一部しか写していなかった**。API は通るが、内部 fetch をする管理画面は全ページ 500 だった |
| 6 | 二重送信の検査を書き、「未防御は 16 件」と数えた | **検査の網目から漏れていた**。`method: "POST"` のように引用符が続く前提の正規表現だったため、`method: editing ? "PATCH" : "POST"` を見落とした。本当は 17 件だった |
| 7 | 面の監査が「深さ=1 / あふれ=0px」を返したので合格と判定した | **壊れ方が基準の網の外だった**。要素の幅が潰れていたが、**幅が狭いと面の深さは正しく、はみ出しも起きない**。すべての基準を満たしたまま画面は読めなかった |
| 8 | 全体設定の「既定の言語」を保存できたので受入基準を通ったと判定した | **保存は見たが反映を見ていなかった**。値も出所（環境変数→この設定で保存済み）も画面に正しく出るのに、`getLocale()` がその設定をどこからも読んでおらず、**選んでも表示言語は何も変わらなかった** |
| 9 | ブラウザで幅を測り「body=0 / main=32 / input=102」と報告した | 🚨 **測定器そのものが壊れていた**。`window.innerWidth` が **1px** だった（`Emulation.setDeviceMetricsOverride` で 390 を指定したが、ヘッドレスのウィンドウが 1px のままだった）。**html から順に 0 になっていたのは、アプリでなく計測環境の話** |
| 10 | 「消した名前で作り直せるか」を測り、`duplicate key` が**出ない**ことを見て「🟢 作れた」と判定した | 🚨 **「無い」で判定すると、エラーも「無い」に入る**。実際は `relation "ohmycms_labels" does not exist` が返っており、**作れていないのに緑**だった（migrate が落ちていたのに出力を捨てていた）。→ **`INSERT 0 1` との完全一致**で判定し直した（2026-08-16） |

1〜3 は「本当は見えるはずのものが見えていない」、4 と 5 は「壊れているのに通ったように見える」。
向きは逆だが、**判定基準が事実を写していない**という点で同じものだ。

6 はどちらとも違う**3つ目の型**で、**検査そのものに死角がある**。
1〜5 は「測り方が事実を写していない」だが、6 は**測りに行っていない**。
見落とした 1 件は権限の保存（`policy-permissions-manager.tsx:106`）で、
**このリストの中でいちばん壊れると困る経路**だった。

🚨 **検査を書くと安心してしまう。** 落とせる形にした瞬間、
その出力（16 件）を**事実そのものとして扱ってしまった**。
検査は事実ではなく**事実についての主張**であり、他の主張と同じだけ疑う必要がある。

5 は**規約を書いた側**が踏んだ。ポートの割り当てを決めるとき、`/api/health` が 200 なのを見て
「一致させなくても動く」と結論した。実際は `/admin` が 500 で、**MVP ⑤ が RED のまま数時間過ぎた**。
`AGENTS.md §4`「curl でソースが取れたを表示確認と書かない」は作業者向けに書かれていたが、
**規約や決定を書くときにも同じだけ効く**。

8 は 1〜6 のどれとも違う**4つ目の型**で、**確かめた対象がそもそも別物**だった。
1〜5 は「測り方が事実を写していない」、6 は「測りに行っていない」、
**8 は「隣にあるものを測って、目的のものを測った気になっていた」**。

設定機能に固有の形をしている。設定画面は**保存できたことを正しく表示する**（値が変わり、
出所が「環境変数の初期値」から「この設定で保存済み」へ変わる）。ここまでは全部正しい。
だから**画面を見ているかぎり、いつまでも気づかない**。欠けていたのは
「保存した値を**誰かが読んでいるか**」だけで、そこは画面に出ない。

実際、`default_locale` は保存も表示も出所の解決も完璧に動いていて、
**`getLocale()` からだけ参照が無かった**。同じ設定テーブルの中で、
`project_name` は繋がっていて `default_locale` は繋がっていない、という状態を
**受入基準4「環境変数だけで起動でき、その後 GUI で上書きできる」を通した**と報告していた。

🚨 **設定項目は「保存できる」ではなく「保存したら実際の振る舞いが変わる」を1件ずつ見る。**
項目が5つあるなら5回見る。1つ動いたから他も動くだろう、は通用しない
（実際 `project_color` と `project_logo` は、この確認で**どこからも読まれていない**と分かった）。
見るのは設定画面ではなく、**その設定が効くはずの画面**（言語ならログイン画面の文言、
注意書きならログイン画面の表示、色なら実際に描画された色）。

🚨 **判定基準そのものが間違っていると、PASS も FAIL も意味を持たない。**
3 は「正しい修正を差し戻す」ところまで行きかけた。**偽の赤は偽の緑と同じくらい高くつく。**

## 決めたこと

**否定形を確かめる前に、その手順が本当に検出できることを示す。**

具体的には、否定形の隣に必ず次のどれかを置く。

### 1. 対照実験（いちばん強い）

**同じ手順で、検出されるはずのものを実際に検出してみせる。**

SVG の XSS を確かめたときは、`Content-Disposition: attachment` が付いていて
「script が実行されなかった」ことを見た。それだけでは、私の検出方法が壊れているのか
防御が効いているのか区別できない。そこで**同じ SVG を正しい MIME で inline 配信して**、
`document.title` が `PWNED-BY-SVG` に変わることを確認した。
ペイロードは生きていて、検出方法も動く。**だから「実行されなかった」は本物だと言える。**

権限の検証も同じ形にしている。A では `null` が返ることの隣に、
**管理者では同じ URL で値が返る**ことを必ず置く。データは実在していて、
クエリの組み方も正しい。**遮断だけが効いている**と言える。

### 2. 肯定形とセットにする

「他人の行が見えない」は、**自分の行は見える**ことと対にして初めて意味を持つ。
全部 403 にすれば否定形はすべて通るが、それは CMS として壊れている。

### 3. 判定基準が事実を写しているか疑う

`command -v node` は「Node.js があるか」を測っていない。「`node` という名前の
実行可能ファイルが PATH にあるか」を測っている。この2つは違う。

  ❌ `command -v node || echo NO_NODE`  … シムがあると「ある」に見える
  ✅ `find / -name node -type f`         … 実体のバイナリを数える（0 件だった）
  ✅ `readlink -f $(command -v node)`    … 正体を見る（`/usr/local/bin/bun` だった）

同じ形で失敗したものがもう1つある。ビルドの鮮度を
「修正コミットで入った関数名を grep して数える」で判定しようとしたが、
その関数は **export されていない module-local 関数**で、Turbopack が名前を圧縮するため
ビルド成果物には残らない。**最新でも 0 件**になる。

  ✅ ビルドコンテキストを `git archive <sha>` にする（コンテキストがその commit そのものになる）
  ✅ イメージに `LABEL org.opencontainers.image.revision` を焼き、`docker inspect` で読む
  ✅ それでも最後は**振る舞い**で確かめる（管理者では見えて一般ユーザーでは見えない）

**ラベルは着手前の足切り、対照実験は結論の担保**。役割が違うので両方置く。

### 4. 対象に「自分の版」を名乗らせる

ラベルは `docker inspect` でしか読めない。**測る側がアプリから読めるほうが確実**なので、
ビルド時の SHA を実行時の環境変数として渡し、`/api/version` が返すようにした
（`OHMYCMS_GIT_COMMIT`。`docker/Dockerfile` と `compose.yml` / `acceptance/compose.acceptance.yml`）。

受入ハーネスは「リポジトリの HEAD」を対象の版として出していたが、
`studio-acc` は `COPY . .` で**ビルド時のコードを焼き込む**（マウントではない）ので、
HEAD と中身が一致するとは限らない。**古い対象の結果を、新しい版の結果として記録してしまう。**
実際に「リポジトリ=ac08384 / 対象の版=b3331e1c」という食い違いが見出しに出た。

    GIT_SHA=$(git rev-parse HEAD) GIT_DIRTY=$(git status --porcelain | wc -l) \
      docker compose up -d --build

🚨 **渡し忘れると `unknown` になる。「不明」を「一致」と読まないこと。**

配線するときに踏んだ罠が2つある。どちらも**「イメージには値があるのにコンテナでは空」**という形で出る:

1. **`ENV` の継続行（`\`）の中では `ARG` が展開されない。** 実測で空文字になった。

        ENV A=1 \
            OHMYCMS_GIT_COMMIT=$GIT_SHA     # ❌ 空になる
        ENV OHMYCMS_GIT_COMMIT=$GIT_SHA     # ✅ 単独行なら展開される

2. 🚨 **compose の `environment` は「未設定なら渡さない」ではなく「空文字で上書きする」。**
   `OHMYCMS_GIT_COMMIT: ${OHMYCMS_GIT_COMMIT:-}` と書いてあると、
   **Dockerfile の `ENV` を空で潰す**。イメージ側の値を残したいなら既定値を繋ぐ:

        OHMYCMS_GIT_COMMIT: ${OHMYCMS_GIT_COMMIT:-${GIT_SHA:-unknown}}

   このときも**イメージを調べれば値が入っている**ので、イメージだけ見ると正しく見える。
   **コンテナの `printenv` まで見ること。**

### 5. 検査を書いたら、**検査の網目**を疑う

検査スクリプトを書くと「これで漏れない」と感じるが、それは**書いた人が想像できた書き方**しか
捕まえない。想像の外にある書き方は、**違反として報告されずに消える**。ゼロ件は
「違反が無い」ではなく「私の正規表現に当たらなかった」かもしれない。

同じことを一日に二度やった。

  ❌ `/className=\{?["'\`]/`                     … `className={cn("…")}` を読み落とす（50 箇所が無検査だった）
  ❌ `/method:\s*["'](POST|PATCH|DELETE)["']/`  … `method: editing ? "PATCH" : "POST"` を読み落とす
  ✅ `className` 以降の**文字列リテラルを全部連結**してから判定する
  ✅ 「`method:` と**同じ行に**変更系の語がある」で見る（値の形を仮定しない）

どちらも**値がどう書かれるかを仮定した**のが原因だった。
**構文の形を仮定するほど網目は粗くなる。** 迷ったら、粗く拾って**許容リストで絞る**方に倒す
（面の検査は実際にこの形にしてある）。

#### 🚨 同じことが「検査」でなく「**防御**」でも起きる（2026-08-14）

SAML のログイン後の戻り先を、**正規表現で形を見て**判定していた。

    /^\/(?!\/)[^\s]*$/     「`/` で始まり、2文字目が `/` ではない」

**3 通り抜けた**（実測。ブラウザの飛び先まで確認した）:

    "/\evil.com"     → http://evil.com/    特別なスキームでは `\` が `/` として解釈される
    "/\/evil.com"    → http://evil.com/
    "/..//evil.com"   → 正規化されて "//evil.com" になり、別サイトへ出る

どれも**上の条件を満たしている**。戻り先は **IdP を往復して戻ってくる**ので
**攻撃者が中身を決められる**値であり、「ログインしたら偽サイトに着く」が作れていた。

    ❌ 形を仮定して弾く                          … 仮定の外の書き方が素通りする
    ✅ **実際に解決してから、結果を見る**        … `new URL(値, 基準)` のオリジンと、先頭の `//` を見る

🚨 **このとき、否定形の受入は 10 件そろえて全部通っていた。**
署名の改竄・署名の削除・リプレイ・Audience・期限——どれも対照つきで確かめてあった。
**それでも戻り先だけは「形の判定」で済ませていた。**
指摘したのは**バックグラウンドのセキュリティレビュー**で、**受入項目にも入っていなかった**。

**受入 N/N は「私が思いついた攻撃を N 件並べた」でしかない。**
数が多いことは網羅の証拠にならないので、**自分と別の目**（別の担当・自動レビュー・攻撃演習）を
**必ず1つ通す**。

#### 🚨 型として: **代理を測らない。見たいことを直接測る**

同じ日に、**3人が別々の場所で同じ誤りを踏んだ**。共通しているのは
**「見たいこと」の代わりに「見やすいもの」を測っていた**こと。

    saml   … 見たいのは「**ブラウザがどこへ行くか**」／測っていたのは**文字列の形**
    design … 見たいのは「**影が見えるか**」    ／測っていたのは**値が `"none"` でないか**
    design … 見たいのは「**折り返しているか**」／測っていたのは**幅の絶対値**

**本物は測りにくいので、測りやすい代理を測った**——という一点で揃う。
そして🚨 **代理は必ずどこかでずれる。** ずれる場所は代理ごとに違うので、
**代理を使う限り、抜けを数え上げることはできない。**

| 何を判定したかったか | ❌ 形で判定した | 何が抜けたか | ✅ 意味で判定する |
|---|---|---|---|
| **この戻り先は自サイト内か**（saml） | `/^\/(?!\/)…$/` で「`/` 始まり `//` でない」 | `"/\evil.com"` `"/..//evil.com"` が別サイトへ出た | **`new URL()` で解析**し、オリジンと先頭 `//` を見る |
| **この文字は縦積みに潰れているか**（design） | 幅が **40px 未満**という絶対値 | 下部ナビのラベルは **10px** なので `"Home"` は 28px でも1行に収まる。**フォントサイズを見ていなかった** | **症状そのもの**。`height > fontSize×2`（2行を超えている）かつ `width < fontSize×2.5` |
| **この要素は影を持つか**（design） | `boxShadow !== "none"`（**番兵と比べただけ**） | Tailwind は影が無くても `rgba(0,0,0,0) 0px 0px 0px 0px, …` を置くので、**"none" ではない → 影がある**になった | レイヤーごとに分解し、**色が透明でない かつ ずれ・ぼかしが 0 でない**ものがあるか |

**代理の判定は、代理と本物がずれる場合を1つでも知らないと穴になる。** そして
🚨 **知らないずれ方は、定義上、思いつけない**（`\` が `/` として解釈されるのも、
`..//` が `//` に正規化されるのも、Tailwind が透明な影を置くのも、**知らなければ検査に書けない**）。

🚨 **3件とも「代理そのものは正しく動いていた」**のが厄介なところ。
正規表現は書いたとおりに一致し、`!== "none"` は正しく比較し、`< 40` は正しく比べていた。
**壊れていたのは、代理と本物の対応づけ**だけで、**コードを読んでも見つからない。**

**解析して意味で判定すれば、書き方の網羅が要らなくなる。**
`new URL()` はブラウザと同じ規則で解決するので、**ブラウザが行く先とずれない**。
これが「形を全部数え上げる」より強い理由は、**数え上げの完全性を人間が保証しなくてよくなる**こと。

#### 実務で最初に効くところ

🚨 **戻り先（リダイレクト先）を外から受け取るときは、必ず `safeRelativePath()` を通す**
（`apps/studio/lib/auth/urls.ts`）。`?next=` / `?redirect=` / SAML の `RelayState` /
OAuth の `state` に載せたパス——**利用者以外が値を決められる経路はすべて対象**。
**認証共通の場所に置いてある**（SAML の下に隠すと、次に書く人が存在に気づかず
同じ正規表現を書き直す）。

（design の2件は本人の申告と訂正による）

確かめ方は §1 と同じで、**対照実験**が要る。

  - **わざと違反を書いて、検査が落ちることを見る**（面の検査はこれで網目の穴が2つ見つかった）
  - **検査が数えた件数を、別の手段で数え直す**（`rg` の素の件数と突き合わせる）
  - **件数が想定と1件でも違ったら、差分の1件を必ず開く**

🚨 **検査を新設したコミットでは、検査が落ちるところまで見てからコミットする。**
「違反なし」で終わったコミットは、**検査が動いた証拠を何も残していない**。

### 6. **測定器が生きているか**を、測る前に1行で確かめる

司令塔がブラウザで幅を測り「`body=0` / `main=32` / `input=102`」と報告して、
実装担当に修正を2回指示した。実際は **`window.innerWidth` が 1px** だった。
`Emulation.setDeviceMetricsOverride` で 390 を指定したのに、ヘッドレスのウィンドウが 1px のままで、
**`html` から順に 0 になっていたのは計測環境の話**だった。

  ✅ **測る前に `window.innerWidth` / `clientWidth` が意図した値かを出力する。** 違ったら中断する
  ✅ **「測った対象」を必ず出力する**（`52×24px` が嘘だと気づけるのはこれがあるとき）
  ✅ **測定器が生きている指標を、結果の中に混ぜておく**
     実例: 同じページの sp と pc で「表示されているナビの数」が **0 と 12** に割れていた。
     これは**2つのビューポートが実際に違う幅だったときにしか起きない**。
     幅が潰れていれば両方 0 になるので、**割れていること自体が測定器の生存証明**になっていた

#### 🚨 壊れた測定器が、正しい結論を指すことがある

上の誤報のあと、実装担当が**条件を揃えた対照実験**で測り直したところ:

```
親 390px / 左右 padding 16 → 使える幅は 358
  修正前（外側に幅なし）   outer = 16px   section = 16px
  修正後（外側に w-full）  outer = 358px  section = 358px
```

**「0」ではなく「16px」だった。** 16px は **「あ」1文字の幅**で、
オーナーが報告した「文字が1文字ずつ縦に並ぶ」症状と一致する。

つまり **数字は誤りだったが、診断（外側の器に幅が無い）は正しかった** ——**と、この時点では思われた。**

#### 🚨 その「裏取り」も不完全だった（同じ日に3人が3通りの数字を出した）

上の対照実験には、**実物のクラスが1つ落ちていた**:

> 🚨 **`@container/surface`（`container-type: inline-size`）を入れ忘れていた。**
> **コンテナは中の割合計算の基準が変わる**ので、16px という数字は実物と違う可能性がある。

同じ件で**デザイン担当は 0**、**実装担当は 16px** を出した。**どちらも不完全な再現**で、
**「製品でそれが起きた」の証明にはなっていない。**

#### 🚨 決着: 不具合は本物だった。撤回の方が行き過ぎだった

デザイン担当が、**撤回のあとに自分で測り直して**決着させた。前2回の再現の不備を全部埋めてある:

- CSS = **稼働中のサーバが実際に配っているバンドル**（405KB）をそのままダウンロードして使用
- マークアップ = **`git show <修正コミット>^` から取った修正前のクラス文字列そのまま**
- 修正前 / 修正後を**同じページに並べて同時に測定**
- 🚨 **測定器を先に確認**（`window.innerWidth` = 390 を確認してから測った）

```
              main   outer   section   p(幅)   p(高さ)
修正前        390     0       0        0       480px
修正後        390    358     358      358      20px
```

🚨 **修正前は幅0。段落の高さが 480px = 文字が1文字ずつ縦に並ぶ。オーナーが見た症状そのもの。**

**「誤報」ではなく「壊れた計測器で本物を指した」が正確。**
測定**方法**は壊れていたが、指していた**対象**は実在の欠陥だった。

0 と 16px の食い違いも解けた。**`container-type: inline-size` があると中身が幅に寄与しなくなるので
0 まで落ちる。入れると 0、抜くと 16。あの1クラスが挙動を決めていた。**

**確定した事実:**

| | 状態 |
|---|---|
| 明朝体（`--font-sans` の自己参照） | ✅ **本物**。`Times` → `Noto Sans`（computed style で実測） |
| **外側の器に幅が無く 0 に潰れる** | ✅ **本物**。実バンドル + 修正前のクラスで再現・測定済み |
| オーナーの画面で見えていたのがどちらか | 🚨 **`unverified`**（スマホ実機のログが無い）。**どちらも本物で、どちらも直っている** |

### 🚨 7. 失敗した対象をあとから調べると、**失敗そのものが証拠を消している**ことがある（2026-08-14）

これまでの型は全部「**測る対象が違った**」だった
（curl と画面 / `command -v` と実体 / ディスクと git / 隣の設定項目）。
これは違って、**対象は正しいのに、調べに行った時点で証拠が無くなっている**。

SAML の応答が ACS で 401 になったので、同じ応答を手元で検証し直した。返ってきたのは
`InResponseTo is not valid`——**「送った要求と対応していない」という意味**の失敗だった。
ところが実際の一次原因は別で、`InResponseTo` は**送った ID と一致していた**（突き合わせて確認済み）。

からくりは、**検証が失敗すると、ライブラリが `InResponseTo` の台帳の行を削除する**こと。

    1回目（ACS）    … 本当の原因で失敗 → **その拍子に台帳の行が消える**
    2回目（手元）   … 台帳が空なので「InResponseTo が無い」で失敗
                      → **一次原因と無関係な、二次的な症状しか見えない**

**「同じ入力でもう一度試す」が成り立たない。** 1回目が状態を変えているので、
2回目は**別の実験**になっている。

  ✅ **失敗する経路を叩く前に、証拠が残る経路で1回測る**
     （実際には「ACS を叩かずに応答だけ取る」経路を作って、そこで検証した）
  ✅ **失敗時に状態を変えていないか**を、ライブラリ・DB・キャッシュについて先に確かめる
  ✅ **1回目の失敗のログを取る。** 「あとで再現すればいい」が効かない場面がある

🚨 **これは調査の話であって、実装の欠陥ではない。** ライブラリが行を消すのは正しい
（使い捨ての値を残さない）。**正しい実装が、調査を難しくすることがある**というだけで、
**そのことを知らないと、存在しない原因を追いかける**。

### 8. 🚨 反証が出たときも、**検証してから**引き下がる

この一件で、司令塔は**2回撤回し、2回とも自分では測っていなかった**。

1. 実装担当の「再現しない」を受けて数字を撤回 → 実装担当は**別のページ**を測っていた
2. 実装担当の自己申告を受けて診断まで撤回 → その自己申告も**不完全な再現**の話だった

デザイン担当も同じ型を踏み、自己申告している:

> 🚨 **反証が出たときに、検証せずに撤回した。**
> 「間違っていた」と言われて、**確かめずに引き下がるのも同じ誤り**だった。
> **肯定するときも否定するときも、測ってから言う。撤回にも根拠が要る。**

**主張に根拠が要るのと同じだけ、撤回にも根拠が要る。**
「間違いでした」は、**それ自体が新しい主張**であって、無条件に安全な逃げ道ではない。

  - ✅ 撤回する前に「**では正しい値は何か**」を自分で測る
  - ✅ 撤回できないなら「**私の測定は信用できない。誰か測り直してほしい**」と書く
    （**結論を反転させず、根拠だけを取り下げる**）
  - ❌ 反証を受けて即座に結論ごと反転させる（**今回これで、本物の不具合を2回見失いかけた**）

  - 🚨 **数字を撤回するとき、診断も一緒に疑う。** 「数字は誤りだが診断は正しい」で止めると、
    **誤った診断がそのまま残る**（実際にここで一度止めてしまった）
  - 🚨 **再現用のミニ HTML は、実物のクラスを1つでも落とすと別物になる。**
    片方は `@container` を落とし、片方は製品のレイアウトを落とした。
    **再現を作ったら「何を写して、何を省いたか」を並べて書く。**
    省いた1つが、まさに挙動を決めている要素かもしれない
  - **撤回するときは**どちらを撤回するかを分ける。ただし**片方だけ残して安心しない**
  - 🚨 **逆もある。合っている数字から誤った診断が出る。**
    実例: 「SVG は attachment が付く / HTML は付かない」は**正しい観測**だったが、
    そこから出した「HTML だけの問題」という診断は誤りで、**SVG 側にも同じ穴があった**
    （MIME を偽装すると外れる）

#### 「再現しない」と言うときも対照実験が要る

同じ件で、実装担当は「再現しない」と2回報告した。しかし測っていたのは
**既に別の担当が書き換えて `Surface` を使わなくなったページ**で、
**再現するはずの条件を一度も組み立てていなかった**。

**否定形の報告（再現しない・違反なし・漏れていない）にも、§1 の対照実験を適用する。**
「再現しない」は「**再現する条件を作って、それでも起きなかった**」で初めて言える。

### 9. 🚨 対照（肯定形）そのものが妥当かを確かめる

§1〜§2 で「否定形は肯定形とセットにする」「対照を先に置く」と決めた。
だが今度は**その対照そのものが壊れていた**。

受入担当が「小さい画像にブラーが付かない＝実装の不具合」と報告した。真因は
**対照に使っていた 32x32 の PNG のバイト列が壊れていた**（IDAT の CRC 不一致・zlib で展開できない）。
実装は仕様どおり（**壊れた画像はブラーを作らないが、アップロード自体は成功する**）だった。

受入担当の自己申告:

> 「PNG を上げて取り出せる」は PASS していたが、それは**バイト列を往復させていただけ**で、
> **画像として妥当かは一度も確かめていなかった。**

🚨 **決定的な証拠**: 対照を組み立て直した瞬間、配信が **`image/png` → `image/webp`** に変わった。
本物の画像になったので圧縮されるようになった＝**それまでは（画像でなく）バイト列を往復していただけ**。

  ✅ **対照は「リテラルを貼る」のでなく「組み立てる」**（PNG なら CRC・IDAT が正しくなるように）
  ✅ **対照が「意図した性質」を実際に持つか確かめる**（画像なら本当に画像として妥当か）
  ✅ **肯定形が本当に肯定を示しているか**を、独立の手段で確認する
     （この件では zlib で IDAT を独立展開して「他の PNG は壊れていない」まで確かめた）

**§5 は「測定器が壊れていた」。この §6 は「測定に使う"正しいはずの入力"が壊れていた」。**
判定器・測定器・対照——**確かめる側の道具は、確かめる対象と同じだけ疑う。**

#### 疑われた側が、疑った側の道具を調べて正す

この件で、実装を「不具合だ」と名指しされた担当（storage）が、
**自分を守るのでなく、名指しした側（受入担当）のバイト列まで調べて真因を出した。**
「私の実装は正しい」で止めれば、受入担当は存在しない不具合を追い続けた。

**実装を疑われたら、相手の測定を調べる。** 反論でなく、共同で真因に向かう。

## やらないこと

- **`unverified` を放置しない。** 確かめられないなら「なぜ確かめられないか」を書く。
  「たぶん大丈夫」は書かない
- **否定形だけの報告をしない。** 🟢 と 🔴 を並べて出す
- **1つの指標で「動いている」と言わない。** `/api/health` は DB しか見ていない。
  画面が描画されるかは**認証つきで実際にページを引いて確かめる**（本文のバイト数まで見る）
