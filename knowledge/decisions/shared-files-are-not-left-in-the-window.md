# 共有ファイルは、窓に自分の行を置かない

> 由来: 2026-08-16。共有の決定ドキュメントを編集し、**予告を出して 60〜120 秒待っている間に**、
> 別の担当が同じファイルへ `git add` を打ち、**私の未コミットの 7 行がその人のコミットに入った**。
> 内容は失われていないが、**「description が『color は未検証』を落としていた」という
> 別の件名のコミットの中**に在るので、`git log` からは辿れない。
>
> 🚨 **誰も規律を破っていない。** 巻き込んだ側も巻き込まれた側も、その日の規律どおりに動いた。
> **規律のほうが、ファイル単位までしか守っていなかった。**
>
> 関連: [共有資源は同時に1つしか使わない](./shared-resources-are-exclusive.md)（**資源**単位の排他） /
> [検査は死角を宣言する](./checks-must-declare-blind-spots.md)（**ファイル**単位の巻き込みの記録）

## 0. 何が守れて、何が守れないか（実測）

```
🟢 守れる … **他のファイル**を巻き込まない
            （`git add <パス>` / `git commit --only <パス>`）
🚨 守れない … **同じファイルの、他人の未コミット行**
```

【測った 2026-08-16・台で再現】同じファイルに他人の行と自分の行を置いて `git commit --only <そのファイル>`:

```
コミットに入った … 他人 1 / 自分 1（**両方**）／ 残った差分 **0 行**
🚨 `git add` を 1 度も打たずに `--only` だけでも同じ（**他人の行が staged でも unstaged でも運ぶ**）
＝ **`--only` が絞るのは「どのファイルか」だけで、「そのファイルの誰の行か」ではない**
```

## 1. 守り（強い順）

### 🥇 置かない — **予告 → 編集 → `git commit --only` を直接打つ（`git add` を使わない）**

```
❌ 編集 → 予告 → 60〜120 秒待つ → add + commit   ← 🚨 窓の間、自分の行が無防備に置かれる
❌ 予告 → 編集 → **add** → commit                ← 🚨 **add と commit の間にも窓が在る**
✅ 予告を編集より前に出す → 編集 → **`git commit --only <パス…> -m "…"`**（**add を打たない**）
```

🚨 **【2026-08-17 に反転】最初この節は「予告 → 編集 → add → commit を 1 手」と書いていた。**
**それでは足りない。`add` と `commit` の間に門が数秒走り、その隙間が消えていなかった。**

```
実際に起きたこと … ある担当が `add` して待っている間に、別の担当が素の `commit` を打ち、
   🚨 **待っていた側の 10 行が、打った側のコミットに入った**
   （🚨 待っていた側のコミット自体は `fatal: cannot lock ref` で**失敗している**。
     ＝ **コミットは失敗したのに、変更は他人のコミットで HEAD に入った**）
🟢 司令塔が自分の台で再現:
   🔴 B が `add` してから素の `commit` … 🚨 **A が add した別ファイルが入る**
   🟢 B が `git commit --only <自分のパス>`（**add せず**）… **A のものは入らない**
      🟢 対照 B 自身のファイルは入る ／ A の add はそのまま残る
＝ 🚨 **漏れているのは共有された索引**（`.git/index` は 13 ペインで 1 つしかない）
```

🚨 **既に `add` してしまっているものが在るなら `git reset -q <パス>`**（**作業ツリーは変わらない**）。
🚨 **門の最中に HEAD が動くと `fatal: cannot lock ref` で失敗する。それは正しい動作**——
**握り潰さず、もう一度打つ。**

🚨 **予告の窓は、共有ファイルでは「他人に拾われうる時間」でもある。**
予告は「打つ前に止めてもらう」ための窓だが、**同じ窓が、自分の行を置く時間になる**。

🚨 **この守りは片務**（自分の側しか守れない）。**他人が窓を開けているときは効かない**
（同日、別の担当が **3 回**・さらに別の担当が **8 回**、窓を開けたまま作業していたと名乗っている）。
→ **🥈 と併用する。代替ではない。**

### 🥇 assert — **変える前の文字列と「件数」を指定して書く**

```
✅ 置換は「old が **ちょうど 1 件** であること」を確かめてから書く
   （python なら `assert s.count(old) == 1`。Edit 系の道具は既定でこの性質を持つ）
🚨 **0 件（もう直っている）でも、2 件（増えた）でも止まる**
```

🚨 **これは「さっき測った数」を前提にしていない。書くその瞬間に数え直している。**
同日、予告の窓の中で他人が同じ修正を入れたケースがあり、**担当を止めたのは
時刻の見張りではなく、この assert だった**（`git log` を予告の前に引いても、窓の中の変更は見えない）。

> **前提を新しくする**（log / status を引き直す）と、**前提を消す**（assert）は別。
> 消せるなら消すほうが強い。

### 🥈 見て気づく — **`commit --only` を打つ直前に、行を目で読む**

```
git diff HEAD -U0 --output-indicator-new='>' --output-indicator-old='<' -- <パス…> | grep -E '^[<>]'
```

🚨 **記号を `>` / `<` に付け替えるのが要点**（2026-08-17・司令塔）。
差分の `+`/`-` と、中身の `+`/`-`（markdown の箇条書き・`---` の削除・`diff --git` を含む行）が
**同じ列に並んで区別できない**——それがこの守りを **6 回**壊した根だった。
**別の記号にすれば、条件で外す必要がそもそも無い。**

```
🚨 未追跡（`??`）は diff 系に出ない → `git -C <根> status --porcelain -- <パス…>` を併せて見る
```

🚨 **`git diff` ではなく `git diff HEAD`**。`git diff` は「作業ツリー ⇄ 索引」なので、
**他人が既に `git add` した行は 1 行も見えない**（＝ **いちばん危ない状態で、いちばん静かに 0 を返す**）。

🚨 **この守りは、同じ日に 6 回直っている**（箇条書きを落とす / staged が見えない /
`--` で始まる削除を落とす / 複数パスでヘッダが混ざる / 未追跡が見えない / 記号が衝突する）。
**6 回直しても 7 つ目が在るかもしれない。単独では頼らない。**

**触る前の 1 手（安い）**: `git status --porcelain -- <パス>` の **1 列目**

```
`M ` … 🚨 誰かが add 済み（**`git diff` では見えない**）
` M` … add されていない ／ `MM` … 両方 ／ `??` … 未追跡
```

## 1-5. 🚨 同じことが「枝」でも起きる（2026-08-16 実測・3 例目）

共有ツリーで誰かが `git checkout` すると、**以後のコミットは全員ぶん、その枝に載る**。

```
【測った】03:30 `main` → `chore/v1-scope-drop-promise-table` へ切替（reflog）
   以後 **3 本**（別々の担当）が **main に入っていない**状態で積まれた
   🟢 対照 `HEAD..main` … 0 本（＝ 取り残しではなく、分岐しただけ）
🚨 同じ日に **1 時間で 3 回**起きている（うち 1 回は **main より 6 本遅れた枝**だった）
```

🚨 **`git status` も `git diff` も、いまの枝の中しか見ない。**
**門は緑・commit も成功し、どこにも「main ではない」とは出ない。**
＝ §0 の「ファイル単位でしか絞れない」と同じ形が、**枝単位**で起きている。

```
✅ 守り: **打つ前に** `git rev-parse --abbrev-ref HEAD`
🚨 そして共有ツリーでの `git checkout` は**許可制**（枝が要るなら `git worktree` を使う）
```

### 🚨 この守りが見えないもの（**配る前に 1 つ挙げる**）

**detached HEAD**。使い捨ての台で実測した:

```
`git rev-parse --abbrev-ref HEAD` → 🚨 **`HEAD`**
   ＝ **「HEAD」という名前の枝に居るように読める**（**守りが素通りする**）
その状態で commit すると … 🚨 **どの枝にも載らない**（sha でしか辿れない）
   `git branch --contains HEAD`（擬似行を除く）… **0 本**
   🟢 対照 main の先端 … **1 本**（＝ この数え方は動く）
```

```
🟢 見えるもの … `git status -sb` の 1 行目 … **`## HEAD (no branch)`**
🟢 見えるもの … **commit 自身の出力** … `[detached HEAD baa9d6d]`
   ＝ 🚨 **枝ずれに気づかせたのも、この commit の出力だった**（`[chore/… a17dd36]`）
```

🚨 **`git branch --contains` は、detached のとき `* (HEAD detached from …)` という
擬似行を出す。** そのまま `wc -l` すると **1**（＝「載っている」と読める）。
**道具が自分を数える**——`ps | grep` が自分のコマンド行を数えるのと同じ族。

## 2. 🚨 数ではなく行を見る

`git diff --stat` の数は「**何の数か**」を言わない。
同日、`+10` を「description が長いから」と読んで add し、**8 行が別人のものだった**例が在る。

```
❌ 「追加 10 行だから、私の description だけ」
✅ **行を読む。自分が書いていない行が 1 行でも在れば、止めて持ち主へ 1 行**
```

## 3. 共有ファイルとは（このリポジトリで）

```
knowledge/**  docs/**  （とくに index.md — **全員が 1 行ずつ足す**）
lefthook.yml  apps/studio/scripts/**  （＝ 実行される場所。予告制）
```

🚨 **`knowledge/` に置いた時点で、それは自分のファイルではない。**
「自分が書いたファイルだから」は、共有ファイルでは予告を省く理由にならない。

## 4. アンチパターン

- ❌ 共有ファイルを編集してから予告を出し、返事を待つ（**窓に置く**）
- ❌ `--only` / `git add <パス>` を「他人の行も守れる」と読む（**ファイルしか絞らない**）
- ❌ `git diff`（`HEAD` なし）で「他人の行は無い」と判断する（**staged が見えない**）
- ❌ `--stat` の行数だけを見て打つ（**数は何の数かを言わない**）
- ❌ 🚨 **共有ツリーで `git add` を使う**（**add と commit の間の窓で、他人が自分の行を運ぶ**。§1）
- ❌ 置換を、対象の存在と件数を確かめずに書く（**もう直っていても上書きする**）
- ❌ 本体と索引の 1 行を別々の commit で出す（**索引だけ先に入る窓ができる**）

## 5. レビュー観点

- [ ] 共有ファイルなら、**予告 → 編集 → `git commit --only`** の順で出したか（🚨 **`git add` を打っていないか**）
- [ ] 置換に、変える前の文字列と**件数**の確認が入っているか
- [ ] 打つ直前に `git diff HEAD -U0 --output-indicator-new='>' --output-indicator-old='<'` で**行を**読んだか
- [ ] `git status --porcelain -- <パス>` の 1 列目を見たか（`M ` を見落としていないか）
- [ ] 本体と索引を同じ commit で出したか
