# フォルダは「誰かの持ち物」にしない

## 背景

認可の穴を塞ぐ作業（ファイル・フォルダに認可が入っていなかった）の中で、
受入基準として「A が B のフォルダを見られないこと」を求めた。

しかし実測の結果、**`directus_folders` の列は `id` / `name` / `parent` の3つだけで、
所有者を表す列が無い**ことが分かった。所有者ベースの行フィルタが**そもそも書けない**。

## 決定

> 基準日: 2026-08-13

**フォルダは組織全体の整理棚として扱い、所有者による分離をしない。**

権限は「フォルダというコレクションに対する権限」（見られる / 作れる / 消せる）で制御する。
これは Directus と同じ設計であり、欠陥ではない。

受入基準は「**フォルダにも認可機構が載っていること**」に読み替える。実測で確認したのは以下:

| 確認 | 結果 |
|---|---|
| ポリシー未付与のユーザーがフォルダ一覧を取得 | **403**（fail-closed が効いている） |
| 管理者がフォルダ一覧を取得 | **200** |
| ポリシー未付与のユーザーがフォルダを作成 | **403** |

## 理由

1. **Directus でもフォルダは所有されない。** フォルダは「誰の持ち物か」ではなく
   「どこに置いてあるか」を表す構造で、アクセス制御はコレクション単位で行う。
   前身プロジェクトの実運用でも 16 フォルダを**共有の整理棚**として使っていた。
2. **所有者を持たせると、共有が難しくなる。** 部署やチームで同じ棚を使う運用が普通なので、
   所有者で割ると「誰も触れないフォルダ」が生まれやすい。
3. **ファイル本体には所有ベースの分離が効いている。** 分離が必要なのは中身であって、棚ではない。

## 影響

- フォルダ一覧は「そのユーザーがフォルダ権限を持っているかどうか」で全部見えるか全部見えないかになる。
  **フォルダ単位の細かい出し分けはできない。**
- 将来これが必要になったら **`directus_folders` に所有者列（またはテナント列）を足す**マイグレーションが要る。
  そのうえで、ファイルと同じ行フィルタの仕組みに載せられる。
- ファイル本体の分離は別途効いているので、**フォルダが見えても中身が見えるわけではない**。

## 根拠

- `apps/studio/lib/db/migrations/20260804001000_create_directus_folders.ts` を実測。
  列は `id` / `name` / `parent`（`parent` は自己参照の外部キー）のみ
- 上記3件の HTTP ステータスを実測（2026-08-13）
- 前身プロジェクトの実運用記録（16 フォルダを共有の整理棚として使用）
